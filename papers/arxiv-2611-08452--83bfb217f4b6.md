###### Abstract

Reproducing machine learning experiments requires reconstructing
procedures from information scattered across papers, released code, and
supporting artifacts. For coding agents, reproduction success can
therefore depend on their ability to fill in missing details, rather
than on the released artifacts alone. We ask whether preserving
recovered procedures and decisions improves subsequent independent
reproduction. We define a standardized artifact design comprising a
refined codebase, environment setup, experiment launchers, and a
reproduction guide, and introduce ReproBridge, an agent workflow for
constructing these refined reproducible artifacts. ReproBridge-Bench
provides 1,029 tasks from 387 experiments across 36 papers, anchored by
five human-verified reference scores per task. Agents attempt tasks in
fresh sessions with raw code or refined artifacts; a separate Auditor
checks execution evidence. Across four evaluated models, refined
artifacts raise mean reproduction success from 76.4% to 92.6% and reduce
downstream API spending by 19.7% on average. The cross-model
success-rate spread narrows from 21.6 to 3.9 percentage points, with all
four models achieving mean success rates above 90%. Removing any
component reduces success in the ablation study, with the largest losses
from code and environment removal. These results suggest that preserving
execution knowledge helps even models with lower raw-code success
reproduce experiments more reliably and at lower API cost. ¹¹ 1 Project

[https://wyyyb.github.io/reprobridge_website/](https://wyyyb.github.io/reprobridge_website/)

## 1 Introduction

Reproducing a machine learning experiment often requires recovering
details that its paper and released code leave implicit. A reproducer
may resolve incompatible dependencies, identify the intended
configuration, repair a data loader, and work out how run outputs become
a reported score. Even a successful attempt can leave these decisions
buried in conversations or shell histories, forcing the next reproducer
to repeat the investigation. Code release is an essential starting point
([Pineau et al., 2021](#bib.bib1)); preserving the procedure recovered
during execution is a further step toward reusable research artifacts
([Stodden et al., 2016](#bib.bib20)).

Coding-agent benchmarks expose this reconstruction burden through
unresolved dependencies and misidentified outputs ([Siegel et al.,
2024](#bib.bib7)), missing implementation details ([Xiang et al.,
2025](#bib.bib21)), and plans that never become completed experiments
([Starace et al., 2025](#bib.bib6)). Consulting cited papers can recover
some missing details ([Zhao et al., 2026b](#bib.bib25)), but successful
execution may still depend on knowledge a capable agent supplies
implicitly. _How much does reproduction success depend on released
artifacts, and how much on the reproducer’s ability to compensate for
missing details?_

Here, _reproduction_ means independently re-executing machine-learning
experiments using author-released materials, targeting numerically
compatible measurements. _Research artifacts_ comprise the code, data,
checkpoints, environment specifications, and documentation supporting a
study. Our hypothesis is that preserving the procedures and decisions
recovered during reproduction can improve computational reproducibility.
Dependency resolution can become an installation procedure; experiment
discovery, a dedicated launcher; and a correction, a documented choice
with its justification and affected tasks. We study this hypothesis
through three contributions.

##### Artifact design.

We standardize a _refined reproducible artifact_ with four components: a
refined codebase, environment setup, experiment launchers, and a
reproduction guide (Figure ; Section
[3.2](#S3.SS2 "3.2 Four components preserve execution knowledge ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Together they preserve executable procedures and the reasons for their
settings and repairs. Component removals test the contribution of each
part, while an ordinary-outputs control tests reuse of code, scripts,
and logs without the standardized handoff.

##### Construction workflow.

ReproBridge constructs these artifacts from a paper and its official
repository (Section
[3.1](#S3.SS1 "3.1 Construction workflow ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Humans define the workflow, delivery standards, and protocols; agents
specify experiments, prepare and execute them, and preserve the
resulting procedures through review and packaging. Subsequent reuse is
evaluated in fresh Reproducer sessions that receive either the raw
codebase or the refined artifact.

##### Benchmark and empirical evaluation.

ReproBridge-Bench provides 1,029 tasks from 387 experiments across 36
papers, with five human-verified reference scores per task (Section
[2](#S2 "2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Numerical compatibility is assessed against observed executions and
their variability; a separate Auditor checks execution evidence because
matching numbers alone can conceal substituted measurements. Across four
coding agents, refined artifacts improve success by 5.5 to 23.2 pp and
reduce downstream API spending by 16.8% to 23.7%. Robustness analyses,
component ablations, case studies, and human validation of the integrity
checks examine the scope and mechanisms of these gains (Section
[4](#S4 "4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).

## 2 Problem formulation and ReproBridge-Bench

### 2.1 Execution deviations and reference variation

A task specifies the data, model configuration, training or evaluation
procedure, and reporting statistic to reproduce. The paper’s stated
setup takes precedence over conflicting code. Let $`\mu`$ be the
expected value of that statistic when the specified experiment is
faithfully executed. The published score is one observation, not an
error-free value of $`\mu`$.

For an attempt producing a measurement $`Y`$, we write

|     |     |     |
| --- | --- | --- |
|     |

       ``` math
       Y=\mu+D+\varepsilon.
       ```                   |     |

Here $`D`$ is the shift in expectation from execution choices departing
from the specified experiment, and $`\varepsilon`$ is zero-mean
variation conditional on them. This working model draws on the
distinction between systematic and random effects in measurement ([Joint
Committee for Guides in Metrology, 2020](#bib.bib16); [Taylor and
Kuyatt, 1994](#bib.bib4)). Stochastic training can vary between runs
([Nagarajan et al., 2018](#bib.bib3)). Independent repetitions can
reduce uncertainty about the mean of a fixed procedure ([Bouthillier et
al., 2021](#bib.bib2)), but do not remove a persistent shift $`D`$.
ReproBridge aims to reduce $`|D|`$ by preserving procedures and
decisions for faithful execution, while $`\varepsilon`$ remains.

We use five human-verified reference observations of the same statistic
per task. Assuming faithful and independent reference executions
($`D=0`$), their mean estimates $`\mu`$, and their spread characterizes
$`\varepsilon`$. A prediction interval accommodates uncertainty in that
estimated center and variation in a new observation $`Y`$ ([National
Institute of Standards and Technology, n.d.](#bib.bib12)). Section
[2.3](#S2.SS3 "2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
describes collection and verification. Numerical compatibility is
combined with the execution-integrity checks in Section
[4.1](#S4.SS1 "4.1 Evaluation protocol and setup ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"):
a nearby number alone does not show that the intended experiment was
performed.

### 2.3 Reference collection and task verification

The reference protocol specifies five human reproducers on separate
servers, starting from the same pinned raw commit with separate
execution directories and coding-agent sessions. They must not reuse
another participant’s generated scripts or measurements, refined
artifacts, or downstream reproduction traces. Coding-agent assistance is
permitted, but humans inspect the scripts, configurations, edits, and
measurement extraction actually used. Before aggregation, the five
reproducers’ execution setups were cross-verified against the paper’s
specified setup and the common task definition. Each reference
observation measures the specified task statistic: a multi-seed mean or
best-of-$`N`$ statistic is one observation, not interchangeable with
single-seed scores.

Verifiers must fix unspecified repetition and seed choices before
inspecting scores, and must not tune procedures or repeat valid
measurements until they approach the published value. Diagnostic runs
and corrected reruns are recorded separately with reasons for
replacement; numerical disagreement alone does not justify discarding a
valid execution. Appendix
[A.3](#A1.SS3 "A.3 Human reference-verification protocol ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
gives the complete verification and evidence-retention protocol.

##### Numerical compatibility.

Following Section
[2.1](#S2.SS1 "2.1 Execution deviations and reference variation ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
the five observations estimate $`\mu`$ and reference variation
$`\varepsilon`$. For task $`j`$, let $`p_{j}`$ be the published score
and $`x_{j1},\ldots,x_{j5}`$ the reference observations, with sample
mean $`\bar{x}_{j}`$ and sample standard deviation $`s_{j}`$. A reported
range is represented by its midpoint. The compatibility interval is

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
I_{j}^{(q)}=[\bar{x}_{j}-r_{j}^{(q)},\bar{x}_{j}+r_{j}^{(q)}],\qquad r_{j}^{(q)}=\max\left\{t_{(1+q)/2,4}s_{j}\sqrt{1+\tfrac{1}{5}},\;0.01|\bar{x}_{j}|\right\}.
``` |  | (1) |

The default is $`q=0.95`$. Without the explicit 1% tolerance floor, this
is a Student-$`t`$ prediction interval for a new observation of the same
statistic under an independent, approximately normal working model
([National Institute of Standards and Technology, n.d.](#bib.bib12)). It
accommodates both uncertainty in the reference mean and variation in the
new observation. Thresholds are fixed across raw and refined-artifact
conditions; $`q=0.80`$ supplies the stricter scoring check in Section
[4.3](#S4.SS3 "4.3 Gains persist across papers and scoring thresholds ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").

##### Reference variability and task eligibility.

Categories 1 and 2 both require $`p_{j}\in I_{j}^{(.95)}`$, and differ
only in relative reference variability. We define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
V_{j}=100\,\frac{\max_{i}x_{ji}-\min_{i}x_{ji}}{|p_{j}|}\quad(p_{j}\neq 0);\qquad V_{j}=+\infty\quad(p_{j}=0).
``` |  | (2) |

Stable tasks satisfy $`V_{j}\leq 10`$, meaning that the reference range
is at most 10% of the absolute published score; higher-variability tasks
exceed this threshold. Both categories enter the downstream evaluation.
We pool them for the main comparison and examine them separately in
Section
[4.3](#S4.SS3.SSS0.Px3 "Reference variability. ‣ 4.3 Gains persist across papers and scoring thresholds ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").
Appendix
[A.4](#A1.SS4 "A.4 Error model and reference rules ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
gives the uncertainty derivation and additional details of the numerical
rules.

### 2.4 Scope and information access

The evaluated set contains 631 full-procedure and 398 evaluation-only
tasks (730 GPU, 299 CPU-only). Evaluating an explicitly permitted
official checkpoint does not require repeating its training. Evaluation
alone cannot establish completion of a training task.

All eight downstream conditions use the same task categories and
numerical thresholds, applied outside the Reproducer session. Published
targets remain visible in the paper and task specification; the Auditor
checks that submitted values come from new executions. Session
instructions withhold the reference information, alternative repository
condition, and other agents’ run directories. An allowed checkpoint may
serve as input; a shipped score file never counts as a measurement.

The benchmark includes 586 lower-is-better and 443 higher-is-better
measurements, all assessed by the same two-sided compatibility rule.
This evaluates agreement with the specified experimental result: a score
beyond either bound remains numerically incompatible, including one that
improves on the published value. Reference submissions must also link
each score to the starting code commit, executed scripts and edits,
environment and hardware, configuration and seeds, raw outputs, and
score-extraction or aggregation procedure, making the reported statistic
traceable to a concrete execution. Appendix
[A](#A1 "Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
gives selection records, verification protocols, and statistical rules.

## 3 ReproBridge: artifact design and construction

ReproBridge turns reproduction work into an artifact that a later
researcher or agent can use without access to the construction
conversation. The handoff comprises refined code, environment setup,
experiment launchers, and a reproduction guide. Its construction
workflow preserves the evidence behind execution choices as well as the
executable steps themselves.

### 3.1 Construction workflow

Humans define the workflow, delivery standards, and protocols; agents
perform all construction, review, and packaging. Figure
[2](#S3.F2 "Figure 2 ‣ 3.1 Construction workflow ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
organizes this work into three stages: *Specify* fixes the intended
experiment before execution; *Execute* establishes a working procedure
and records measurements, repairs, and failures; and *Preserve* packages
that procedure and its rationale for reuse. Table
[2](#S3.T2 "Table 2 ‣ 3.1 Construction workflow ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
specifies each role’s inputs and persistent outputs.

Figure 2: ReproBridge artifact construction. Six roles form three
stages: Specify (Intake, Planner), Execute (Builder, construction
Reproducer), and Preserve (Distiller, Packager). Footers list stage
outputs. Solid arrows show construction; dashed links show independent
review and revision. The final handoff contains refined code,

| Role |  Input and responsibility |  Output and check |
|----|----|----|
| Intake |  Paper, pinned raw code, selected tasks; read and map the inputs |  Input manifest, experiment groups, artifact availability, initial ambiguities |
| Planner |  Task mapping and ambiguities; specify the measurement before execution |  Task specifications with source references, recorded choices, execution plans, draft launchers |
| Builder |  Dependency and artifact requirements; construct a working environment |  Locked dependencies, setup and data scripts, container definition, smoke-test evidence |
| Reproducer |  Plans and verified setup; execute and record justified changes |  File-backed measurements, code changes, repetition records, explicit failure reasons |
| Distiller |  Execution evidence, repairs, and decisions; synthesize the handoff |  Reproduction guide, change record, aggregation and variability guidance |
| Packager |  Code, setup, launchers, and documents; assemble a portable deliverable |  Refined artifact and clean-shell verification evidence |
| Reviewer |  Plans, execution records, or completed artifact; challenge unsupported claims |  Localized findings at planning, reproduction, and final handoff checkpoints |

Table 2: Construction skills: inputs, responsibility, and persistent

##### Persistent evidence connects the stages.

A phase controller sequences the roles and checks required outputs
between stages. Before scored execution, task specifications record the
data, model, procedure, reporting statistic, source references, and
unresolved choices. This makes execution decisions explicit before their
results are known. When paper and code conflict, agents follow the
paper’s setup and flag the discrepancy (Section
[6](#S6 "6 Discussion and limitations ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Each measurement must link to an actual output file; blocked tasks
retain an explicit failure reason, and diagnostic runs remain separate
from scored repetitions. The guide and change record are then grounded
in these stored specifications, execution records, and justified
repairs.

##### Independent review tests the evidence and the handoff.

A Reviewer inspects plans, execution records, and the completed artifact
in contexts separate from the roles being reviewed. It returns localized
findings to the responsible stage for revision and rechecking. Delivery
also requires testing the supplied entry points from a clean shell,
including an inexpensive real repetition and checks on output structure
and score extraction. The delivered environment must match the one used
for construction measurements. Human reference information is withheld
throughout construction. Appendix
[B](#A2 "Appendix B Artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
gives the full role specifications and delivery checks.

### 3.2 Four components preserve execution knowledge

A later reproducer needs to know what code to run, how to prepare its
environment, how to obtain the requested measurement, and why particular
choices were made. The four-component *refined reproducible artifact*
(RRA in figures and tables) addresses these needs. The *refined
codebase* repairs execution defects and supplies missing experiment
support. *Environment setup* specifies compatible dependencies and data
or checkpoint acquisition. *Experiment launchers* connect tasks to
configurations, execution scope, outputs, and measurement extraction,
distinguishing scored runs from smoke tests. The *reproduction guide*,
including its change record, explains settings, paper–code
discrepancies, reporting statistics, and resource or numerical
sensitivities. Section
[4.5](#S4.SS5 "4.5 Each artifact component contributes to reuse ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
tests the contribution of each component through removal experiments.

The guide connects instructions to their rationale. Each ambiguity entry
records its source location, the gap, the adopted resolution and
rationale, sensitivity, and affected tasks. The change record
distinguishes execution fixes, correctness fixes, and convenience
changes, while retaining pitfalls and open choices. Repetition guidance
preserves the specified reporting unit and characterizes variation
$`\varepsilon`$ without selecting favorable outcomes. Figure
[3](#S3.F3 "Figure 3 ‣ 3.2 Four components preserve execution knowledge ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
illustrates how SCIQL’s guide links measurement decisions and failure
checks to executable support; Appendix
[B.2](#A2.SS2 "B.2 Four-component handoff and document structure ‣ Appendix B Artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
expands its twelve-section structure.

Figure 3: A refined artifact for SCIQL. Left: selected guide entries
specify the six-criterion, five-seed protocol, unweighted aggregation,

## 4 Experiments

### 4.1 Evaluation protocol and setup

Opus 5 constructs the refined artifacts for the main experiment. Fresh
Reproducer sessions receive the paper, selected tasks, and either raw
code or its refined artifact. Construction conversations, hidden
reference observations, and the alternative condition are withheld.
Sessions submit new measurements and execution evidence; we compare
success, token usage, and API spending.

Sonnet 4.6, Sonnet 5, Opus 5, and Gemini 3.8 Flash (Gemini 3.8 in
figures and tables) attempt all 1,029 tasks from 36 test papers, with
one fresh session per paper–model–condition per evaluation. Both
raw-code and refined-artifact conditions use a 24-hour wall-clock limit
per paper. GPU experiments use eight H100-80GB GPUs. Codex is the
primary Auditor. Harnesses differ across vendors, so cross-model
comparisons are descriptive. Paper-wise, stratified, and task-level
diagnostics use the first evaluation. Appendix
[C](#A3 "Appendix C Evaluation protocol and audit validation ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
details the harness, information boundaries, and auditing.

##### Execution-integrity audit.

An independent Auditor checks the evidence chain for each reported
result, tracing the value to its output location, execution record, and
generating script. It uses ledger timestamps to check execution and
extraction order, and available script and output hashes to verify that
the inspected files match the recorded versions. The Auditor
cross-checks executed code, logs, and extracted values to locate copied
measurements, altered outputs, or substituted computations.

After mechanical screening identifies leads, a *Finder* inspects
executed code and records and proposes localized violations. A separate
*Refuter* tries to overturn each proposed invalidation by checking the
evidence, its effect on the measurement, and the task specification.
Unsubstantiated findings remain uncertain. If the evidence remains
contested, a panel examines its support, the measurement effect, and
alternative explanations. The Auditor operates after reproduction and
provides no feedback to the Reproducer.

##### Invalidation criteria and task success.

The five eligible violation classes distinguish copying a value without
measuring it, substituting the measurement instrument, altering an
operand used by the intended formula, choosing the reported outcome
conditional on observed values, and computing the wrong statistic.
Invalidation requires an eligible violation supported by localized
evidence, a material effect on the measurement, and a failed refutation.
A numerical mismatch, crashed run, hardware difference, or suspicion
without a localized artifact does not automatically meet these
conditions. Paper–code discrepancies are assessed against the same
criteria.

A task succeeds when its result lies in the fixed compatibility interval
(Equation
[1](#S2.E1 "In Numerical compatibility. ‣ 2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"))
and is not invalidated by the primary Auditor; missing or incompatible
results fail. Uncertain audit findings do not count as invalidations.
Section
[4.6](#S4.SS6 "4.6 Gains persist across Auditors despite imperfect detection ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
checks the sensitivity of this scoring rule to the Auditor and validates
audit judgments against human review.

### 4.4 Preserved procedures support recovery and reduce reconstruction

Figure 5: Recovering failures and shortening preparation.

Case studies and qualitative analyses use the first evaluation. Across
paired task–model outcomes, 813 raw failures become successes, against
136 reversals (Figure
[5](#S4.F5 "Figure 5 ‣ 4.4 Preserved procedures support recovery and reduce reconstruction ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Recoveries include 348 numerical mismatches, 210 unexecuted tasks due to
execution or resource barriers (*Not run*), and 255 audit-invalid
numerical matches. These records suggest two complementary
contributions: completing ambiguous or incomplete measurement
specifications and preserving executable procedures for reuse.

##### Completing and clarifying measurement specifications.

In Mixture of Concept Bottleneck Experts ([De Santis et al.,
2026](#bib.bib51)), the reduction of multiple tree-edit distances is
unspecified, and the released code lacks a collector for Table 1. Sonnet
5’s raw attempt sums the four distances, reporting 60 rather than 15.
The refined artifact resolves this ambiguity by specifying the
per-expression mean and supplying the collector; the later attempt
reports 15. SCIQL’s released code similarly leaves the mapping from run
outputs to table entries incomplete; the refined artifact specifies the
output field and aggregation across criteria and seeds. Such
clarification and experiment-to-result mapping together represent about
35% of the case-review attribution distribution.

##### Recovered configurations become executable: HELIX.

For HELIX ([Zhang et al., 2026a](#bib.bib32)), Opus 5 restores the
paper’s architecture on raw code but retains the shipped batch size and
learning rate. The refined artifact identifies a repository revision
matching that architecture, records it as the source of the adopted
settings, and exposes them through a launcher. A later attempt produces
numerically compatible MAEs for both illustrated tasks. The guide
records the evidence for the choice, and the launcher makes it reusable
(Appendix
[D.5](#A4.SS5.SSS0.Px1 "Recovering omitted configuration: HELIX. ‣ D.5 Worked reproduction examples ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).

##### A compatible environment transfers across sessions: WBMM.

For six COCO tasks in WBMM ([Song et al., 2026](#bib.bib61)), Sonnet
4.6’s raw attempt fails to install a compatible vision-library stack for
H100. The refined artifact preserves the dependency versions, build
prerequisite, and source-build route for the target architecture. The
later session executes all six tasks without a code patch; its box and
mask AP values agree numerically with the reported targets. This case
shows how an environment repair can become a reusable installation
procedure (Appendix
[D.5](#A4.SS5.SSS0.Px2 "An environment route that transfers: WBMM. ‣ D.5 Worked reproduction examples ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).

##### Fixing bugs in the released code.

In Effective Model Pruning ([Wang et al., 2026](#bib.bib46)), the
released loader silently labels all 10,000 TinyImageNet validation
images as one class. During construction, ReproBridge adds a script
organizing images by their true labels and a launcher check requiring
prepared data. In paired Gemini 3.8 Flash runs, ResNet-18 validation
loss changes from 8.898 on raw code to 2.288 with the refined artifact,
close to the paper’s 2.303. Model–paper sessions changing code
downstream fall from 113/144 to 54/144, and median time to first scored
execution decreases for every model (Figure
[5](#S4.F5 "Figure 5 ‣ 4.4 Preserved procedures support recovery and reduce reconstruction ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
right). Together with lower token use, this indicates less
reconstruction.

##### Explicit procedures also help the model that built them.

Clearer code organization and explicit execution decisions can reduce
repeated search and context demands, even for the model that built the
artifact. In ETTFS ([Che et al., 2026](#bib.bib45)), the raw Opus 5
attempt searches 6,377 lines of Python for measurement code absent from
the release. The refined artifact organizes the added measurement code
into a dedicated profiling module, a launcher that sequences training
and profiling, and documented output fields. A fresh Opus 5 session
follows this structure and completes a previously blocked measurement.

##### Remaining failures.

Failures shared by both handoffs mainly reflect paper–code setup
mismatches, typographical errors in the paper, or experimental
variability placing measurements outside the compatibility interval.
Refinement can also preserve or introduce incorrect experimental
choices.

The 136 reversals from raw success to refined failure comprise 84
numerical mismatches, 31 resource/access failures, 11 audit-invalid
matches, and 10 execution blockers. AuxiliaryMCMC and LiME account for
50 and 14 reversals, respectively, or 47.1% combined. The LiME case
([Kowsher et al., 2026](#bib.bib39)) illustrates an attempt that fails
to complete training and evaluation; AuxiliaryMCMC ([Yuan and Wang,
2026](#bib.bib43)) illustrates numerical fragility, hardware
sensitivity, and protocol deviations under time pressure (Appendix
[D.3](#A4.SS3 "D.3 Failure modes and concentrated regressions ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).

##### Component-removal protocol.

Refined-code removal restores the original source; environment removal
deletes the setup route; launcher removal deletes the experiment entry
points. For these three conditions, descriptions of the removed
component are also deleted from the remaining documentation and scripts.
The guide ablation removes the guide itself. The change record belongs
to the documentation component.

A source file and an explanation of how to reconstruct it can carry
overlapping knowledge. Deleting only the file leaves a route for the
downstream agent to restore the same functionality. Removing both the
component and its descriptions tests the loss of that information while
leaving the other components available; the resulting losses are
conditional on those retained materials.

##### The full artifact improves on ordinary outputs.

The complete artifact outperforms ordinary outputs by 11.8 pp (Table
[6](#S4.T6 "Table 6 ‣ 4.5 Each artifact component contributes to reuse ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
Ordinary outputs also outperform raw code, demonstrating value in
reusing execution work. Both handoffs come from separate upstream runs
with comparable resource use. The comparison evaluates protocol-guided
construction and its resulting handoff.

Code and environment removal cause the largest losses, showing the need
for repaired implementations and compatible dependencies. Removing the
guide or launchers also reduces success when code and environment remain
available: an executable codebase can still leave settings, measurement
rules, and entry points implicit. Retained components can partly
compensate for a removal (Appendix
[D.4](#A4.SS4 "D.4 Component ablations and reconstruction effort ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).
These losses favor pairing executable support with explicit guidance on
measuring results.

### 4.7 Repeated reuse can offset construction API cost

Constructing the 36 artifacts costs \$5,026 in API usage (\$139.61 per
paper). At the mean downstream costs in Table
[3](#S4.T3 "Table 3 ‣ 4.2 Refined artifacts improve success and reduce downstream cost ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
break-even requires 8, 13, and 9 reuse rounds for Sonnet 4.6, Sonnet 5,
and Opus 5, respectively. Each round repeats all 36 papers; the scenario
charges the full construction cost to one model, holds prices and
savings fixed, and excludes GPU, auditing, and maintenance costs. The
corresponding API savings are \$653, \$409, and \$615 per complete reuse
round, respectively. Higher success accompanies these savings, so reuse
improves reproduction while progressively recovering the construction
investment. Appendix
[E](#A5 "Appendix E Cost accounting ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
details the accounting rates and break-even calculation.

## 5 Related work

##### Scientific trust and computational reproducibility.

Scientific trust depends on collective scrutiny and accessible evidence
([Oreskes, 2019](#bib.bib13); [Nosek et al., 2015](#bib.bib14); [Munafò
et al., 2017](#bib.bib15)); AI-assisted research retains these
requirements ([Messeri and Crockett, 2024](#bib.bib18)). Following ACM
terminology, *reproducibility* means independent execution of authors’
artifacts, rather than independent reimplementation or bitwise-identical
replay ([Association for Computing Machinery, 2020](#bib.bib5); [Peng,
2011](#bib.bib19)). Reproducibility Enhancement Principles and the
NeurIPS reproducibility program promote explicit dependencies, code
release, and reporting checklists ([Stodden et al., 2016](#bib.bib20);
[Pineau et al., 2021](#bib.bib1)).

##### Research reproduction benchmarks.

PaperBench assesses reconstruction through expert rubrics covering code,
execution, and results ([Starace et al., 2025](#bib.bib6));
SciReplicate-Bench also studies implementation reconstruction ([Xiang et
al., 2025](#bib.bib21)). REPRO-Bench and ReplicationBench extend
assessment to social science and astrophysics ([Hu et al.,
2025](#bib.bib22); [Ye et al., 2025](#bib.bib23)). CORE-Bench tests
execution of released Code Ocean capsules and questions about their
outputs ([Siegel et al., 2024](#bib.bib7)). ReproBridge-Bench evaluates
released artifacts through binary task success, combining intervals
based on variability across five human-verified executions with an
independent integrity audit. Tasks include GPU training and evaluation.
Table
[4](#S4.T4 "Table 4 ‣ External benchmark. ‣ 4.2 Refined artifacts improve success and reduce downstream cost ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
compares handoffs under CORE-Bench’s scoring rule.

##### Automated reproduction and reusable experience.

PaperCoder constructs repositories through planning and code generation
([Seo et al., 2026](#bib.bib24)). AutoReproduce recovers implicit
details from cited papers and evaluates execution fidelity ([Zhao et
al., 2026b](#bib.bib25)). VERITAS executes research procedures and
produces patched code, fix records, and claim assessments ([Liu et al.,
2026a](#bib.bib9)); our external comparison tests reuse of its handoff.
Reflexion retains verbal feedback, while Voyager accumulates executable
skills ([Shinn et al., 2023](#bib.bib10); [Wang et al.,
2023](#bib.bib11)). The Compiler for Agent-Native Research Artifacts
(ARA) ([Liu et al., 2026b](#bib.bib8)) packages papers and repositories
with expert rubrics in its PaperBench study; a model judge scores
reproduction against those rubrics. We construct runnable four-component
handoffs without evaluation rubrics or human reference scores, and
assess their value through four component removals and an
ordinary-outputs control.

## 6 Discussion and limitations

The four component contracts make reproduction experience reusable, and
ReproBridge-Bench provides verified reference scores for evaluation. We
study their roles together; the delivery protocol guides what
ReproBridge recovers and preserves during construction. In the
formulation of Section
[2.1](#S2.SS1 "2.1 Execution deviations and reference variation ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
the aim is to reduce avoidable deviations $`D`$ while documenting
uncertainty about the intended experiment.

### 6.1 Use before submission and by later reproducers

The primary intended use is for authors to apply ReproBridge as a
reproducibility check before submitting a paper and releasing its
artifacts. Executing the paper’s specified setup can expose missing
details, execution barriers, and paper–code inconsistencies, giving
authors concrete issues to inspect and correct before submission.
Third-party reproducers can likewise preserve their work in the same
format to lower the cost of later attempts. A human reader can use the
setup route and launchers to execute experiments, then inspect the guide
and change record to assess the settings and repairs. Our experiments
measure reuse by coding agents.

### 6.2 Paper–code misalignment

When the paper and released code conflict, ReproBridge strictly follows
the paper’s setup and flags the discrepancy with source locations and
affected tasks. For example, the Manifold-Aware Perturbations guide
identifies a learning rate of $`10^{-4}`$ in the paper versus
$`10^{-3}`$ in the released code. Such records help authors check
consistency between their manuscript and implementation during the
pre-submission review described above.

A separate agent-assisted static analysis records 238 in-scope
contradiction findings touching 669 distinct selected tasks. A
contradiction requires an explicit paper statement and conflicting
implemented behavior; absent implementations and choices on which the
paper is silent are recorded separately. These findings are possible
sources of execution deviation $`D`$, but their effects on measured
performance require controlled comparisons. They are neither
human-validated error rates nor explanations of the measured gains. The
analysis is separate from primary success scoring, and its records were
not supplied to evaluated Reproducers. Appendix
[D.6](#A4.SS6 "D.6 Separate alignment analysis ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
documents the scope, categories, and evidence.

### 6.3 Limitations

The evaluation conditions on retained papers, fixed reference regions,
and the tested agents; it is not a conference-wide reproduction rate.
Five reference observations are a protocol choice, not a guarantee of
adequate uncertainty estimation. Numerical compatibility does not
certify scientific validity or complete fidelity to the stated
experiment, and refined artifacts can preserve incorrect assumptions.
Automated audits also miss some violations, as quantified against human
verification.

The complete artifact intervention includes upstream investigation,
repair, review, and packaging. Ordinary outputs and refined artifacts
are produced in separate runs with comparable upstream resource use.
This comparison evaluates the construction workflow and resulting
handoff together; it does not isolate the effect of reorganizing
identical outputs. Component ablations measure losses conditional on the
remaining materials. Case annotations and variability strata describe
patterns rather than isolate causal effects.

API savings concern downstream Reproducer sessions. Construction,
independent verification, GPU execution, maintenance, and human review
have separate costs; reuse estimates assume fixed prices and savings.
Human time savings and comprehension require a separate study.

## 7 Conclusion

ReproBridge standardizes recovered reproduction procedures and decisions
into four reusable components: a refined codebase, environment setup,
experiment launchers, and a reproduction guide. ReproBridge-Bench
provides verified reference scores to assess their value. Reproduction
success depends jointly on artifact quality and reproducer ability. All
four evaluated models achieve mean reproduction success above 90% with
refined artifacts, including those with lower raw-code success. The
cross-model success-rate spread and downstream API spending both
decrease. Removing code or environment setup causes the largest ablation
losses; removing guides or launchers also reduces success with the other
components retained.

Future work should evaluate reuse by human researchers and measure the
full costs of constructing, verifying, and maintaining artifacts across
repeated attempts.

## Appendix A Benchmark and reference protocol

This appendix covers selection, reference verification, statistical
rules, and paper inventories.

### A.1 Task selection and reporting units

##### Extraction and reporting units.

Each retained task has a paper identifier, task identifier, source
experiment identifier, paper-table locator, reported score, metric
direction, task type, and compute type. The selected set contains 730
GPU tasks and 299 CPU-only tasks; 586 have lower-is-better metrics and
443 higher-is-better metrics. Absolute interval membership is used in
both cases: outperforming the target in one direction does not
automatically satisfy numerical compatibility. Of the 36 papers, 28 are
classified as GPU papers and eight as CPU-only papers.

##### Sampling and exclusions.

The supplied sampling manifest records 742 Spotlight papers, a
mechanically filtered pool of 241 papers with code and
non-purely-theoretical content, a random sample of 50, and 36 retained
papers. Its primary exclusion categories are artifact/code availability
(six), compute requirements (four), and closed-model dependence (four).
The compute criteria concern papers for which more than half of the main
experiments require over 100 H100 GPU-hours per experiment or more than
one eight-H100 node; the API criterion concerns more than half of the
main experiments. These are selection criteria, not measured universal
execution budgets. Tables
[9](#A1.T9 "Table 9 ‣ A.5 Retained and excluded paper inventories ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
and
[10](#A1.T10 "Table 10 ‣ A.5 Retained and excluded paper inventories ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
provide the retained and excluded inventories.

### A.3 Human reference-verification protocol

For reference collection, a *human verifier* is a participant
responsible for both reproducing an experiment and checking its
execution evidence. The following requirements apply to each of the five
participants in Section
[2.3](#S2.SS3 "2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts");
this role is distinct from human validation of the downstream Auditors.

##### Common starting point and independent execution.

Each verifier must use a separate server and a fresh checkout of the
same pinned raw-repository commit, together with the paper, common task
specification, and authorized supporting artifacts. Execution
directories and coding-agent sessions must remain separate. Verifiers
must not reuse another participant’s generated scripts or measurements,
constructed refined artifacts, or downstream reproduction traces.
Published scores remain visible in the paper but cannot substitute for
newly computed measurements.

##### Experimental fidelity and documented repairs.

Before aggregating the reference measurements, the five verifiers’
executed scripts, configurations, and reporting procedures were
cross-verified to confirm that the executions followed the paper’s
specified setup and the common task definition. Verification must check
the task’s dataset and split, preprocessing, model configuration,
training procedure, and evaluation metric against that setup, including
required hardware and numerical precision, and inspect the released
implementation for consistency. A training task cannot be replaced by
checkpoint evaluation; an official checkpoint is permitted when the task
explicitly specifies evaluation-only reproduction. Necessary environment
or implementation fixes must retain the intended experiment, with their
rationale and differences from the starting commit recorded. Material
ambiguities must be documented rather than resolved by selecting
whichever interpretation best matches the published score.

##### Human responsibility for agent-assisted work.

Coding agents may assist with setup, debugging, and script preparation.
The human verifier must inspect the scripts and configuration actually
executed, including agent-generated edits, data loading, checkpoint
selection, and metric extraction. Verification must connect the reported
value to the computation that produced it, rather than rely on an
agent’s summary, a successful exit code, or numerical proximity alone. A
measurement whose execution fidelity cannot be established must not be
accepted as a reference score.

##### Consistent reporting units and repetitions.

Each participant must produce one complete observation of the specified
reporting statistic per task. For a multi-seed mean, this includes all
required seed-level runs and their prescribed aggregation; for
best-of-$`N`$, it includes all $`N`$ candidates and the specified
selection rule. Constituent runs must not be pooled across participants
to create the five reference observations. Seed choices, repetition
counts, and stopping rules must follow the task protocol; unspecified
choices must be documented and fixed before inspecting the resulting
scores. Prescribed fixed seeds do not remove the requirement for
separate executions.

##### No score-driven selection or substitution.

Verifiers must not tune procedures or repeat valid measurements until
they approach the paper’s score. Diagnostic runs and corrected reruns
must be distinguished from reference measurements, with the reason for
replacement recorded; numerical disagreement alone is not grounds for
discarding a valid execution. Failed or resource-blocked attempts must
retain their failure reason, without substituting cached scores, another
participant’s result, or an imputed value. Numerical compatibility is
assessed after execution verification using the common rules in Section
[2.3](#S2.SS3 "2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").

##### Evidence retention and information separation.

Each submitted observation must identify its task, verifier, execution,
starting commit, executed scripts and edits, environment and hardware,
configuration and seeds, raw outputs, and score-extraction or
aggregation procedure. The verification record must state what was
checked and any unresolved deviations. Reference measurements and
verification guidance must remain separate from ReproBridge and
downstream Reproducer inputs. These requirements support execution
fidelity; the statistical assumptions for combining the five
observations are specified separately in Appendix
[A.4](#A1.SS4 "A.4 Error model and reference rules ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").

### A.4 Error model and reference rules

We expand the formulation in Section
[2.1](#S2.SS1 "2.1 Execution deviations and reference variation ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
and give additional details of the compatibility and category rules
defined in Section
[2.3](#S2.SS3 "2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").

#### A.4.1 Execution error and reference uncertainty

Let $`\pi_{j}`$ specify the intended data, configuration, execution
conditions, and reporting statistic for task $`j`$. Its target is
$`\mu_{j}=\mathbb{E}_{\pi_{j}}[Y_{j}]`$, the expected result under that
procedure. A paper score $`p_{j}`$ has realized discrepancy
$`p_{j}-\mu_{j}`$; neither its magnitude nor its cause is determined by
the published value alone. If the reporting unit is a multi-seed mean or
best-of-$`N`$ statistic, $`Y_{j}`$ denotes that entire statistic.

For attempts yielding a computed result, let $`Z`$ denote the realized
execution procedure, including choices reconstructed from the supplied
information. Expectations describe repeated attempts for a fixed task,
agent, and artifact condition. Suppressing these indices, define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
m(Z)=\mathbb{E}[Y\mid Z],\qquad D=m(Z)-\mu,\qquad\varepsilon=Y-m(Z).
``` |  | (A.1) |

Then $`\mathbb{E}[\varepsilon\mid Z]=0`$ and
$`\mathbb{E}[D\varepsilon]=0`$. With finite second moments, conditioning
on the procedure gives

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathbb{E}[(Y-\mu)^{2}]`$ | $`\displaystyle=\mathbb{E}[(m(Z)-\mu)^{2}]+\mathbb{E}[\operatorname{Var}(Y\mid Z)]`$ |  | (A.2) |
|  |  | $`\displaystyle=(\mathbb{E}D)^{2}+\operatorname{Var}(D)+\mathbb{E}[\varepsilon^{2}].`$ |  |  |

The first two terms capture persistent mean shifts and variation in
those shifts across reconstructed procedures. The last captures
variation conditional on the procedure. This distinction is analogous to
between-condition and within-condition effects in measurement models
([Joint Committee for Guides in Metrology, 2020](#bib.bib16)). For a
faithful fixed procedure, $`D=0`$; conversely, $`D=0`$ alone does not
prove fidelity, since different procedures can have the same expected
score. Nor must the residual variance be equal across raw and
refined-artifact conditions. Independent repetitions of an unchanged
procedure reduce the variance of its mean, not a persistent shift in its
expected value.

##### What five reference observations estimate.

Under a faithful reference model, $`X_{ji}`$ are independent
observations of the same reporting statistic under comparable execution
conditions, with mean $`\mu_{j}`$ and variance
$`\sigma^{2}_{j,\mathrm{ref}}`$. Let $`\bar{X}_{j}`$ be their sample
mean and $`s_{j}`$ the observed sample standard deviation. Thus
$`\mathbb{E}[\bar{X}_{j}]=\mu_{j}`$ and
$`\operatorname{Var}(\bar{X}_{j})=\sigma^{2}_{j,\mathrm{ref}}/5`$.
Approximate normality motivates the Student-$`t`$ construction. A
confidence interval for $`\mu_{j}`$ has half-width
$`t_{0.975,4}s_{j}/\sqrt{5}`$ ([NIST/SEMATECH, n.d.](#bib.bib17)); a
prediction interval for a new observation instead has half-width
$`t_{0.975,4}s_{j}\sqrt{1+1/5}`$ ([National Institute of Standards and
Technology, n.d.](#bib.bib12)). The latter includes both
reference-center uncertainty and the new observation’s variability.
Equation
[1](#S2.E1 "In Numerical compatibility. ‣ 2.3 Reference collection and task verification ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
additionally imposes the explicit 1% tolerance floor.

If a downstream measurement $`Y`$ is independent of these unbiased
reference observations, then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{E}[(Y-\bar{X}_{j})^{2}]=\mathbb{E}[(Y-\mu_{j})^{2}]+\frac{\sigma^{2}_{j,\mathrm{ref}}}{5}.
``` |  | (A.3) |

Squared distance to the reference mean therefore also contains
reference-estimation uncertainty. The paper uses the decomposition to
motivate knowledge preservation, not to report empirically identified
bias or variance components.

### B.1 Construction-skill specifications

ReproBridge implements artifact construction through role-specific
skills, each with instructions, reference protocols, tools, and required
outputs. The specifications below expand the construction contracts and
coordination described in Section
[3.1](#S3.SS1 "3.1 Construction workflow ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
and Table
[2](#S3.T2 "Table 2 ‣ 3.1 Construction workflow ‣ 3 ReproBridge: artifact design and construction ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").
Separate downstream Reproducer and Auditor workflows evaluate the
artifacts; human reference collection and human audit validation belong
to benchmark development and evaluation, respectively.

##### Intake.

Read the complete paper, including appendices, before planning. Preserve
the selected task list and pinned raw commit. Map each task to its table
entry, survey the implementation, check required artifacts, and record
missing details. Do not silently substitute an unavailable repository
revision or redefine a task to fit the available code.

##### Planner.

For each task, specify the measurement, data, procedure, aggregation,
and stated repetitions, with references to supporting paper passages or
code locations. Group tasks that share an execution. Record the adopted
resolution of each ambiguity before the dependent run; prepare an
executable plan and launcher. The Planner does not execute experiments.
When paper and code conflict, strictly follow the paper’s stated setup,
flag the conflicting code and affected tasks, and record the required
implementation corrections before the dependent run.

##### Builder.

Resolve and record dependencies, provide reproducible acquisition of
required data and checkpoints, and test the resulting environment. The
environment described by the deliverable should be the one used for
construction measurements, not an untested reconstruction assembled
afterward. Environment work must not silently change the experimental
plan.

##### Construction Reproducer.

Execute planned experiments in the prepared environment. Link values to
actual output files and record commands, resources, and failures.
Distinguish diagnostic runs from scored repetitions; justify changes and
repetition extensions. Do not silently edit a frozen plan or select
favorable repetitions in place of the specified reporting statistic.
Every task needs a supported measurement or an explicit, evidenced
reason why none was produced.

##### Distiller.

Write the guide and change record from stored task specifications,
execution evidence, repairs, and choices. Explain the reporting
statistic, observed variability, resource requirements, pitfalls, and
uncovered scope. Preserve uncertainty where the record does not resolve
it. Historical measurements belong in separate result records, not in
instructions substituting for new measurements.

##### Packager.

Assemble the code, environment, launchers, and documentation actually
used. Check portable paths and verify the handoff from a clean shell,
including an inexpensive real repetition. Compare the output structure
and extraction route with the record. Do not invent replacement values
or treat a successful smoke test as completion of a scientific
experiment.

##### Reviewer.

Check the plan before scored execution, inspect evidence and recorded
changes during reproduction, and test the final handoff as an unfamiliar
user. Inspect the underlying files and outputs directly instead of
accepting another role’s summary. Produce localized findings with the
responsible role; do not repair and approve the same work in one
context.

##### Alignment extension.

The Aligner skill extracts paper-side requirements before inspecting
their implementation, then records contradictions separately from
missing code and unspecified details. It does not execute experiments,
edit plans, or infer a measured performance effect from a plausible
mechanism. Appendix
[D.6](#A4.SS6 "D.6 Separate alignment analysis ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")
describes the separate analysis.

### C.2 Independent reproduction skill

A fresh downstream Reproducer session uses the repro-run execution
skill. It receives the assigned repository, paper, and selected tasks,
then plans experiment scripts, prepares permitted inputs, schedules
executions, extracts values, and reports code changes and evidence
locators. The session retains responsibility for the final evidence,
including work delegated by the harness.

Programmatic support freezes inputs, schedules work under the resource
limits, links values to files, and checks evidence consistency.
Scientific assessment combines these records with inspection of the
paper and executed code.

### C.4 Two-person human verification protocol

Two human auditors cross-verified selected Reproducer outcomes. The
protocol below defines this review’s evidence requirements and
cross-checking responsibilities. It evaluates existing execution
records; human reference collection (Appendix
[A.3](#A1.SS3 "A.3 Human reference-verification protocol ‣ Appendix A Benchmark and reference protocol ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"))
generates numerical reference observations.

##### Review scope and unit.

Both reviewers must examine each selected task–condition outcome,
including outcomes not flagged by either automated Auditor. Reviewing
only automated disagreements or invalid flags would miss violations
accepted by both systems. Shared executions may support several
judgments, but each alleged violation must be linked to the affected
task scores; a problem in one experiment does not automatically
invalidate every result in the paper.

##### Trace the measurement to primary evidence.

Each reviewer must connect the submitted score to the executed command,
scripts and configuration, input artifacts, raw outputs, and extraction
or aggregation procedure. The supplied code and subsequent changes must
be inspected to establish the computation underlying the scored result.
Review must also check for copied values, substituted measurements,
result-dependent selection, incorrect reductions, and altered execution
records. Automated explanations can identify claims to inspect, but are
not evidence by themselves.

##### Apply the same invalidation criteria.

Reviewers must apply the invalidation criteria in Section
[4.1](#S4.SS1 "4.1 Evaluation protocol and setup ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
considering permitted reporting rules and environment or resource
effects before confirming a violation. Judgments concern the executed
procedure and its evidence rather than inferred intent.

##### Cross-check judgments and resolve disagreements.

Each reviewer must record a judgment and its supporting evidence before
the pair compares assessments. Each must then check the other’s task
mapping, supporting files and outputs, and interpretation, including
counterevidence. Disagreements must be resolved by returning to the
execution record and documenting why a judgment is retained or revised,
not by treating either automated Auditor as a tie-breaker. Both
reviewers must endorse the final human label and its rationale; an
unresolved case must not be presented as an agreed judgment.

##### Retain the review record and compare verdicts.

The record must retain task and condition identifiers, the associated
execution, both initial judgments, evidence locators, any disagreement
and its resolution, and the final cross-verified label. Correctness of
an automated verdict must be evaluated against this human label,
separately from whether its explanation identifies the correct
mechanism. Count each task–condition outcome once when computing
detection statistics, even when several outcomes share execution
evidence.

A reversal is a task–model pair that succeeds with raw code but fails

paper. Table

A paper can contain both recovered and lost tasks: Gemini’s

##### AuxiliaryMCMC: numerical fragility interacts with a finite budget.

The Opus 5 refined-artifact Gaussian sweep for AuxiliaryMCMC ([Yuan and
Wang, 2026](#bib.bib43)) targets 100 rounds at each of three acceptance
rates. Its measured workload exceeds the available clock at the chosen
concurrency, and the agent executes only 55 rounds per rate. The primary
audit invalidates numerical matches affected by this altered measurement
procedure. Separately, one Poisson-MALA chain remains constant with zero
acceptance. Its undefined effective sample size propagates through the
evaluator’s ordinary mean, leaving three measurements unavailable. The
Reproducer declines to redraw only the failed chain, which would select
a repetition based on its outcome. Effective sample size per second also
varies with host load and concurrency.

The raw attempt also runs fewer than 100 rounds in part of its sweep.
These records illustrate runtime constraints, numerical edge cases, and
deviations from the prescribed measurement procedure.

##### LiME: setup success is not experiment completion.

In Sonnet 5’s refined-artifact attempt on LiME ([Kowsher et al.,
2026](#bib.bib39)), data staging and environment preparation take
approximately 83 minutes, but the full schedule includes 5,949 training
steps followed by evaluation over 47 splits. The attempted run’s
observed throughput projects 7 to 92 wall-clock hours per variant,
competing within the paper’s 24-hour allocation. Model-construction
parameter counts are available before training finishes, whereas
accuracy measurements require completed training and evaluation. The
session reaches the former but not the latter. Across models, 13 of
LiME’s 14 reversals are resource/access failures and one is a numerical
mismatch.

##### Interpreting residual numerical mismatches.

The 84 numerical reversals span several possible mechanisms: stochastic
training, timing conditions, changed execution choices, and unresolved
paper–code disagreements. Construction may also introduce an incorrect
setting, metric interpretation, or repair that later agents inherit.
Diagnosing a particular reversal requires tracing its executed
configuration and measurement procedure. The Manifold-Aware
Perturbations guide, for example, flags a learning-rate discrepancy
between the paper and released code for further inspection (Appendix
[D.5](#A4.SS5 "D.5 Worked reproduction examples ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts")).

### D.5 Worked reproduction examples

These examples expand the paired-run case evidence in Section
[4.4](#S4.SS4 "4.4 Preserved procedures support recovery and reduce reconstruction ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
retaining exact configurations, task identifiers, and measurements. They
illustrate information preserved in the refined artifact and
corresponding recorded outcomes.

##### Recovering omitted configuration: HELIX.

For HELIX ([Zhang et al., 2026a](#bib.bib32)), Opus 5 restores the
paper’s architecture on raw code but retains a shipped batch size of 32
and learning rate of approximately $`6.29\times 10^{-4}`$. The guide’s
ambiguity entry A6 identifies revision 9760b347, whose architecture
matches the paper configuration, as the source for batch size 8 and
learning rate $`5.75\times 10^{-4}`$. The --paper_config launcher makes
this choice executable. The recorded MAE changes from 0.15265 to 0.12986
for T004 and from 0.50527 to 0.41160 for T006; the respective
compatibility intervals are \[0.12524, 0.13448\] and \[0.38442,
0.43878\]. The artifact records the repository history and architectural
match as the rationale for adopting these settings.

##### An environment route that transfers: WBMM.

For six COCO tasks (T063–T068) in WBMM ([Song et al.,
2026](#bib.bib61)), Sonnet 4.6’s raw attempt fails to install a
compatible mmcv-full stack for H100. The refined artifact specifies
matching PyTorch/MMDetection dependencies, the Ninja build prerequisite,
and a source build for the target architecture. The downstream
refined-artifact session makes no code patch and executes all six tasks.
Its two box AP values, 51.61 and 52.78, agree numerically with reported
targets 51.6 and 52.8; mask AP is 44.78/45.64 against 44.8/45.6. The
artifact preserves an executable dependency route for later reuse.

##### Fixing validation labels: Effective Model Pruning.

The released TinyImageNet loader uses ImageFolder on a validation
directory containing only an images subdirectory. It therefore assigns
all 10,000 validation images to one class. During construction,
ReproBridge adds a preparation script that places images into class
directories using val_annotations.txt, verifies 200 classes and 10,000
images, and writes a preparation receipt required by the launcher. In
Gemini 3.8 Flash’s paired runs, the ResNet-18 validation loss is 8.898
with raw code and 2.288 with the refined artifact, against the paper’s
2.303. This records a concrete repair and its downstream reuse.

##### Organizing measurement code for reuse: ETTFS.

The raw Opus 5 attempt searches the released ETTFS ([Che et al.,
2026](#bib.bib45)) source for the metrics in Tables 2 and 3, finds no
producing implementation, and leaves the inference-time measurement
unexecuted. During construction, ReproBridge adds Code/profile_ttfs.py,
documents the metric definitions and output fields, and supplies a
launcher that trains a checkpoint before profiling it. The later Opus 5
session uses this explicit route and reports 2.0652 inference time steps
against the paper’s 2.03. The artifact localizes code and resolved
decisions that would otherwise require renewed investigation.

##### A measurement is not just a model execution: Mixture of Concept Bottleneck Experts.

For four-expert settings in Mixture of Concept Bottleneck Experts ([De
Santis et al., 2026](#bib.bib51)), the paper does not specify how
multiple expression distances should be reduced, and the repository
provides no Table 1 collector. The raw Sonnet 5 attempt constructs a
matching between learned and reference expressions but reports the sum
of tree-edit distances. For two tasks this produces 60 and 188, whereas
the per-expression means are 15 and 47. The refined artifact resolves
the ambiguity by documenting the denominator and implementing the
corresponding collector; those downstream values are 15 and 47. The case
locates the discrepancy in the underspecified reporting statistic.

##### Preserving the experimental aggregation: SCIQL.

The released SCIQL ([Petitbois et al., 2026](#bib.bib27)) code produces
run outputs but does not assemble the Table 1 statistic, leaving the
mapping from logged fields and experiment settings to reported values
incomplete. The raw Sonnet 4.6 attempt uses one default criterion, one
seed, and an incorrect output column for a table statistic that averages
across six criteria and five seeds. The refined artifact’s launcher and
collector make this mapping explicit by specifying the sweep and the
correct alignment field. One representative measurement changes from
19.70 to 55.66 against a paper value of 58.6. Criterion selection,
output mapping, and repetition change together in this case,
illustrating preservation of the complete measurement protocol.

##### An optimizer release is not a complete experiment: FlashOptim.

FlashOptim ([Gonzalez Ortiz et al., 2026](#bib.bib38)) supplies
optimizer code but not the GPT-2 training and evaluation harness for the
selected table. Gemini’s raw attempt leaves 18 GPT-2 outcomes
unexecuted. The refined artifact adds a training/evaluation harness,
data acquisition, output mapping, and launchers; all 18 pass in its
recorded downstream attempt. The construction report lists 6,346 added
lines of experiment support.

##### A localized repair: POET-X.

The defect occurs in examples/peft_pretraining/training_utils.py, line
222. Full batches call collate_fn, whereas the trailing partial batch is
returned as a list. The evaluator calls batch.items(), so it fails when
the final batch is reached. The patch changes the tail to yield
collate_fn(batch). The record traces the sole caller to validation and
describes CPU checks covering empty, partial, complete, and over-full
batch counts, without changing the example count. This example
illustrates how a later reproducer can recover both the fix and its
experimental scope.

##### Flagging a setup discrepancy: Manifold-Aware Perturbations.

The guide’s ambiguity entry A1 contrasts the paper’s stated learning
rate of $`10^{-4}`$ with the released driver, training scripts, and 171
committed manifests using $`10^{-3}`$, and marks the discrepancy as high
sensitivity. This gives authors a concrete inconsistency to inspect and
resolve before submission.

### D.6 Separate alignment analysis

A separate static audit compares selected paper results with their raw
implementations. It distinguishes implemented behavior that contradicts
the paper from absent implementations and details on which the paper is
silent. Among 293 recorded findings, 238 are in scope for contradiction
analysis and touch 669 distinct tasks. High-severity labels occur on 73
findings touching 482 tasks; 25 papers have at least one such finding.
Task counts are deduplicated; a task may have multiple severity labels.

Agents produced these findings through static inspection of papers,
code, and committed evidence. The analysis is separate from primary
success scoring and covers the selected evaluation tasks. The evidence
includes the learning-rate case above and a diffusion-objective case in
which the code squares a norm described as an unsquared distance,
changing its gradient. These cases illustrate that numerical
compatibility and code execution can coexist with a paper–implementation
discrepancy.

##### From an apparent gap to a localized finding.

The audit first extracts the paper-side requirement independently of the
code-side inspection. It then identifies the implementation in that
role, such as the function computing the loss or selecting the
evaluation population. A contradiction requires an explicit paper
statement and conflicting implemented behavior, with source locations
and affected task IDs. If no implementation occupies the role, the
finding is a missing implementation; if the paper specifies no relevant
choice, it is underspecification rather than a contradiction. This
separates 44 absent-implementation records and 11 paper-silent records
from the 238 in-scope findings.

##### What these discrepancies mean.

A learning-rate disagreement is concrete even without retraining: one
can point to the paper’s $`10^{-4}`$ and the code’s $`10^{-3}`$. But the
resulting change in final accuracy cannot be inferred from that factor
alone. Similarly, replacing a distance by its square changes the
objective and gradient weighting; its empirical impact requires a
controlled comparison. The workflow records the contradiction and its
scope while following the paper’s specified setup. These records can
guide authors’ reproducibility checks before submission. In the terms of
Section
[2.1](#S2.SS1 "2.1 Execution deviations and reference variation ‣ 2 Problem formulation and ReproBridge-Bench ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
the discrepancies are possible sources of $`D`$, not estimates of its
magnitude.

Severity is also an agent judgment. The record set assigns 73 findings a
high label, of which 63 use an argued magnitude-based route and 10
concern inability to instantiate the stated setup. These labels help
prioritize inspection. The alignment records were not supplied to the
evaluated Reproducers.

### E.1 Construction investment and reuse

Constructing the 36 artifacts costs \$5,026 in API usage, averaging
\$139.61 per paper.

##### Sources of construction effort.

The workflow provides a qualitative explanation of API expenditure.
Specification requires reading the paper and code to resolve experiment
settings and measurement rules. Execution support requires environment
repair, missing implementation, and diagnosis through successive runs;
each revision can require further code and log inspection. Review and
packaging then check the evidence and preserve the resulting procedures.
The WBMM dependency route and HELIX configuration recovery in Section
[4.4](#S4.SS4 "4.4 Preserved procedures support recovery and reduce reconstruction ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
together with the FlashOptim training/evaluation harness in Appendix
[D.5](#A4.SS5 "D.5 Worked reproduction examples ‣ Appendix D Extended results and case evidence ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
illustrate these kinds of work. GPU runtime is a separate expense: it
affects API spending through associated model calls for setup,
inspection, and debugging, not through elapsed GPU time itself.

##### Model-specific reuse.

For downstream model $`m`$ in {Sonnet 4.6, Sonnet 5, Opus 5}, let
$`c_{m}^{\mathrm{raw}}`$ and $`c_{m}^{\mathrm{refined}}`$ be the mean
paired aggregate API costs in Table
[3](#S4.T3 "Table 3 ‣ 4.2 Refined artifacts improve success and reduce downstream cost ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts"),
and let $`C_{\mathrm{build}}=\$5{,}026`$ be the full construction
expense. One reuse round repeats the 36-paper workload represented by
those costs. With stationary per-round spending, raw reuse costs
$`nc_{m}^{\mathrm{raw}}`$, while refined-artifact reuse costs
$`C_{\mathrm{build}}+nc_{m}^{\mathrm{refined}}`$. The API break-even
count is

|  |  |  |
|----|----|----|
|  |
``` math
n_{m}^{*}=\left\lceil\frac{C_{\mathrm{build}}}{c_{m}^{\mathrm{raw}}-c_{m}^{\mathrm{refined}}}\right\rceil\quad\text{when }c_{m}^{\mathrm{raw}}>c_{m}^{\mathrm{refined}}.
``` |  |

Each model-specific scenario bears the full construction cost. For
positive construction cost and nonpositive savings, there is no finite
API crossover.

For example, Sonnet 5 costs a mean of \$1,726 per raw round and \$1,317
per refined-artifact round. The difference is \$409; \$5,026 divided by
this saving is 12.29 rounds, hence 13 complete rounds to break even. The
corresponding continuous crossover points are 7.70 rounds for Sonnet 4.6
and 8.17 for Opus 5, giving the 8 and 9 complete rounds reported in
Section
[4.7](#S4.SS7 "4.7 Repeated reuse can offset construction API cost ‣ 4 Experiments ‣ ReproBridge: Building Reproducibility into ML Research Artifacts").

These scenarios repeat the complete 36-paper workload at fixed prices,
caching, artifact contents, and agent behavior. Costs and savings are
aggregated over paper sessions, including shared executions that produce
multiple task scores. The crossover accounts for construction and
downstream Reproducer API spending; independent auditing, GPU execution,
maintenance, and unrecorded cache-storage fees are excluded. Human
reference collection is a separate benchmark-development cost.
