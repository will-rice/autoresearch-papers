# EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution

Kaipeng Xu¹, Xianli Yan¹, Yan Wang^(1,\*), Xiang Liu¹, Shan Liu²
Affiliation: \[

###### Abstract.

Deep time-series forecasting models have rapidly diversified, yet
adapting them to a specific task still requires extensive expert effort
in model selection, mechanism diagnosis, architecture design,
implementation, and evaluation. Existing AutoML methods are constrained
by predefined search spaces, while general-purpose LLM research agents
lack reliable control over experimental protocols and model promotion.
We introduce EvoCast, a fully autonomous research-agent system for
iterative forecasting architecture evolution. EvoCast first establishes
and diagnoses a task-specific baseline through executed mechanism
ablations, then generates evidence-grounded research directions from
dataset characteristics, diagnostic results, prior rounds, and failure
records. Its central design, cognition-authority separation, assigns
open-ended hypothesis generation and code implementation to LLM agents,
while deterministic program authorities control source-edit boundaries,
canonical evaluation, and promotion decisions. Experimental outcomes are
accumulated as evidence to guide subsequent rounds. Results show that
EvoCast completes complex architecture modifications with higher
implementation success and lower agent-side token/time cost, and
develops task-specific architectures that outperform selected baselines,
strong forecasting models, and agent baselines in three real-world
forecasting cases. The code is available at
[https://github.com/18e0-x/EvoCast](https://github.com/18e0-x/EvoCast).

## 1. Introduction

Deep time-series forecasting supports decision making in energy systems,
transportation systems, industrial monitoring, and many other dynamic
environments ([Lim and Zohren, 2021](#bib.bib6)). Recent forecasting
architectures have rapidly diversified across decomposition-based
modeling, frequency-domain modeling, patch tokenization, and
variable-centric modeling, forming a heterogeneous and fast-evolving
model ecosystem ([Wu et al., 2021](#bib.bib7); [Zhou et al.,
2022b](#bib.bib8); [Nie et al., 2023](#bib.bib9); [Liu et al.,
2024](#bib.bib10)). Real forecasting tasks also differ substantially in
periodicity, distribution drift, variable interaction, horizon length,
and noise characteristics, so a single general-purpose architecture
rarely dominates across all settings ([Qiu et al., 2024](#bib.bib1)).
Developing a suitable forecasting architecture for a specific task
therefore still requires extensive expert effort, including baseline
selection, mechanism diagnosis, architecture modification, source-code
integration, and controlled evaluation. A practical autonomous research
system must perform these steps under a fixed evaluation protocol so
that baselines, candidates, and research rounds remain comparable.

Existing automation methods cover model search, configuration, code
refinement, and experiment feedback. Reliable forecasting architecture
development additionally requires cross-file information-flow
restructuring, task-specific mechanism insertion, fixed-protocol
evaluation, and comparable model promotion. These requirements define
the setting for EvoCast and distinguish it from existing automated
architecture and agentic research systems.

Autonomous forecasting architecture research requires flexible research
generation under deterministic experimental control. LLM agents are
useful for interpreting heterogeneous forecasting code, identifying
candidate mechanisms, and implementing nontrivial architectural edits
([Huang et al., 2024a](#bib.bib19)). Program-controlled experimental
rules must fix the dataset, split, metric, training policy, editable
source boundary, and promotion rule throughout a run. This requirement
builds on the need for fair, consistent, and comparable evaluation
emphasized by forecasting benchmarks and NAS evaluation practice ([Qiu
et al., 2024](#bib.bib1); [Lindauer and Hutter, 2020](#bib.bib13)). When
research generation, code execution, and result adjudication are handled
inside the same open-ended agent, failure interpretation, evaluation
assumptions, and promotion decisions can contaminate later rounds and
waste token and wall-clock budgets ([Huang et al., 2024a](#bib.bib19);
[Xu et al., 2026](#bib.bib25)). Unified evaluation infrastructures such
as TFB make auditable architecture evolution possible by fixing task
definition, evaluation protocol, and model comparison under a common
benchmark surface ([Qiu et al., 2024](#bib.bib1)).

This paper presents EvoCast, a fully autonomous research-agent system
for task-specific forecasting architecture evolution. Starting from a
forecasting task specification, EvoCast organizes one autonomous run as
a fixed-protocol research loop: it establishes a task-specific baseline,
diagnoses that baseline through executed mechanism ablations, generates
evidence-grounded research directions from dataset characteristics,
diagnostic evidence, prior rounds, and failure memory, and implements,
evaluates, and promotes candidate architectures under the same protocol.
Its central design is cognition-authority separation: LLM agents handle
open-ended hypothesis generation, source implementation, and report
narration, while deterministic program authorities control source
validity, canonical evaluation, metric comparison, model promotion, and
state updates. Successful improvements, scientific negative results, and
engineering failures are written into the evidence state, reducing
repeated trial-and-error and grounding later rounds in auditable facts.

We evaluate EvoCast through three research questions. RQ1 studies
implementation reliability and efficiency, asking whether EvoCast can
translate forecasting architecture ideas into executable, semantically
correct, and protocol-compliant code with higher success and lower
agent-side token/time cost. RQ2 studies end-to-end forecasting utility,
asking whether EvoCast can develop task-specific architectures that
outperform selected baselines, strong forecasting models, and agent
baselines in three real-world forecasting cases. RQ3 studies
orchestration and authority design, asking which parts of
cognition-authority separation are necessary for reliable autonomous
architecture research.

Our main contributions can be summarized as follows:

- •
  We formulate autonomous forecasting architecture evolution as a
  fixed-protocol research loop that spans baseline establishment,
  mechanism diagnosis, bounded implementation, canonical evaluation,
  promotion, and evidence update in heterogeneous forecasting
  repositories.
- •
  We introduce cognition-authority separation for reliable autonomous
  research. This design assigns hypothesis generation and source
  implementation to LLM agents, and deterministic authorities control
  source validity, runtime evaluation, model promotion, and state
  updates.
- •
  We build an evidence-grounded execution framework that turns research
  directions into provenance-tracked source candidates, uses repair and
  failure memory to reduce ineffective iteration, and accumulates
  scientific and engineering evidence across rounds.
- •
  We evaluate EvoCast on repository-level implementation and end-to-end
  forecasting research tasks, showing stronger implementation
  reliability, lower token and time cost, and task-specific architecture
  improvements under controlled budgets.

## 2. Related Work

#### Automated Forecasting Architecture Development.

Deep forecasting architectures encode different assumptions about
temporal structure, variable interaction, and information flow ([Wu et
al., 2021](#bib.bib7); [Zhou et al., 2022b](#bib.bib8); [Nie et al.,
2023](#bib.bib9); [Liu et al., 2024](#bib.bib10)). TFB shows that their
behavior is strongly dataset dependent under a common evaluation
protocol ([Qiu et al., 2024](#bib.bib1)). AutoML, hyperparameter
optimization, and neural architecture search automate model selection
and configuration within specified templates or operator spaces ([He et
al., 2021](#bib.bib11); [Elsken et al., 2019](#bib.bib12)). Recent
LLM-assisted approaches extend this process through multi-agent
architecture design, bounded task-specific search, and generated
architectures with runtime repair ([Yang et al., 2024b](#bib.bib26);
[Jeong et al., 2026](#bib.bib27); [Poikarayil et al.,
2026](#bib.bib28)). EvoCast evolves executable source modules from an
established task-specific repository baseline, using executed mechanism
diagnosis to select bounded architecture changes under a canonical
evaluator.

#### LLMs and Agentic Systems for Time Series.

Language models support forecasting, temporal reasoning, and multimodal
time-series modeling ([Jin et al., 2024](#bib.bib14); [Liu et al.,
2025a](#bib.bib15); [Zhong et al., 2025](#bib.bib16); [Liu et al.,
2025c](#bib.bib29); [Das et al., 2026](#bib.bib30)). TimeSeriesScientist
automates data understanding, planning, validation, and reporting, while
SEA-TS and GenAutoML develop forecasting code or task-specific
architectures through iterative feedback ([Zhao et al.,
2025](#bib.bib24); [Xu et al., 2026](#bib.bib25); [Poikarayil et al.,
2026](#bib.bib28)). EvoCast combines an executable task baseline,
executed baseline ablations, persistent evidence state, and
deterministic promotion authority, so each subsequent architecture
direction is grounded in formal evidence from the same protocol.

#### Autonomous Research Agents and Controlled Experimentation.

Autonomous research agents connect research proposals, code editing, and
experimental feedback into iterative workflows. MLAgentBench provides
standardized machine-learning experimentation environments, AIDE
explores candidates through code-space search, R&D-Agent coordinates
research and development roles, and AutoResearch verifies candidates
through execution feedback ([Huang et al., 2024a](#bib.bib19); [Jiang et
al., 2025](#bib.bib20); [Yang et al., 2025](#bib.bib22); [Kumar et al.,
2026](#bib.bib23)). MLE-STAR further uses executed ablations to locate
high-impact code regions for targeted refinement ([Nam et al.,
2025](#bib.bib31)).

For long-horizon research, ResearchLoop, AIRA², FML-bench, ResearchGym,
and Arbor emphasize task contracts, consistent evaluation, execution
infrastructure, and cross-round evidence management ([Xia and Wang,
2026](#bib.bib35); [Hambardzumyan et al., 2026](#bib.bib36); [Zou et
al., 2026](#bib.bib37); [Garikaparthi et al., 2026](#bib.bib38); [Jin et
al., 2026](#bib.bib39)). EvoCast applies these principles to
task-specific forecasting architecture evolution: starting from an
executable repository baseline, live-path mechanism diagnosis and
cross-round evidence guide bounded source changes, while deterministic
programs control boundary validation, canonical evaluation, model
promotion, and evidence write-back. This design connects
research-direction generation with experimental adjudication through
explicit role separation, keeping architecture changes and subsequent
evidence accumulation under one fixed protocol.

### 3.1. Task Setting

EvoCast organizes autonomous forecasting architecture development under
a fixed task protocol. For one target task, the system first freezes

|     |     |     |
| --- | --- | --- |
|     |

       ``` math
       \mathcal{P}=(\mathcal{D},y,L,H,\mathrm{mode},m,B),
       ```                                                 |     |

where $`\mathcal{D}`$ is the dataset, $`y`$ is the prediction target,
$`L`$ is the lookback length, $`H`$ is the forecasting horizon,
$`\mathrm{mode}`$ is the forecasting mode, $`m(\cdot)`$ is the formal
evaluation metric, and $`B`$ is the research budget. This protocol
remains unchanged throughout one autonomous run and is reused by
baseline selection, diagnosis ablations, formal research candidates, and
final promotion checks.

This formulation defines EvoCast as a repository-level research problem
under one stable comparison surface. The system must operate on real
heterogeneous forecasting repositories, produce executable architecture
modifications, and return a validated current-best architecture together
with the executed research evidence that supports it.

### 3.2. Research State and Round Outcome

EvoCast organizes one autonomous run as a stateful multi-round research
process. At round $`r`$, the system maintains

|     |     |     |
| --- | --- | --- |
|     |

       ``` math
       \mathcal{S}_{r}=(M_{r},E_{r},\mathcal{H}_{r}),
       ```                                             |     |

where $`M_{r}`$ is the current incumbent model, $`E_{r}`$ is the
evidence bundle used for planning, and $`\mathcal{H}_{r}`$ is the round
history. The evidence bundle aggregates task evidence,
baseline-diagnosis evidence, accepted results, valid negatives, unstable
gains, repair records, and failure memory. The round history preserves
the executed research trajectory for later planning and state update.

Each formal research round returns an outcome

|     |     |     |
| --- | --- | --- |
|     |

````math
o_{r}\in\{\mathrm{accepted},\mathrm{rejected},\mathrm{unstable},\mathrm{failed}\}.
``` |  |

An accepted round passes boundary validation, produces valid canonical
metrics, and satisfies the fixed multi-seed promotion rule against the
incumbent. A rejected round produces valid canonical metrics but does
not improve over the incumbent. An unstable round improves in a single
run but does not satisfy the seed-stability requirement for promotion. A
failed round does not produce a valid formal result because source
construction or canonical execution fails. These outcomes give EvoCast a
unified state-update interface in which every round contributes
auditable evidence.

## 4. Method

### 4.1. Overview of the EvoCast Research Loop

EvoCast organizes task-specific forecasting architecture development as
a fixed-protocol autonomous research loop. Given a task card, a
forecasting repository, and a bounded research budget, the system
follows the five stages in
Figure [2](#acmlabel2 "Figure 2 ‣ 3. Preliminaries ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution"):
task grounding, baseline establishment, baseline diagnosis, formal
iterative research, and final reporting. The loop is driven by the
frozen task protocol $`\mathcal{P}`$ and the evolving research state
$`\mathcal{S}_{r}`$.

At round $`r`$, EvoCast reads $`\mathcal{S}_{r}`$, generates one
research direction, executes one bounded candidate, and writes the
validated outcome into $`\mathcal{S}_{r+1}`$. The equations and
algorithm below define this transition.

### 4.2. Task Grounding and Baseline Establishment

Task grounding turns the task card into a stable research starting
point. EvoCast reads the dataset, target, lookback, horizon, forecasting
mode, and evaluation metric, freezes them as $`\mathcal{P}`$, and writes
them into the grounded task package. The characteristics extractor then
computes dataset characterization features and adds them to the task
evidence, so later planning is conditioned on executed task structure.

Baseline establishment defines the single formal comparison anchor for
the entire run. Let $`\mathcal{B}_{\mathrm{exec}}`$ denote the set of
baseline models that execute successfully under protocol
$`\mathcal{P}`$. EvoCast selects

|  |  |  |
|----|----|----|
|  |
``` math
b^{\star}=\arg\min_{b\in\mathcal{B}_{\mathrm{exec}}}m(b;\mathcal{P}),
``` |  |

where the metric direction follows the formal evaluation setting. In the
experiments of this paper, lower error indicates a stronger model. The
selected single baseline anchors all later candidate comparisons and
also serves as the execution starting point for mechanism diagnosis.
Under this design, the canonical evaluator reuses the same dataset
split, metric, training policy, and evaluation path for baselines,
ablations, and promoted candidates, thereby fixing one comparison
surface throughout the run.

### 4.3. Baseline Diagnosis for Mechanism Evidence

The selected baseline identifies which executable model is currently
strongest, and baseline diagnosis identifies why that model works on the
current task. EvoCast analyzes the active prediction path of
$`b^{\star}`$, extracts ablatable mechanisms, and turns them into
executable diagnosis targets tied to concrete source regions and
input-output preservation contracts.

Let $`\mathcal{A}(b^{\star})`$ denote the mechanism set extracted from
the active path of the selected baseline. For each diagnosis target
$`a\in\mathcal{A}(b^{\star})`$, EvoCast executes the ablation under the
same protocol and records

|     |                                                      |     |
|-----|------------------------------------------------------|-----|
|     |
       ``` math
       \Delta(a)=m(a;\mathcal{P})-m(b^{\star};\mathcal{P}).
       ```                                                   |     |

Ablation outcomes provide mechanism-level evidence for later planning.
Clear degradation after removal supports preserving the mechanism’s core
function; improvement suggests redundancy or task mismatch and
identifies a replacement or restructuring target; a small change marks a
weak or unresolved mechanism. Build, runtime, and protocol failures
record implementation risks, while mechanism judgments rely on ablations
with valid formal metrics. Diagnosis thus identifies functions to
preserve, mechanisms to explore, and implementation risks to avoid.

### 4.4. Formal Iterative Research with Cognition-Authority Separation

Formal iterative research is the largest closed-loop region in
Figure [2](#acmlabel2 "Figure 2 ‣ 3. Preliminaries ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution").
At the start of round $`r`$, the Research Planner reads the frozen task
protocol and the current research state, then produces one research
direction

|     |                                         |     |
|-----|-----------------------------------------|-----|
|     |
       ``` math
       d_{r}=\Pi(\mathcal{P},\mathcal{S}_{r}),
       ```                                      |     |

where $`\Pi(\cdot)`$ denotes the planner policy. The planner uses
different evidence sources for different decisions. Task evidence
describes periodicity, trends, variable scale, and horizon requirements;
the current model and its active source path establish the executable
starting point; diagnostic ablations, accepted results, valid negatives,
and unstable gains update mechanism judgments; import, shape, runtime,
and boundary failures identify implementation risks. The planner first
identifies unresolved architectural needs, then generates multiple
standalone module-level hypotheses. It compares their evidence
grounding, information-flow changes, redundancy with prior directions,
and implementation feasibility before selecting one direction for
execution.

The selected direction $`d_{r}`$ specifies the target mechanism, source
insertion point, testable hypothesis, expected information-flow change,
failure to avoid, and expected knowledge gain. The hypothesis links task
needs to the architecture modification, while expected knowledge gain
states which mechanism explanation the outcome would support or weaken
and how it would inform later direction selection. Historical rounds
supply evidence for this judgment, and implementation starts from the
active source state. Each round executes one direction, tying its
outcome to a specific research hypothesis.

The builder then compiles $`d_{r}`$ into a bounded implementation task.
This task fixes the active source snapshot, editable boundary, task
protocol, and repair budget. It allows new-module insertion,
information-flow rerouting, and local path restructuring inside the
allowed source region, while keeping the task semantics, training
policy, evaluation interface, and public model contract unchanged. The
builder edits only the allowed model-side source region, while the
dataset path, evaluator, metric computation, training budget, and
promotion logic remain frozen in the authority-controlled execution
path.

### 4.5. Validated Outputs and Evidence-Carrying State Update

After direction selection, candidate execution follows the two-step
form:

|  |  |  |
|----|----|----|
|  |
``` math
\quad c_{r}=\beta(d_{r},\mathcal{P},M_{r}),\qquad o_{r}=\Gamma(\mathcal{P},\mathcal{S}_{r},c_{r}),
``` |  |

where $`\beta(\cdot)`$ denotes bounded candidate construction under the
fixed protocol and editable source region, and $`\Gamma(\cdot)`$ denotes
authority-controlled execution. This chain performs source-boundary
validation, canonical training and evaluation, metric comparison, and
promotion adjudication. Only candidates that pass boundary validation,
produce valid formal metrics, and satisfy the fixed comparison rule can
enter the accepted state. Model-state promotion is triggered only when
the candidate passes boundary validation, produces valid canonical
metrics, and satisfies the fixed multi-seed comparison rule against the
current incumbent.

The incumbent model is then updated by

|  |  |  |
|----|----|----|
|  |
``` math
M_{r+1}=\left\{\begin{array}[]{ll}c_{r},&\mbox{if }o_{r}=\mathrm{accepted},\\
M_{r},&\mbox{otherwise}.\end{array}\right.
``` |  |

and the next research state is written as

|     |                                                   |     |
|-----|---------------------------------------------------|-----|
|     |
       ``` math
       \mathcal{S}_{r+1}=U(\mathcal{S}_{r},c_{r},o_{r}).
       ```                                                |     |

The update $`U(\cdot)`$ writes model state, mechanism evidence, and
engineering memory according to the outcome. An accepted candidate
becomes the incumbent, with its supporting formal metrics and gate
decision recorded. A rejected candidate leaves the incumbent unchanged
and records an executed hypothesis that did not improve the metric as a
valid negative. An unstable candidate preserves the incumbent and
records both the single-run gain and the failed stability gate. A failed
candidate preserves the incumbent and records the failure stage, cause,
and repair trace. Valid negatives adjust mechanism judgments, unstable
gains indicate evidence strength, and engineering failures identify
implementation risks.

The next round rereads these records alongside the current model to
assess supported explanations, weakened directions, and unresolved
needs. Model state changes only after promotion, while evidence state
accumulates valid improvements, negatives, unstable gains, and failure
records, allowing subsequent planning to use the full research
trajectory.

When the research budget is exhausted or the termination condition is
met, EvoCast freezes the final incumbent, formal metrics, accepted
rounds, valid negatives, gate decisions, and failure records. The Report
Narrative Agent reads only these frozen facts and generates the final
HTML report. The output bundle therefore contains the validated
current-best model, reproducible source and configuration, resource
usage, and a human-auditable final narrative.

### 5.1. Research Questions

We organize the evaluation around three research questions.

- •
  RQ1: Implementation Reliability. Can EvoCast faithfully translate
  forecasting architecture ideas into executable, semantically correct,
  and protocol-compliant implementations across heterogeneous
  forecasting repositories?
- •
  RQ2: End-to-End Research Utility. Can EvoCast autonomously discover
  task-specific architectures that improve over strong forecasting and
  research-agent baselines under controlled budgets?
- •
  RQ3: Orchestration and Authority Design. Which parts of
  cognition-authority separation are necessary for reliable autonomous
  architecture research?

### 5.2. Experimental Setup

All experiments are conducted on the unified benchmark infrastructure
provided by TFB. Baseline, ablation, and candidate evaluation reuse the

### 5.3. RQ1: Implementation Reliability

RQ1 evaluates whether a method can reliably realize a given forecasting
architecture idea as executable code. We construct a controlled
idea-to-code benchmark with 30 tasks from 10 forecasting backbones and
three predefined idea-complexity levels: local modification,
cross-module integration, and novel module insertion. All methods
receive the same repository snapshot, idea text, and editable boundary.
The compared methods are Direct Independent Edit, mini-SWE-agent ([Yang
et al., 2024a](#bib.bib21)), AIDE ([Jiang et al., 2025](#bib.bib20)),
R&D-Agent ([Yang et al., 2025](#bib.bib22)), and AutoResearch ([Kumar et
al., 2026](#bib.bib23)). This setup directly compares their ability to
implement the same architecture idea in real heterogeneous forecasting
repositories.

The three complexity levels operationalize distinct implementation
capabilities. Local modification requires a precise edit inside an
existing deep-learning module, such as replacing an activation function
or inserting a lightweight channel mixer. Cross-module integration
requires understanding multiple source regions and establishing a new
executable connection, such as adaptive fusion between a decomposition
module and a forecasting head. Novel module insertion requires the new
mechanism to participate in the live forecasting path or to reorganize
that path. This stratification makes success rate reflect local coding
precision, cross-file interface matching, and main-path restructuring
ability.

Table [1](#S5.T1 "Table 1 ‣ 5. Experiments ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution")
reports the overall results. EvoCast achieves the highest success rate
while maintaining perfect fidelity and the strongest repair performance,
and it is also more time- and cost-efficient than the other agent
baselines. Direct Independent Edit is the cheapest method, but it also
has the lowest success rate; the remaining agent baselines outperform
direct editing but still fall clearly behind EvoCast. These results show
that EvoCast improves success rate, efficiency, and stability together
when implementing complex deep-learning architecture changes. As tasks
move from local edits to cross-module integration and novel module
insertion, cognition-authority separation more reliably turns research
intent into valid implementations.

reports the complexity-level and backbone-level analysis.

### 5.5. RQ3: Orchestration and Authority Design

RQ3 evaluates how EvoCast’s system design supports the final outcome. We
perform controlled system ablations over the fixed EvoCast workflow, and
each variant removes or weakens one key mechanism. The comparison tracks
both final forecasting quality and agent-side cost, so this section
measures the role of the full research loop.

A1 removes dataset characterization, A2 removes baseline diagnosis, A3
removes evidence-grounded planning, A4 removes authority-controlled
execution, and A5 removes iterative evidence update. These variants
isolate how task evidence, mechanism diagnosis, planning quality,
execution control, and cross-round memory affect the stability of the
autonomous research loop.

All variants use Melbourne Pedestrian T33 with PatchMLP as the starting
backbone, lookback 168, horizon 24, and MSE as the optimization metric.
The formal research cap is 20 rounds, with at most three repair attempts
per round. Each variant removes its designated mechanism while
preserving the remaining workflow.

Table [5](#S5.T5 "Table 5 ‣ 5.4. RQ2: End-to-End Research Utility ‣ 5. Experiments ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution")
shows that the full loop achieves the lowest final MSE while maintaining
controlled resource use. A1 and A2 weaken direction quality; A3
maintains continuous execution but selects weaker directions; A4
simultaneously yields the weakest final quality and the highest resource
cost; and A5 loses later-round accumulation without iterative evidence
write-back. Each ablation therefore degrades forecasting quality,
research stability, or budget efficiency.

## 6. Conclusion

EvoCast turns forecasting architecture development into an autonomous
process that can establish a task-specific starting point, accumulate
executable research evidence across rounds, and deliver a final
forecasting architecture tailored to the target scenario. Along this
workflow, the system establishes a task-specific baseline, constructs
mechanism evidence, advances live-path architecture evolution, and
ultimately develops a forecasting model suited to the current scenario.
Each accepted architecture change is tied to executable source code,
canonical evaluation, and a traceable state update, so the final result
is both reusable and practically deployable.

The main value of this work is that it advances autonomous time-series
modeling toward task-specific model development. For forecasting
research, this means that one fixed workflow can develop suitable
time-series models for different real-world scenarios. More broadly, it
shows that the central value of autonomous scientific coding systems
lies in producing executable, auditable, and scenario-adaptive research
artifacts around concrete tasks.

## Appendix A Extended Related Work

### A.1. Deep Time-Series Forecasting Architectures

Deep time-series forecasting has developed into a heterogeneous
architecture ecosystem. Representative families cover decomposition and
frequency modeling, patch-level temporal representation, cross-variate
dependency modeling, linear modeling, dense encoding, and time-frequency
hybrid modeling ([Wu et al., 2021](#bib.bib7); [Zhou et al.,
2022b](#bib.bib8); [Nie et al., 2023](#bib.bib9); [Zhang and Yan,
2023](#bib.bib45); [Liu et al., 2024](#bib.bib10); [Zeng et al.,
2023](#bib.bib40); [Das et al., 2023](#bib.bib84); [Wu et al.,
2023](#bib.bib65)). These architecture families encode different
assumptions about temporal structure, variable interaction, and
information flow. TSLib systematizes this ecosystem as a reusable
benchmark library for deep time-series models across forecasting,
imputation, anomaly detection, and classification ([Wang et al.,
2024b](#bib.bib5)).

This architectural diversity creates a direct need for task-specific
development. TFB further provides a controlled and fair evaluation
protocol for forecasting and shows that forecasting architectures
exhibit strongly dataset-dependent behavior ([Qiu et al.,
2024](#bib.bib1)). These observations make baseline selection,
controlled comparison, and architecture modification central parts of
forecasting research. EvoCast builds on this setting and organizes
baseline establishment, baseline diagnosis, and architecture evolution
within one fixed-protocol research loop.

### A.2. Automated Forecasting Model and Architecture Development

Automated model development has been studied extensively through AutoML,
hyperparameter optimization, and neural architecture search. AutoML and
hyperparameter optimization automate model selection and configuration,
while NAS explores candidate structures inside predefined operator
spaces or architecture templates ([He et al., 2021](#bib.bib11); [Elsken
et al., 2019](#bib.bib12)). These methods provide strong automation
within explicit search spaces.

Recent LLM-assisted architecture design extends automation from fixed
search spaces to dynamic structure construction. NADER organizes
architecture design as a multi-agent process, AgentNAS generates a seed
architecture and then constructs a bounded task-specific search space
around it, and GenAutoML generates task-specific forecasting
architectures together with runtime checks and self-repair ([Yang et

## Appendix B System and Implementation Details

This section expands the fixed-protocol autonomous architecture
development loop described in
Section [4](#S4 "4. Method ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution").
Given a forecasting task, a model repository, and a bounded research
budget, EvoCast fixes the task protocol, establishes a comparable
baseline, converts the baseline into executed mechanism evidence, runs
bounded architecture research rounds, updates the research state through
program authorities, and generates a final HTML report from frozen
facts.

The goal of this section is to explain the execution semantics behind
Section [4](#S4 "4. Method ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution").
Cognitive agents generate ablation targets, research directions,
candidate source states, and final narrative. Program authorities
control source boundaries, canonical evaluation, promotion decisions,
result semantics, and state write-back. This division keeps open-ended
architecture exploration inside a fixed comparison surface.

### B.1. Detailed Workflow

#### End-to-End Execution Path.

EvoCast organizes one autonomous research task as a fixed execution
path. The system first reads the task card and fixes the dataset,
forecasting mode, targets, lookback, horizon, metric, training budget,
research-round budget, and repair budget. It then establishes the active
baseline under the fixed protocol and performs mechanism-level diagnosis
on that baseline. During formal research, the Research Planner reads
task evidence, mechanism evidence, prior-round evidence, failure memory,
and the current best model to select one module-level direction. The
Coding / Builder Agent implements that direction within a bounded source
scope, and the Program Authority Chain performs source validation,
canonical evaluation, promotion judgment, and state update. After
termination, the Report Narrative Agent reads frozen facts and generates
the final HTML report.

The execution path is grounded in a fixed comparison surface. All
baselines, ablation candidates, research candidates, and seed
evaluations share the same task protocol. Each round therefore has a
unified interpretation: accepted candidates update the model state,
valid rejections update scientific evidence, unstable improvements
become weak positive evidence, and engineering failures update failure
memory. The next planner invocation reads the updated state, which turns
the loop into evidence-driven iteration.

Figure [2](#acmlabel2 "Figure 2 ‣ 3. Preliminaries ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution")
shows the complete runtime path of EvoCast. The upstream stages fix the
task protocol and establish the baseline, the middle stages perform
baseline diagnosis and formal research rounds, and the downstream stages

final reporting. The central relation is the closed-loop state flow:
accepted results, negative results, repair records, and failure records
are written into the research state and become inputs to later Research
Planner invocations.

#### Cognitive Roles and Program Authorities.

EvoCast separates cognitive roles from program authorities. The
cognitive roles include the Baseline-Diagnosis Planner, the Research
Planner, the Coding / Builder Agent, and the Report Narrative Agent.
They generate ablation targets, research directions, candidate source
states, and final report narrative. Program authorities control source
boundary checking, candidate materialization, canonical evaluation,
promotion gate decisions, result semantics, and persistent state update.

This separation defines three permissions. LLM agents can generate
research intent and code changes. Builder edits must remain inside the
fixed editable boundary. Experimental facts, metrics, promotion
decisions, and model-state updates are confirmed only by program
authorities. Agent self-report does not directly become an experimental
conclusion.

#### Boundary Enforcement.

Boundary enforcement separates model-side editing from evaluation-side
fact production. The editable region covers only the model-side source
files allowed in the current round. The dataset loader, split
definition, metric computation, training schedule, evaluation runner,
and promotion logic remain frozen outside the Builder’s editable scope.
Each candidate first passes source-boundary validation before canonical
evaluation is launched. Candidates that violate the frozen protocol are
marked as protocol-invalid results and do not enter formal comparison.

### B.2. Fixed Task Protocol and Task Grounding

#### Task and Protocol Initialization.

Each autonomous run starts from a fixed task protocol. Before research
begins, the system fixes the dataset, target, lookback, horizon,
forecasting mode, metric, training budget, research-round budget, and
repair budget. The protocol is written into the grounded task package
and is reused by baseline evaluation, ablation execution, candidate
evaluation, and seed-stability checks.

The fixed protocol defines the comparison surface for the entire
autonomous run. The Research Planner preserves the task definition. The
Coding / Builder Agent preserves the training strategy, input length,
prediction horizon, and evaluation rule. The Program Authority Chain
generates formal results under the same metric and evaluator.
Improvements, rejections, and failures are therefore interpreted on one
shared semantic surface.

#### Dataset Characterization as Task Evidence.

Task grounding also converts the raw dataset into planner-readable
evidence. EvoCast follows the feature-computation protocol of the TFB
benchmark ([Qiu et al., 2024](#bib.bib1)) and extracts correlation,
transition behavior, distribution shift, seasonality, trend,
stationarity, and short- and long-term distribution differences from
valid variables.

For a univariate dataset, the system keeps the feature vector of the
target variable. For a multivariate dataset, it aggregates valid
variables to form a dataset-level profile:

|  |  |  |  |
|----|----|----|----|
|  | $`\displaystyle\mathbf{z}_{D}=\bigl[`$ | $`\displaystyle z_{\mathrm{corr}},\bar{z}_{\mathrm{trans}},\bar{z}_{\mathrm{shift}},\bar{z}_{\mathrm{season}},\bar{z}_{\mathrm{trend}},`$ |  |
|  |  | $`\displaystyle\bar{z}_{\mathrm{station}},\bar{z}_{\mathrm{short}},\bar{z}_{\mathrm{long}}\bigr].`$ |  |

These features serve only as planning evidence. They describe whether
the task exhibits cross-variable dependency, distribution drift,
periodic structure, trend, or nonstationarity, and they are read
together with baseline diagnosis, prior rounds, and failure memory. They
do not directly choose a specific architecture modification.

#### Baseline Establishment.

Baseline establishment converts the fixed task into a comparable
architecture starting point. Under the fixed protocol, EvoCast runs
baseline candidates and selects the active baseline through canonical
evaluation. This baseline serves as both the comparison anchor for later
research candidates and the executed starting point for baseline
diagnosis.

This stage fixes the source base for architecture evolution. Ablation
targets, research directions, and candidate comparisons are all defined
around the active baseline or the promoted current best model.

### B.3. Baseline Establishment and Diagnosis

#### Executed Mechanism Ablation.

Baseline diagnosis converts the active baseline from a comparison anchor
into mechanism evidence. EvoCast first analyzes the active prediction
path and then uses the Baseline-Diagnosis Planner to generate runnable
mechanism-ablation targets. Each ablation target is tied to a concrete
source region, an ablation action, and an input-output preservation
contract.

Each ablation target goes through the same execution chain used in a
formal research round. The Coding / Builder Agent implements the
ablation candidate, and the Program Authority Chain performs validation,
canonical evaluation, and adjudication. Only ablations that produce
valid evaluation results enter later research evidence.

This execution policy gives baseline diagnosis formal experimental
status. Mechanism importance is determined by real execution under the
shared protocol.

#### Outcome Semantics of Ablation.

Ablation outcomes are converted into planner-readable diagnostic
semantics. Clear degradation marks the removed mechanism as essential
for the current task. Clear improvement marks the mechanism as harmful
or redundant and makes it a replacement or restructuring target. Small
change marks the mechanism as weak or uncertain. Build/runtime failures
enter engineering failure memory, and protocol violations are excluded
from formal research evidence.

| Ablation result | Diagnostic label | Planning consequence |
|----|----|----|
| Clear degradation | essential | Preserve the core function and modify cautiously |
| Clear improvement | harmful or redundant | Prioritize replacement or restructuring |
| Small change | weak or uncertain | Keep it as an exploration target |
| Build/runtime failure | engineering failure | Do not draw a scientific conclusion |
| Protocol violation | invalid | Discard or rerun |

#### Planning Principle.

The core job of the Research Planner is to convert accumulated evidence
into the next testable hypothesis. It first identifies which
architecture capability is still missing for the current task, then
compares multiple mechanism-level candidates, and finally keeps one
direction for the round. A valid direction must be grounded in the
current evidence, map to a real source region of the active
architecture, and increase later research knowledge whether the outcome
is positive, negative, unstable, or failed.

The resulting research direction contains four categories of content.

information-flow change and the empirical outcome that would support or

region and implementation risks. The expected knowledge gain explains
how the round will affect later planning. These four parts define the
research intent but do not possess execution authority.

#### Authority Boundary.

The Research Planner has direction-generation authority. It can
interpret evidence, compare hypotheses, select a source-grounded
direction, and define expected knowledge gain. It cannot modify source
code, change the task protocol, expand the editable boundary, run
evaluation, or update the current best model. The next stages handle
implementation and experimental adjudication.

The Program Authority Chain converts the Builder output into a formal

The candidate-execution chain proceeds from the Builder’s final
workspace to candidate materialization, external verification, canonical
evaluation, promotion-gate judgment, and evidence plus model-state
update.

Promotion Gate is the deterministic adjudication stage for model-state
updates. It handles candidates that have passed source validity and
runtime validity, compares them against the current best under the fixed
metric and comparison rule, and applies the seed-stability requirement
before authorizing promotion.

Single-run improvement is recorded as evidence, while stable improvement
is required for model-state promotion. EvoCast places seed evaluation
inside the Promotion Gate so that current-best updates depend on
reproducible gain. This stability check protects later planning,
evidence accumulation, and final reporting from incidental seed effects.

Promotion semantics are therefore split into two levels. The first level
is evidence recording: single-run improvements, valid rejections, and
unstable gains can all be written back as executed evidence. The second
level is incumbent replacement: only candidates that pass
source-boundary validation, produce valid canonical metrics, and satisfy
the fixed multi-seed comparison rule can update the current best model.
This split keeps evidence accumulation and model-state promotion
distinct.

This authority chain turns a candidate source state into an experiment
with clear research semantics. The research conclusion comes from real
execution and fixed rules.

#### Execution Semantics.

The Program Authority Chain distinguishes source validity, runtime
validity, and scientific admissibility. Source validity checks whether
the candidate respects the editable boundary and forms a formal
candidate. Runtime validity checks whether the candidate runs under the
shared evaluator. Scientific admissibility checks whether the result
satisfies the predefined comparison and stability rules. Only candidates
that pass all three levels can affect the model state.

Under this framework, candidate execution yields four formal outcome
classes: accepted candidate, valid rejection, unstable improvement, and
engineering failure. An accepted candidate updates the current best
model. A valid rejection produces confirmed negative evidence. An
unstable improvement becomes weak positive evidence and does not update
the current best. An engineering failure updates failure memory and
constrains later implementation paths.

### B.6. Iterative State Update and Final Reporting

#### One-Round Lifecycle.

One formal research round contains five steps: research-direction
selection, candidate implementation, authoritative execution, outcome
classification, and state update.

Each round focuses on exactly one research direction and closes with a
recordable state update. A round can produce a positive result, negative

#### Repair within the Same Round.

When a candidate fails during verification or formal evaluation, the
system returns structured failure feedback to the same Builder session
inside the current round and allows repair within the repair budget.
Repair keeps the same research direction, task protocol, editable
boundary, and comparison rule.

This design confines engineering repair to candidate executability
restoration. The Builder can use runtime feedback to fix import, shape,
interface, or live-path activation issues, while the research goal and
modification scope remain fixed. This keeps round attribution clear and
reduces repeated restarts.

#### Model State and Evidence State.

EvoCast maintains two core state types. The model state records the
current baseline, current best model, comparison anchor, and promotion
history. The evidence state records ablation outcomes, historical
directions, valid negative results, unstable improvements, accepted
candidates, repair records, and engineering failures. State updates are
separated by outcome type: accepted candidates update the model state;
valid rejections and unstable improvements update scientific evidence;
engineering failures update failure memory; repair history updates
implementation-risk evidence.

Consistent with
Section [4](#S4 "4. Method ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution"),
incumbent replacement is written as

|-----|------------------------------------------------------------------|-----|
|     |

       M_{r},&\text{otherwise}.\end{cases}
       ```                                                               |     |

This rule covers only the current-best model update. Accepted candidates
replace the incumbent, while the other outcomes keep the incumbent
unchanged.

The evidence update is written as

|     |                                  |     |
|-----|----------------------------------|-----|
|     |
       ``` math

semantics can be expanded as

|  |  |  |

``` |  |

candidates produce confirmed positive evidence and model promotion,

#### Next-Round Effect of Different Outcomes.

The next Research Planner reads the full updated research state,
including accepted candidates, negative results, unstable improvements,
repair history, failure memory, and baseline diagnosis. This update rule
turns historical execution into constraints and clues for later
planning, which reduces repeated failure paths and unnecessary
trial-and-error.

#### HTML Report Generation.

When the research budget is exhausted or a termination condition is met,
the system freezes the final current-best model, round history,
canonical metrics, gate decisions, accepted and rejected evidence, and
failure records. The Report Narrative Agent reads these frozen facts and
generates a human-readable HTML report.

The Report Narrative Agent is responsible for narrative generation only.
It cannot modify metrics, promotion decisions, model state, or evidence
state. The final report is therefore a narrative output derived from
frozen research facts.

The final output bundle includes the validated current-best model,
reproducible source and configuration, token usage, and HTML report. The
planner generates research intent, the builder forms candidate source
states, the authority chain produces experimental facts, and the report
agent turns frozen facts into an auditable result.

## Appendix D Additional Results and Analysis

### D.1. RQ1 Additional Results

RQ1 evaluates repository-level implementation capability under fixed
predefined tasks. All compared methods receive the same initial
repository snapshot, the same idea text, the same editable and forbidden
regions, and the same canonical build/smoke entry. The comparison
therefore measures whether a given architectural idea can be translated
into faithful, protocol-compliant, and executable code under a shared
validation pipeline.

The formal task suite contains 30 tasks built from 10 forecasting
backbones and 3 idea-complexity levels per backbone. The 10 target
backbones are DLinear, xPatch, FiLM, Crossformer, DUET, iTransformer,
PatchTST, Amplifier, TimeFilter, and CrossLinear ([Zeng et al.,
2023](#bib.bib40); [Stitsyuk and Choi, 2025](#bib.bib81); [Zhou et al.,
2022a](#bib.bib74); [Zhang and Yan, 2023](#bib.bib45); [Qiu et al.,
2025](#bib.bib47); [Liu et al., 2024](#bib.bib10); [Nie et al.,
2023](#bib.bib9); [Fei et al., 2025](#bib.bib72); [Hu et al.,
2025](#bib.bib71); [Zhou et al., 2025a](#bib.bib42)). All methods use
MiniMax-M3 as the unified agent-driving model, and all compared agent
methods use a fixed decoding temperature of 0.1.

The three idea-complexity levels are predefined task labels. For each
backbone, the idea text is already given in advance, and the comparison
focuses on whether an agent can faithfully translate that fixed idea
into executable code under realistic deep-learning implementation
constraints.

The compared methods are defined as follows.

- •
  Direct Independent Edit: a one-shot direct repository edit from the
  given idea text, without multi-step planning, bounded repair, or
  agent-level orchestration.
- •
  mini-SWE-agent ([Yang et al., 2024a](#bib.bib21)): a lightweight
  software-engineering agent that iteratively edits the repository with
  tool use and execution feedback.
- •
  AutoResearch ([Kumar et al., 2026](#bib.bib23)): an execution-grounded
  research workflow that organizes the task into iterative proposal,
  implementation, and validation steps.
- •
  AIDE (2025) ([Jiang et al., 2025](#bib.bib20)): a search-based ML
  engineering agent that explores and evaluates candidate implementation
  trajectories.
- •
  R&D-Agent ([Yang et al., 2025](#bib.bib22)): a dual-role
  research-and-development workflow in which proposal generation and
  code realization are handled by separate agent functions.

Together, these baselines cover one-shot editing, lightweight SWE
agents, search-based engineering, execution-grounded research workflows,
and split-role research/development pipelines.

|  Level |  Definition |  Typical forms |  Main capability under test |
|----|----|----|----|
|  Level 1: Local Modification |  Modify an existing module locally without changing the surrounding execution structure. |  Replace an activation; add a residual gate; adjust the normalization position; insert a lightweight channel mixer. |  Small and precise local code edits inside an existing deep-learning block. |

|  Level 3: Novel Module Insertion |  Add a new module or reorganize the main execution path so that the new mechanism participates in prediction. |  Add a context-conditioned spectral gate; add a horizon-adaptive branch; add a variable interaction router. |  New-module implementation and main-path restructuring under executable repository constraints. |

advantage therefore comes from cross-backbone consistency and does not
depend on isolated wins on a few easier targets. This is the main reason
the backbone-level analysis matters for RQ1: the benchmark evaluates
whether a method can reliably implement ideas in realistic,
heterogeneous deep-learning repositories across the full task set.

et al., 2008](#bib.bib2)) comes from hourly pollutant concentrations and
gas-sensor responses collected at a road-level monitoring station in an
Italian city, which forms a multivariate air-quality forecasting task.
Melbourne Pedestrian T33 ([Godahewa et al., 2020](#bib.bib3)) comes from
hourly pedestrian counts recorded by the City of Melbourne pedestrian
counting system, and we use the public T33 series as a single-series
forecasting task. Steel Industry ([Sathishkumar et al.,
2021](#bib.bib4)) comes from electricity-consumption records collected
in a smart small-scale steel industry in South Korea, and we use it as a
multivariate-to-univariate industrial energy forecasting task with
Usage_kWh as the prediction target.
Table [D.2](#A4.T2 "Table D.2 ‣ D.2. RQ2 Additional Results ‣ Appendix D Additional Results and Analysis ‣ EvoCast: Reliable Autonomous Research Agents for Iterative Forecasting Architecture Evolution")
summarizes the task settings and core characteristics of the three
public datasets.

All tasks follow the same experimental protocol: the data are split by
chronological order with a 7:1:2 ratio for training, validation, and
testing; no split is shuffled; sample construction uses rolling windows
with stride 1; normalization statistics are computed on the training set
only and then reused for validation and testing; and MSE and MAE are
computed in that normalized space.

For general-purpose time-series forecasting models, we use a shared base
training budget with batch size 32, a maximum of 10 epochs, and
early-stopping patience 3. Beyond these shared training constraints,
model-specific hyperparameters are tuned within predefined reasonable
ranges to obtain comparable task-level performance. For agent-based
methods, we keep the training hyperparameters specified by the agent
workflow for its final selected program and then reevaluate that program
under the same formal forecasting protocol. This setting lets strong
forecasting models and agent workflows follow their natural usage
patterns while sharing the same data split, prediction windows,
normalization rule, and evaluation metrics.

The formal comparison includes only artifacts that satisfy the
forecasting-time information constraint and the shared evaluation
protocol. This setting keeps the focus on final deliverable forecasting
artifacts under one fixed evaluator.

All cognitive-agent calls use MiniMax-M3 with thinking mode set to auto.
Temperature follows each method’s own program setting; when a method
does not explicitly pass a temperature value, no additional temperature
override is injected at runtime. EvoCast uses the formal run with seed
2027; when needed, archived seed-evaluation results are used as
stability references. The metrics used in this section are defined as
follows:

- •
  MSE: normalized mean squared error on the formal rolling test windows.
- •
  MAE: normalized mean absolute error on the formal rolling test
  windows.
- •
  Active Sec.: wall-clock seconds consumed by the complete agent
  workflow from start to termination, including planning, coding,
  execution, repair, evaluation, and state update.
- •
  LLM Calls: total number of model calls made during the complete agent
  run.
- •
  Total Tokens: cumulative input and output token usage.
- •
  Cost USD: total API cost under the actual pricing setting.

The compared methods cover both strong forecasting models and autonomous
agent workflows. Together, they span foundation-model forecasting,
multimodal forecasting, machine-learning engineering agents, and
research-oriented agent workflows. The compared methods are defined as
follows:

- •
  Sundial (2025) is a generative time-series foundation model that
  emphasizes scalable pretraining and zero-shot forecasting.
- •
  Toto-2.0-2.5B (2026) is a large-scale time-series foundation model
  that emphasizes forecasting performance gains with model scaling.
- •
  Time-VLM (2025) ([Zhong et al., 2025](#bib.bib16)) is a multimodal
  forecasting model that enhances time-series representations with
  visual and textual signals.
- •
  TimeCMA (2025) ([Liu et al., 2025a](#bib.bib15)) is an LLM-empowered
  multivariate forecasting model that emphasizes multivariate prediction
  under cross-modality alignment.
- •
  AIDE (2025) ([Jiang et al., 2025](#bib.bib20)) is a machine-learning
  engineering agent that models iterative trial-and-error as tree search
  in code space.
- •
  R&D-Agent (2025) ([Yang et al., 2025](#bib.bib22)) is a dual-agent
  research-and-development workflow in which a Researcher proposes
  directions and a Developer executes implementation with
  feedback-driven iteration.
- •
  EvoCast is the proposed fixed-protocol autonomous
  architecture-development workflow with task-specific baseline
  diagnosis, evidence-grounded planning, bounded repository-level
  implementation, canonical evaluation, and program-controlled
  promotion.

### D.3. RQ3 Additional Results

RQ3 examines how EvoCast’s system-level components affect autonomous
architecture-development reliability, final quality, and agent-side
cost. All ablations are defined against the full EvoCast workflow under
the same forecasting task, the same baseline, and the same research
budget. The goal is to isolate how each component contributes to the
full loop from evidence construction to research planning, bounded
execution, and iterative state update.

The task is fixed to Melbourne Pedestrian T33 with PatchMLP as the
baseline, lookback 168, horizon 24, and optimization metric MSE. Each
run contains 20 formal research rounds, and the repair budget is 3. A
valid round is a formal research round that produces a measurable MSE or
MAE. The full EvoCast system contains dataset characterization, baseline
diagnosis, evidence-grounded planning, authority-controlled execution,
and iterative evidence update. RQ3 removes one component at a time while
keeping the remaining pipeline fixed.

Full system setting. The full system executes the complete EvoCast loop
and serves as the reference point for all ablations. It preserves task
evidence construction, executed baseline diagnosis, evidence-grounded
planning, bounded repository-level implementation, and iterative state
write-back across rounds.

A1: Dataset characterization removed. This variant removes
dataset-profile input from the planner while keeping baseline diagnosis,
formal planning, authority-controlled execution, and iterative state
update unchanged. The removed information is the explicit task evidence
that describes data structure, temporal pattern, and forecasting
difficulty. A1 therefore tests how much direction quality depends on
direct task evidence rather than only on baseline behavior and
later-round execution records.

A2: Baseline diagnosis removed. This variant keeps dataset
characterization and the later formal research loop, but it removes
baseline mechanism ablation before research rounds begin. The planner
still sees task evidence, yet it no longer receives executed evidence
about which baseline mechanisms are already effective, weak, or
redundant. A2 therefore tests whether mechanism-level starting-point
judgment is necessary for targeted module selection and efficient budget
allocation.

A3: Evidence-grounded planning removed. This variant keeps dataset
characterization, baseline diagnosis, execution, and evaluation, but it
removes the planner’s structured evidence inputs, including dataset
profile, baseline diagnosis, research context, round history, and recent
status. Candidate construction can still proceed, but direction
selection no longer uses the complete accumulated evidence bundle. A3
therefore tests whether continuous executability alone is sufficient, or
whether high-quality convergence requires fully evidence-grounded
direction selection.

A4: Authority-controlled execution removed. This variant keeps
research-direction generation and multi-round execution, but it removes
repository write-boundary control in the candidate workspace. The
planner still produces mechanism hypotheses, yet candidate
implementation is no longer restricted to source regions directly tied
to the current hypothesis. A4 therefore tests whether execution-boundary
control is necessary to keep repository edits focused, maintain budget
discipline, and preserve reliable formal comparison across rounds.

A5: Iterative evidence update removed. This variant keeps the initial
task evidence, baseline diagnosis, planning, and bounded execution, but
it freezes the historical evidence visible to the planner so later-round
results are no longer written back. The current best model can still be
retained, but failure records, marginal improvements, repair history,
and validated mechanisms no longer enter later planning. A5 therefore
tests whether persistent evidence accumulation is necessary for
sustained multi-round progress.
