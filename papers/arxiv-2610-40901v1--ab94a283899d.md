#  TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research

ChengAo Shen¹    Yanjun Zhao²    Haoxin Liu³    Bonnie Chen⁴    Miles
Ma⁵     
Dongjin Song⁶    Hanghang Tong²    Qingsong Wen⁷    Jingrui He²   
Jingchao Ni^(1🖂)

###### Abstract

As publications and products on time series forecasting (TSF)
proliferate, researchers face a growing burden of analyzing existing
work. First, not all publications release code. For instance, only about
20% of arXiv TSF papers have a code link in the surveyed period. Second,
released code also requires manual maintenance. Thus, TSF researchers
must constantly adapt or implement existing works. However, independent
implementations can differ in experimental settings and are difficult to
maintain. We therefore propose to use AI agents for benchmarking TSF
research and even supporting autoresearch, e.g., developing new TSF
models. Yet directly applying existing coding agents, such as Claude
Code and Codex, is suboptimal: prohibitive costs, limited scalability to
large research projects (e.g., benchmarking), and lack of
self-maintenance. To address these challenges, we propose TSFLab, a
self-improving agent-agnostic “workbench” that equips compatible coding
agents with shared resources and tools for low-cost TSF research and
continuous maintenance of research resources. Our experiments cover
reproduction, benchmarking, and new method development. In reproduction
and benchmarking, TSFLab improves task completion by 20–163% and cuts
fresh tokens per completed task by 11–66% across baselines. A pilot
study of agent-driven method development also shows improved forecasting
accuracy via TSFLab, with 32.8–73.6% fewer fresh tokens and 9.2–68.8%
less development time than the other settings.

## 1 Introduction

Time series forecasting (TSF) is a fundamental task in energy
\[[14](#bib.bib14)\], transportation \[[22](#bib.bib22)\], finance
\[[33](#bib.bib33)\], weather \[[20](#bib.bib20)\], and public health
\[[7](#bib.bib7)\]. In Fig.
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(a),
we summarize the statistics of TSF preprints and code releases using
data from arXiv. As can be seen, code releases grow much more slowly
than papers: only about one in five of the 1,707 papers since 2020
provides a code link. Researchers, particularly those who are new to
this area, must often reimplement baselines and build evaluation
pipelines manually. While TSF libraries exist, keeping them up to date
is challenging: TSLib \[[38](#bib.bib38)\] grew from 18 to 41 methods
despite over 1,200 new papers since 2024, and announced in April 2026
that it is no longer maintained due to limited maintainer capacity.

![Refer to caption](2610.40901v1/01-intro.png)

Figure 1: (a) Growth of TSF papers, papers with code, and methods in
libraries. (b) General agents access external resources directly for

AI agents offer a promising solution. Agent-based autoresearch has shown
potential in reproducing experiments \[[37](#bib.bib37)\], conducting
new experiments \[[17](#bib.bib17), [27](#bib.bib27)\], and developing
new methods \[[25](#bib.bib25), [32](#bib.bib32)\]. In domains such as
biology and chemistry, systems such as ChemCrow \[[3](#bib.bib3)\] and
PantheonOS \[[42](#bib.bib42)\] equip agents with domain-specific
knowledge, tools, and workflows, accelerating research in these areas.
In these agents, the infrastructure surrounding their LLMs is called a
“harness” \[[43](#bib.bib43), [21](#bib.bib21)\].

Unlike a harness, which is part of each agent, a “workbench” lies
outside agents: it is reusable and shareable across agents. Workbenches
exist for general science, such as ToolUniverse \[[10](#bib.bib10)\] and
Scientific Agent Skills \[[18](#bib.bib18)\], and for biomedicine, such
as Biomni-E1 \[[16](#bib.bib16)\], but not for TSF. We introduce a
domain-specific workbench that supports AI agents throughout TSF
research. Existing TSF agent research focuses on harness development
\[[51](#bib.bib51), [11](#bib.bib11), [35](#bib.bib35)\]. However, once
their systems are developed, they cannot automatically benefit from the
emergence of newer agents. In contrast, a workbench is plug-and-play
infrastructure for any compatible agent, such as Claude Code
\[[2](#bib.bib2)\], Codex \[[30](#bib.bib30)\], and Pi
\[[9](#bib.bib9)\], benefiting from their continuously improving
capabilities. As compared in Fig.
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(b)
and (c), a workbench enables reuse across agents and teams: a
reproduction agent can add verified implementations to the workbench for
a benchmarking agent to reuse. Another agent can then reuse these
benchmarks for method development.

Using agents with only their harness for TSF research presents two
challenges: (1) Slowly Updated TSF Knowledge. An LLM-based agent’s
knowledge depends on its training cutoff, so it may not cover newer TSF
models and experimental protocols \[[31](#bib.bib31), [4](#bib.bib4)\].
Web search alleviates this problem, but repeated searches for
large-scale research projects are token-costly. Retrieved sources may be
incomplete or unreliable, and unchecked errors may propagate into
subsequent research. For example, the official code of Informer (i.e., a
TSF model) \[[52](#bib.bib52)\] mistakenly dropped the last test batch
in evaluation, which has influenced the settings of many subsequent
studies \[[31](#bib.bib31)\]. (2) Inconsistent Research Settings. As
shown in Fig.
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(b),
agents that configure experiments independently may resort to different
information sources, leading to different settings, implementations, and
incomparable results. This makes it hard to share findings across agents
and teams, and leads to unnecessary repeated experiments
\[[39](#bib.bib39), [46](#bib.bib46)\]. Both challenges make agent-based
TSF research costly and hard to scale: agents repeat source searches,
model implementations, and experiments across agents and teams.

To address these challenges, we propose TSFLab, a novel TSF workbench,
as illustrated in Fig.
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(c).
TSFLab has four modules: (a) TSF-Domain Guide enables TSF-awareness
through common research workflows, experimental settings, evaluation
protocols, and known pitfalls; (b) Knowledge Structurer decomposes
existing TSF models into reusable units and organizes these units,
methods, and diverse benchmark datasets into a unified structure. This
structure is realized by a “knowledge card” for each method, unit, and
dataset, read level by level (summary, card, source) as a decision
requires, so that AI agents can reason efficiently without token-costly
reading of code and data details. (c) Experiment Workflower executes
agent-declared experiments through a unified runner that validates and
runs experiment configurations and reports results under consistent
protocols. (d) Recursive Improver routinely checks and verifies
up-to-date TSF research outcomes and integrates verified artifacts
(e.g., models, datasets) into the workbench for self-maintenance. The
workbench is updated independently of agent releases. Our contributions
are as follows.

- •
  We identify two causes of agent inefficiency in TSF: slowly updated
  knowledge and inconsistent settings.
- •
  We propose TSFLab, an agent-agnostic TSF workbench that empowers any
  compatible agent without altering it.
- •
  Using TSFLab, we integrated 323 TSF models and compiled 93 datasets,
  along with 71 model units that can be reused for autoresearch.
- •
  We evaluate TSFLab on three research tasks. In reproduction and
  benchmarking, it raises completion by 20–163% and cuts fresh tokens
  per completed task by 11–66% across baselines. A pilot study explores
  method development with fewer fresh tokens and less development time.

## 2 Related Work

TSF Libraries and Benchmarks. TSLib \[[40](#bib.bib40)\], BasicTS
\[[34](#bib.bib34)\], TFB \[[31](#bib.bib31)\], and NeuralForecast
\[[29](#bib.bib29)\] provide implementations and evaluation pipelines,
and GIFT-Eval \[[1](#bib.bib1)\] benchmarks time series foundation
models. Results and rankings change with evaluation settings and tuning
budgets \[[31](#bib.bib31), [4](#bib.bib4)\], yet agents must read
library code to recover these settings. Methods are added and maintained
by hand, so coverage lags the literature (Fig.
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(a)).
TSFLab describes its 323 methods and 93 datasets in knowledge cards read
level by level, with more methods than these libraries (Fig.
[4](#S4.F4 "Figure 4 ‣ 4.2 Main Results ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")).

Research Agents and Harnesses. Agents show potential to reproduce papers
\[[37](#bib.bib37)\], run machine learning experiments
\[[17](#bib.bib17), [27](#bib.bib27)\], and propose new methods
\[[25](#bib.bib25), [32](#bib.bib32)\], but rely on general training
knowledge. Domain agents such as ChemCrow \[[3](#bib.bib3)\] and
PantheonOS \[[42](#bib.bib42)\] add chemistry and genomics tools. TSF
agents such as TimeSeriesScientist \[[51](#bib.bib51)\], TimeCopilot
\[[11](#bib.bib11)\], and MetaCaster \[[35](#bib.bib35)\] orchestrate
forecasters or optimize their training: they produce forecasts rather
than conduct TSF research. In these systems, domain support lives in the
agent’s harness \[[43](#bib.bib43), [21](#bib.bib21)\], so it serves one
agent and must be rebuilt for newer ones. TSFLab serves any compatible
agent unchanged.

Agent Workbenches. Workbenches move domain support outside agents.
ToolUniverse \[[10](#bib.bib10)\] exposes scientific tools to different
agents and generates new ones, Scientific Agent Skills
\[[18](#bib.bib18)\] packages portable procedures, and Biomni-E1
\[[16](#bib.bib16)\] supplies biomedical tools, software, and databases.
They provide tools and procedures for general science or biomedicine,
rather than TSF methods under declared evaluation protocols. TSFLab is a
TSF workbench with TSF-Domain Guide, Knowledge Structurer, and
Experiment Workflower, which executes comparisons under shared, explicit
evaluation protocols across agents and teams.

Self-Improving Agents. STOP and the Darwin Gödel Machine revise agent
code through score-based selection \[[44](#bib.bib44),
[48](#bib.bib48)\], Voyager accumulates skills \[[39](#bib.bib39)\], and
memory systems retain information across tasks \[[46](#bib.bib46),
[49](#bib.bib49)\]. These methods improve a single agent. The Recursive
Improver of TSFLab improves the shared workbench instead: it checks each
method against its paper and official code and merges verified methods,
units, datasets, and findings, so research outputs from every task feed
both the improvement and the maintenance of the workbench.

### 3.1 Problem Statement

Let $`\mathcal{W}`$ be a workbench, and $`\Pi`$ be the set of agents
that are compatible with $`\mathcal{W}`$. Each $`\pi\in\Pi`$ comprises
its underlying model and harness. The harness coordinates model and tool
execution, manages context, and organizes internal workflows. In
contrast, the workbench $`\mathcal{W}`$ provides reusable domain
knowledge, research procedures, and experimental tools without changing
the model or harness:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\pi^{*}=\operatorname{Augment}(\pi,\mathcal{W}),\qquad\pi\in\Pi.
``` |  | (1) |

Our goal is to improve valid task completion (i.e., completing a
research task exactly as required) and reduce cost per completed task.
We describe the evaluation metrics in
§[4.1](#S4.SS1 "4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").

TSFLab supports research through four modules, as shown in Fig.
[2](#S3.F2 "Figure 2 ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research"):
(a) TSF-Domain Guide is used by an agent for task procedures, (b)
Knowledge Structurer selects methods, configures parameters, and reuses
model units, (c) Experiment Workflower executes the declared
experiments, and (d) Recursive Improver verifies new resources and
outcomes for updating the shared workbench.

### 3.2 TSF-Domain Guide

TSF research requires domain knowledge of data integration, method
implementation, and evaluation protocols
(§[1](#S1 "1 Introduction ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")).
TSF-Domain Guide connects this knowledge to workbench procedures: entry
instructions introduce conventions and module interactions, while 17
task-specific skills provide steps, checks, and pitfalls as needed.

For example, when benchmarking methods on a new dataset, a skill guides
the agent to identify time fields, forecasting variables, sampling
frequency, and evaluation settings, then register data through the
workbench’s “add” interface and inspect partitioning and scaling through
its “split” interface. The agent does not need to maintain its own
loading and splitting code. The skill also requires checking whether
forecasts are evaluated on one target or all variables, keeping metrics
consistent across methods. These choices establish the constraints for
resource selection and configuration. The entry instructions and
task-specific skills are detailed in App.
[A](#A1 "Appendix A Framework Structure and Domain Guide ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").

### 3.3 Knowledge Structurer

|  Level |  When to consult |  Information provided |
|----|----|----|
|  Summary |  Screening candidates |  Category and use cases |
|  Card |  Resource selection, configuration, unit reuse |  Capabilities and limits, parameters and interfaces, verification records |
|  Source |  Checking details, resolving doubts, modifying methods |  Original papers, reference code, detailed evidence |

Table 1: Three levels of research knowledge.

After establishing task requirements, the agent uses Knowledge
Structurer to select and configure resources. It provides a knowledge
card for each method, dataset, and unit, organized into summary, card,
and source levels. Summaries support screening; cards describe
capabilities, parameters, interfaces, and limitations; sources provide
papers, reference code, and detailed explanations. This progressive
disclosure \[[13](#bib.bib13), [47](#bib.bib47)\] lets agents retrieve
the detail needed for each decision without rereading sources (Tab.
[1](#S3.T1 "Table 1 ‣ 3.3 Knowledge Structurer ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")).

Method cards connect mechanisms to use cases and configuration. For
example, the card of PatchTST \[[28](#bib.bib28)\] explains its
channel-independent design—modeling variables separately with shared
weights—so an agent can compare it with methods that learn
cross-variable interactions. It also states whether the implementation
supports exogenous inputs or probabilistic forecasts, clarifying task
compatibility. Parameter descriptions define patch length and stride;
existing settings and input-window constraints help agents exclude
unsuitable configurations and plan validation comparisons. The workbench
sets data-dependent parameters, such as input channel count, from
declared dependencies. Dataset cards record data characteristics and
split, scaling, and evaluation protocols. Thus, agents screen resources
by both forecasting mechanism and task compatibility, consulting source
details when a configuration or implementation decision requires them.

Knowledge Structurer also extracts common blocks, such as RevIN, series
decomposition, and attention variants, into shared units that methods
import, enabling shared maintenance; 263 methods reuse at least one
unit. Each unit has a card, and method cards record which units they
use. For example, RevIN removes an input window’s level and scale and
restores them in the forecast. Its card describes the shifts it
addresses, parameters, and channel requirements, helping agents decide
whether to reuse it in a new method.

### 3.4 Experiment Workflower

With resources selected, Experiment Workflower executes agent-declared
experiments through a unified runner. Each method’s specification
defines parameter requirements, construction, and input and output
interfaces, allowing the runner to instantiate the model and connect it
to shared loading, training, and evaluation routines. Presets supply
training settings, dataset protocols, and architecture parameters for
reuse across experiments.

Agents use Compose to combine presets, Override to change settings, and
Sweep to expand methods or values. For new-data benchmarking, an agent
combines dataset and method presets, fixes the lookback, horizon, and
training budget, and sweeps methods and seeds. The runner expands
configurations into a run matrix, then checks configuration validity,
data, model compatibility, environments, and budgets. It returns
problems before training, connecting the agent’s declaration to shared
training and evaluation.

Shared routines split data as configured, fit scaling on training data
only, select checkpoints on validation data, and compute metrics
consistently. The runner schedules runs within resources and budgets,
preserving status, checkpoints, and prior attempts. Recovery checks
configuration, data, and code fingerprints, skips completed runs, and
resumes failed runs from their last complete epoch. Status, wait,
cancel, and resume interfaces reduce manual management of scripts,
processes, and logs.

The runner returns metrics, training time, peak GPU memory, status, and
artifact paths, archiving configurations, seeds, environments, and data
versions. Result summaries compare methods only under the same data
processing, training, and evaluation protocol, reporting seed coverage
and variation. Recorded evidence supports subsequent comparisons,
development, and review through Recursive Improver
(§[3.5](#S3.SS5 "3.5 Recursive Improver ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")).

### 3.5 Recursive Improver

Here, self-improvement means incorporating verified research outputs and
fixes into the workbench’s shared resources and workflows so later
agents can reuse them. For example, evaluation problems found during
research sessions lead to revised guidance and runner checks; later
sessions inherit these repairs.

Recursive Improver brings external resources and agent-produced outcomes
back into the shared workbench through checks for usability, complexity,
and consistency (Fig.
[2](#S3.F2 "Figure 2 ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")d).
Failed checks prompt revision and rechecking before integration,
supporting workbench maintenance.

Usability. Continuous integration (CI) checks basic operations. Method
tests cover construction, a training step, input and output
requirements, and saving and loading; dataset checks cover schema and
evaluation protocols; experiment records require complete configurations
and runner-produced results. They also confirm required card fields and
agreement between method specifications and presets, exposing
integration errors.

Complexity. CI checks function-level cyclomatic complexity and method
size. Cyclomatic complexity counts independent execution paths through a
function; method size counts lines of code. These flag implementations
that are harder to understand, test, and maintain. Code above the limits
requires simpler logic, smaller functions, or shared units, then renewed
runtime and behavioral checks.

Consistency. An independent read-only review agent checks whether cards
describe implementations and whether implementations preserve the
defining mechanisms in papers and pinned official code, using papers
alone when code is unavailable. For example, it checks for
cross-variable computation in a method described as channel-independent.
Paper–code setting differences and implementation choices are recorded.
For extracted units, automated tests compare parameters, outputs, and
input gradients before and after extraction, checking model state,
forward computation, and backpropagation behavior on reference cases.

Accepted resources and verification records enter the workbench to
support subsequent benchmarking, reproduction, and method development.
Additions and fixes from these tasks undergo the same checks, forming a
shared update cycle that reduces repeated collection, implementation,
and setup. Consequently, a session can contribute a reusable method,
unit, or workflow repair alongside its experimental results.

Baselines. We compare TSFLab with two TSF codebases and with no
workbench: Time-Series-Library (TSLib) \[[40](#bib.bib40)\], a model
library, and TFB \[[31](#bib.bib31)\], a benchmarking framework. Without
a workbench, the agent starts from an empty directory with PyTorch. All
main settings use Codex CLI with GPT-6 Luna and identical prompts, data,
network access, and budgets; Tab.
[3](#S4.T3 "Table 3 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
varies the agent.

Research Tasks. (i) Paper reproduction: the agent reproduces the
reported results of a recent forecasting paper that has no official code
and is absent from all compared codebases (RhyMix \[[36](#bib.bib36)\],
StateFlow \[[12](#bib.bib12)\], AdaRDiff \[[19](#bib.bib19)\], and CoRe
\[[23](#bib.bib23)\]; App.
[D](#A4 "Appendix D Experimental Setup and Evaluation ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")).
(ii) Benchmarking on new data: given two new datasets, ERCOT and
Openmeteo, the agent benchmarks eight methods under a common protocol:
three established baselines (DLinear \[[45](#bib.bib45)\], PatchTST

\[[5](#bib.bib5)\]), and three methods for temporal heterogeneity and
embedding enhancement (TimeMosaic \[[8](#bib.bib8)\], PHAT
\[[26](#bib.bib26)\], and EMAformer \[[50](#bib.bib50)\]). (iii) Method
development pilot: on ETTh1 and Weather, the agent searches for a

### 4.2 Main Results

Tab.
[2](#S3.T2 "Table 2 ‣ 3.5 Recursive Improver ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
and Fig.
[3](#S4.F3 "Figure 3 ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
compare TSFLab with the other settings on reviewed task completion,
cost, and code changes. Reproduction accuracy is evaluated separately by
relative error to the reported MSE. We highlight five observations. (1)
TSFLab completes the most tasks with the most accurate results. It
completes all 12 reproduction attempts and 42 of 48 benchmark results,
the most of any setting. Fig.
[3](#S4.F3 "Figure 3 ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")a
shows that its reproductions are also the closest to the papers: TSFLab
reproduces 73% of the 96 scheduled results within 10% of the paper’s
MSE, against 21–46% for the other settings. Completion and agreement
with the reported MSE thus provide complementary views of reproduction
quality. (2) TSFLab also costs less: each completed outcome takes fewer
tokens and less time in reproduction, and fewer tokens and tool calls in
benchmarking, consistent with agents using shared operations instead of
rebuilding them. (3) Its added code is simpler. Benchmarking needs no
code changes, since all eight methods are already integrated and
Experiment Workflower runs them from configuration; in reproduction,
agents add a similar number of lines but 15–29% fewer functions and
18–28% less added cyclomatic complexity than the other settings,
consistent with reuse of existing units. (4) An existing codebase alone
is not enough. TFB completes fewer outcomes than no workbench in both
tasks, mostly because agents replace requested methods with substitutes.
A framework helps an agent only when the agent can extend it faithfully.
(5) The method-development pilot shows similar benefits. On ETTh1 and
Weather (Fig.
[3](#S4.F3 "Figure 3 ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")b,c),
TSFLab reaches the lowest test MSE with less time and fewer fresh tokens
than every other setting; details are in App.
[D](#A4 "Appendix D Experimental Setup and Evaluation ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").
Reproduction benefits from shared units while still requiring new model
code; benchmarking reuses complete methods. The latter therefore
measures the combined benefit of catalog availability and shared
execution. The six unaccepted benchmark results show that integrated
methods alone do not guarantee valid evaluation. Zero added code
measures implementation reuse; completion review establishes whether
experiments follow the declared evaluation protocol.

### 4.3 Ablation Study

Tab.
[3](#S4.T3 "Table 3 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
reports two groups of ablations. In (a), we remove one module at a time
on four reproduction tasks with three attempts each: the TSF-Domain
Guide (entry instructions and skills), the Knowledge Structurer (cards
and sources), or the Experiment Workflower (runner and experiment
commands). Recursive Improver is examined through maintenance and
refactoring outcomes in
§[4.4](#S4.SS4 "4.4 Further Analysis ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").
In (b), we replace the agent: Claude Code with Sonnet 5.5, and Codex CLI
with GPT-6 Sol.

From Tab.
[3](#S4.T3 "Table 3 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(a),
removing any module lowers completion, and each fails differently.
Without the guide, completion drops the most: agents write their own
data loaders, and every rejected attempt uses wrong ETTh1 split
boundaries, so the guide mainly keeps agents on the evaluation protocol.
Without the Knowledge Structurer, cost stays close to the full
workbench, but agents reuse fewer units and add more code and
complexity. Without the Experiment Workflower, agents write their own
training and evaluation code; they add the most code, and their errors
move into evaluation, such as tuning on test scores and averaging batch
errors. Shared execution thus removes errors that finite results alone
do not reveal. Similar token use without the Knowledge Structurer,
despite lower completion, shows that token cost alone cannot measure
reuse.

Tab.
[3](#S4.T3 "Table 3 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")(b)
highlights two observations. (1) Stronger agent configurations reduce
interaction, but not monetary cost. Compared with GPT-6 Luna, GPT-6 Sol
and Sonnet 5.5 reduce tool calls by 48.5% and 51.1%, and fresh tokens by

\(2\) The workbench lets a lightweight agent match the stronger
configurations in completion. Luna and Sol complete all 12 attempts;
Sonnet completes 11. On these tasks, stronger configurations mainly
reduce interaction, while Luna achieves comparable completion at lower
estimated cost.

### 4.4 Further Analysis

Coverage. TSFLab contains 44 of the 50 most cited methods, compared with
29 across the three other codebases combined (Fig.
[4](#S4.F4 "Figure 4 ‣ 4.2 Main Results ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")a).
The catalog combines established baselines with recent methods that have
official code, reducing the integration needed to begin a comparison.
This measure captures baseline availability; forecasting quality is
evaluated through the research tasks.

Compact implementations. Broader coverage accompanies compact model
implementations (Fig.
[4](#S4.F4 "Figure 4 ‣ 4.2 Main Results ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")b).
The median implementation has 144 lines, close to TSLib’s 145, while the
largest has 505 lines, compared with 2,071 in TFB. Shared units
consolidate common computations, and method specifications handle
construction and parameter requirements outside model logic. These
statistics describe model code; the codebases differ in method coverage
and supported functionality.

Maintenance through reuse. As the catalog grows, extracting shared units
helps control code per method (Fig.
[4](#S4.F4 "Figure 4 ‣ 4.2 Main Results ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")c):
one extraction reduced the average function count from 11.9 to 8.6. A
separate refactor reduced maximum function complexity from 20 to 9 while
preserving bit-identical parameters, outputs, and gradients on reference
cases for all 323 methods. Research sessions also expose reusable fixes.
Missing guidance, manual configuration, repeated log polling, and
premature test access led to instruction and runner updates; all 17
initial usability failures were repaired before integration. These cases
illustrate how Recursive Improver turns recurring problems into shared
improvements, although they do not isolate the effect of individual
checks.

Integration beyond model code. Model implementation accounts for only 9%
of method-intake tokens (Fig.
[4](#S4.F4 "Figure 4 ‣ 4.2 Main Results ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")d).
Source reading, catalog search, and verification account for 28%, 27%,
and 28%, respectively. Efficient integration therefore requires reusing
knowledge and verification evidence as well as code. Knowledge cards
retain these findings, helping later agents locate suitable methods and
units without repeating the same investigation. The mean intake uses
6.1M tokens including cache reads; research-task costs in Tab.
[2](#S3.T2 "Table 2 ‣ 3.5 Recursive Improver ‣ 3 TSFLab ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
count fresh tokens and exclude cache reads.

## 5 Conclusion

We presented TSFLab, a shared TSF research workbench that leaves the
agent’s model and harness unchanged. It combines domain guidance,
structured knowledge, reusable units, execution, and verified resource
updates. Across the evaluated tasks, it improves task completion and
token efficiency, and supports method development. Ablations show
complementary benefits from guidance, resource organization, and shared
execution. Retaining source knowledge, implementations, and experiment
records allows new agents to reuse verified results and repairs. TSFLab
supports cumulative TSF research across agents and teams, allowing
verified improvements to remain available as research tasks, underlying
models, and agent harnesses evolve over time.

## Limitations

TSFLab currently focuses on time series forecasting. Its guidance,
resource descriptions, and experiment interfaces are designed for TSF
methods and evaluation protocols, so their effectiveness in other
research domains remains untested. Extending the workbench would require
adapting these resources and checks to the tasks and conventions of each
domain. Within the limited search time, method development has not yet
produced a new method that substantially outperforms all leading
forecasting models. The reported improvements therefore demonstrate
support for the evaluated development tasks rather than a broadly
superior forecasting method. More effective search strategies and
experimentation over longer research cycles remain directions for future
work.

## Ethical Considerations

TSFLab records the sources, upstream licenses, and reference revisions
of the methods it incorporates. Datasets retain their original licenses,
and data that cannot be redistributed are obtained from their providers;
all data are public numeric time series without personal information.
Reviews document discrepancies between papers and code together with the
chosen implementation, making these decisions open to inspection.
Experimental results should be interpreted under their recorded
protocols; benchmark rankings do not establish that a method is best
across all settings. Coding agents execute code with network access, so
their runs should remain sandboxed, with external actions requiring
explicit authorization. Agent sessions and model training also consume
GPU time and API tokens; TSFLab reduces these costs by sharing
implementations and lowering token use.

## Appendix A Framework Structure and Domain Guide

### A.1 Framework Structure

The workbench separates agent decisions from shared execution. The agent
reads guidance, selects resources from the catalog, declares an
experiment, and interprets its records. Four modules support this
sequence:

1.  1.
    TSF-Domain Guide: entry instructions and skills specify workflows,
    protocol checks, and pitfalls.
2.  2.
    Knowledge Structurer: cards record the interfaces, configuration
    rules, and source evidence of each method, dataset, and shared unit
    in the catalog.
3.  3.
    Experiment Workflower: presets and method specifications connect
    each configuration to the shared loading, training, evaluation, and
    recovery routines.
4.  4.
    Recursive Improver: usability, complexity, and consistency checks
    screen new resources and repairs.

The resulting flow is guidance $`\rightarrow`$ resource selection
$`\rightarrow`$ configuration $`\rightarrow`$ execution $`\rightarrow`$
review $`\rightarrow`$ shared updates. The repository keeps models in
src/tsflab/models/\<model\>/, units in models/\_components/, and
workflows in .agents/skills/. Cards describe resources; specifications,
configurations, and tests define runtime behavior.

### A.2 Entry Instructions and Skills

Every session starts from one harness-neutral entry file, AGENTS.md
(Claude Code reads the same file through CLAUDE.md). It states the
workbench conventions, module interactions, resource access, and
verification requirements. Task-specific skills provide the steps,
checks, and common pitfalls of each workflow and are loaded as needed.
For new-data benchmarking, these procedures guide the agent through
identifying data fields and evaluation settings, adding the dataset, and
inspecting its splits and scaling before configuring experiments.

snapshot.

\## What it does

norm: mu = mean_t(x), sigma = sqrt(var_t(x) + eps),

y = (x - mu) / sigma, then y \* gamma + beta if affine.

denorm: inverts the affine, then z \* sigma + mu with the

statistics cached by the latest norm call (detached).

\## When to use

Level or scale drifts across windows or between training and evaluation.
Not when

output channels differ from input, or when statistics must carry
gradients.

subtract_last=False, enabled=True)

### C.1 Declarative Configurations

An experiment is a TOML file that composes presets: a base configuration
(training, optimizer, checkpointing, metrics), a dataset preset (path,
target, scaling, split ratio), and a method preset (architecture
parameters), followed by overrides and a sweep. For methods already
integrated into the workbench, agents declare the experiment without
writing a separate training script. The runner resolves the
configuration into one run per sweep cell (Listing ). Parameters that a
method card declares as following the data (\[data_params\], e.g. enc_in
= { from = "channels" }) are set from the dataset at run time, reducing
manual changes when reusing a method preset on new data. Each method
specification defines parameter requirements, construction, and input
and output interfaces, connecting the model to the shared loader,
trainer, and evaluator.

### C.3 Budgets and Research Rounds

An optional execution policy sets budgets (runs, parallel jobs, wall
time, GPU-hours) and resources (GPUs per run, free memory, threads per
run); the scheduler leases GPUs exclusively and counts all attempts
against the budget. Runs attached to a research round (tsf research
start) score the validation split unless overridden, for
validation-based search. The method-development protocol is specified in
App.
[D](#A4 "Appendix D Experimental Setup and Evaluation ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").

### C.4 Records and Comparable Results

Every run writes a record with its resolved configuration, metrics,
checkpoints, and timing, and appends a row to a results table that
carries protocol and model-variant fingerprints (data content, task,
evaluation, and training settings). tsf result report ranks methods only
within one protocol and reports seed coverage and spread. The same
records feed the public TSFLab leaderboard, which ranks methods on fixed
benchmark protocols and on real-time tracks that are forecast before the
targets are observed
([https://huggingface.co/spaces/Diaugeia/TSFLab](https://huggingface.co/spaces/Diaugeia/TSFLab));
the two benchmarking datasets of App.
[D](#A4 "Appendix D Experimental Setup and Evaluation ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research")
are static exports from these tracks and are evaluated with
chronological splits.

## Appendix D Experimental Setup and Evaluation

### D.1 Shared Setup

Codebases are pinned (TSLib at 4e938a1, TFB at a0087ed), and every
setting receives the same prompt, task file, and raw data. A session
runs the agent headless with no additional user instructions beyond the
task prompt, no persistent memory, plug-ins, or MCP servers, on
dedicated NVIDIA RTX 6000 Ada GPUs with network access. Each task uses a
fixed TSFLab snapshot, taken in the order reproduction, benchmarking,
and method development; the released code (TSFLab 1.0.0) is the latest
version.

### D.2 Datasets

Reproduction and development. ETTh1 \[[52](#bib.bib52)\] is the hourly
energy dataset used in both tasks. We use its first 14,400 rows and
seven channels, with 8,640/2,880/2,880 training, validation, and test
rows. Traffic \[[41](#bib.bib41), [6](#bib.bib6)\] provides the second
reproduction dataset; both reproduction datasets are evaluated at
horizons 96, 192, 336, and 720. Weather \[[41](#bib.bib41)\] supplies
the second development task, with 21 channels and a chronological 7:1:2
split. Development uses input 336 and horizon 192 on both datasets.
Model-specific reproduction input lengths and training requirements
follow.

New-data benchmarking. ERCOT¹¹ 1
[https://www.ercot.com](https://www.ercot.com) contains hourly load for
eight weather zones, covering 2024-10-01 through 2026-09-30 (17,520
rows). Openmeteo²² 2 [https://open-meteo.com](https://open-meteo.com)
contains hourly 2 m temperature for 82 cities, covering 2025-10-01
through 2026-09-30 (8,760 rows). Both are fixed CSV exports from the
workbench’s real-time tracks. These experiments use historical
chronological splits, rather than the live forecasting protocol of the
original tracks. All channels are forecast with input 168 and horizon
24; scaling is fitted on the training partition only, and metrics use
the normalized scale.

### D.3 Paper Reproduction

Papers are arXiv forecasting papers first submitted on or after
2026-06-01. We kept papers that have no official code, are absent from
every compared codebase, report per-horizon MSE and MAE on ETTh1 and
Traffic at horizons 96, 192, 336, and 720 under the standard protocol,
give enough training detail, and train all four horizons in under one
GPU-hour. Each session has four hours, one GPU, and a ready environment.

- •
  RhyMix \[[36](#bib.bib36)\]: input 96; cyclic and multi-scale
  convolution paths with gated forecasting heads; Huber loss. Each cell
  uses five seeds to match the paper’s five-run means. Batch size and
  gate sizes are not specified.
- •
  StateFlow \[[12](#bib.bib12)\]: input 96; recurrent hidden and
  residual-memory states with a chunk decoder. Part of the cell is
  defined in an earlier paper; optimizer and two-stage schedule are
  unspecified.
- •
  AdaRDiff \[[19](#bib.bib19)\]: input 720; a learnable reversible
  residual transform around a linear backbone. Training runs 30
  residual-loss then 10 forecast-loss epochs. The paper gives only the
  search grid.
- •
  CoRe \[[23](#bib.bib23)\]: input 96; coherence and low-rank
  channel-alignment losses applied to iTransformer. Loss weight, rank,
  and learning rate are unspecified. It is related to the existing FreDF
  method, so the task tests whether agents reuse it.

### D.4 Benchmarking on New Data

The task uses the ERCOT and Openmeteo exports described above. The eight
methods are three established baselines contained in all three codebases
and the five most cited forecasting methods of 2026 venues that TSFLab
contains and TSLib and TFB do not (Semantic Scholar, 2026-10-09):

- •
  DLinear decomposes the input into trend and seasonal parts and
  forecasts each with a linear layer. PatchTST applies a
  channel-independent Transformer to patches of each series;
  iTransformer instead treats each variate’s input history as one token
  and attends across variates.
- •
  TimeAlign trains a patch MLP with a future-reconstruction branch and
  aligns history and future representations at local and global levels;
  inference uses the patch MLP alone.
- •
  GTR retrieves segments from a learned full-cycle memory and fuses them
  with the input by 2D convolution, followed by a residual MLP.
- •
  TimeMosaic adapts patch size to the information density of each input
  region and uses segment-specific prompts and linear heads for
  forecasting.
- •
  PHAT buckets each variable by FFT-derived phase and cycle, with
  positive–negative attention per bucket.
- •
  EMAformer augments variate tokens with channel, cycle-phase, and joint
  channel–phase embeddings.

References for these methods are listed in
§[4.1](#S4.SS1 "4.1 Experimental Setup ‣ 4 Experiments ‣ TSFLAB: A Self-Improving Agent-Agnostic Workbench for Time Series Forecasting Research").

This task therefore measures the combined benefit of available method
implementations and the experiment workflow; method availability differs
across codebases. The fixed protocol is:

- •
  Data. Chronological 70/10/20 split; train-only scaling; all channels;
  input 168 and horizon 24.
- •
  Training. Paper or official-code architecture settings; at most ten
  epochs; validation early stopping with patience 3; batch size 32; seed
  42.
- •
  Evaluation. Every test window (stride 1); MSE and MAE on the
  normalized scale.
- •
  Budget. Six hours per session, including environment installation.

### D.5 Method Development Pilot

On ETTh1 and Weather, the agent searches for a method on validation data
under a fixed protocol:

- •
  Data. All channels; input 336; horizon 192; train-only
  standardization; seed 2021.
- •
  Training. MSE loss; Adam, lr $`10^{-3}`$; at most ten epochs; patience
  3; best-validation checkpoint.
- •
  Selection. Validation-only candidate selection; the frozen method’s
  saved checkpoint is tested once.
- •
  Budget. 90 minutes; two GPUs; at most 12 fits and four search

### D.6 Evaluation Metrics

Completion. For reproduction and the ablations, Completed counts
accepted sessions out of $`N`$ ($`x/N`$). A script first checks that
every required output exists. Two read-only reviewer agents then answer
a fixed checklist: where the split is made, where scaling statistics are
fitted, which data select checkpoints, whether every test window is
evaluated, and whether reported values come from executed runs; a third
reviewer decides disagreements. A session is accepted if it covers the
complete requested matrix with executed metrics, the prescribed splits,
train-only scaling, the common evaluation over all windows, and no
test-informed configuration selection; agreement with the paper’s MSE is
evaluated separately and is not an acceptance threshold. For
benchmarking, Completed counts accepted method–dataset results out of 48
(eight methods, two datasets, three attempts). A result is accepted if
its MSE and MAE are finite, the reviews (after any tie-break) support
the protocol, the code implements the method’s defining mechanisms, and
the metrics have execution evidence in the run records.

Accuracy. For $`W`$ test windows, horizon $`H`$, and $`C`$ channels on
the normalized scale,

|  |  |  |
|----|----|----|
|  |
``` math
\mathrm{MSE}=\frac{1}{WHC}\sum_{w,h,c}\big(\hat{y}_{w,h,c}-y_{w,h,c}\big)^{2},\quad\mathrm{MAE}=\frac{1}{WHC}\sum_{w,h,c}\big|\hat{y}_{w,h,c}-y_{w,h,c}\big|.
``` |  |

The relative error of a reproduced result is
$`\epsilon=100\,|\mathrm{MSE}_{\mathrm{run}}-\mathrm{MSE}_{\mathrm{paper}}|/\mathrm{MSE}_{\mathrm{paper}}`$.

Cost. For a setting with attempts $`s\in S`$ and $`n`$ completed
outcomes,

|  |  |  |
|----|----|----|
|  |
``` math
\mathrm{Time}=\frac{1}{n}\sum_{s\in S}T_{s},\quad\mathrm{Tokens}=\frac{1}{n}\sum_{s\in S}K_{s},\quad\mathrm{Calls}=\frac{1}{n}\sum_{s\in S}A_{s},
``` |  |

where $`T_{s}`$ is wall time, $`A_{s}`$ the number of agent tool calls,
and $`K_{s}`$ the fresh tokens of attempt $`s`$: non-cached input,
cache-write input, and output, excluding cache reads. $`S`$ includes
failed attempts. For reproduction, $`n`$ counts accepted sessions; for
benchmarking, it counts accepted method–dataset results. These
denominators differ, so costs are compared within each task. The
method-intake analysis separately reports tokens including cache reads,
as stated in the main text.

Code changes. Let $`F_{0}`$ and $`F_{1}`$ be the functions of the
initial and final source of a session and $`\mathrm{CC}(f)`$ the
cyclomatic complexity of $`f`$ (Radon 6.0.1), with
$`\mathrm{CC}_{0}(f)=0`$ for $`f\notin F_{0}`$. Cyclomatic complexity
counts independent execution paths through a function; conditionals and
loops typically increase it. Then

|  |  |  |
|----|----|----|
|  |
``` math
\Delta\mathrm{LOC}=L^{+}-L^{-},\quad\Delta\mathrm{Funcs}=|F_{1}\setminus F_{0}|,\quad\Delta\mathrm{CC}=\sum_{f\in F_{1}}\max\big(0,\mathrm{CC}_{1}(f)-\mathrm{CC}_{0}(f)\big),
``` |  |

where $`L^{+}`$ and $`L^{-}`$ are added and removed Python source lines.
The source includes experiment scripts and excludes official
repositories cloned into the workspace, installed environments, and
generated run records. Code metrics are averaged over sessions within
each task and then across tasks with equal weight.
````
