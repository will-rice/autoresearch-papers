###### Abstract

Long horizon agentic tasks are now pushing LLM agents past their context
window. To continue the task, the agent scaffold has to free up the
context window, a process known as _context compaction_. Compaction is
generally lossy by design: agents can silently lose task constraints,
instructions, or their reasoning behind earlier decisions. Although
compaction is a standard component of coding agent scaffolds, it has not
been studied systematically with frontier models on realistic, long
horizon agentic tasks. Previous work evaluate smaller open weight models
on toy or synthetic trajectories. We fix the agent scaffold (OpenCode),
implement five compaction strategies inside it, and evaluate three
frontier models on three long horizon benchmarks (PaperBench,
ProgramBench, PostTrainBench). For the two 1M context models, the
compaction threshold does not measurably affect the task performance,
whereas GPT-5.3-Codex, the model with the smallest context window,
performs worse at lower thresholds on PaperBench and, less clearly, on
PostTrainBench. No compaction method outperforms default
self-summarization, and methods that discard more content cost some
models up to 20 points while leaving other models the same. Compaction
can, however, silently remove task constraints: on ProgramBench, the
first compaction summary already drops about one third of the task’s
anticheating rules on average, and this rises monotonically with the
number of compactions. On real user-agent sessions from SWE-chat,
instructions about how the agent should work and what it should not do
are dropped around 6 times more than specifications of what to build. We
argue that current benchmarks are _compaction-friendly_: i.e., the
objective is fixed and the agent’s progress stays on disk, so most of
what compaction discards can be recovered, except constraints that don’t
exist anywhere else.

## 1 Introduction

LLM agents can now run for multiple hours on a single task autonomously.
For example, a single run of PostTrainBench ([Rank et al.,
2026](#bib.bib4)) or ProgramBench ([Yang et al., 2026](#bib.bib3))
produces on average several hundreds of thousands of tokens, more than
many LLMs’ context windows. Widely used agent scaffolds like Claude
Code, Codex CLI, Gemini CLI, Cursor, OpenHands, and OpenCode mostly
handle this with some form of summarization: when the context is near
the limit, the scaffold asks a model to summarize the work so far,
discards the current context, and continues from the summary ([Cassano
and Rush, 2026](#bib.bib12); [Anthropic, 2026a](#bib.bib9); [Smith,
2025](#bib.bib24); [OpenCode contributors, 2026](#bib.bib8)). This
process is called _context compaction_.

Most compaction methods are lossy by design. If the summary removes
something, the agent can then lose task constraints, certain
instructions, or the chain of thought behind previous decisions. This
raises two questions: can the agent still solve the task, and does it
still respect the rules it was given? Previous works have shown that
constraints specified by the user often do not survive compaction ([Wang
et al., 2026](#bib.bib1)). Other work compares compaction with other
context management methods on downstream accuracy, but on long context
question answering or web search, where the long input is given upfront
([Zhang et al., 2025](#bib.bib16); [Wu et al., 2025](#bib.bib25); [Sun
et al., 2025](#bib.bib26)). However, none of these studies measure the
downstream effect of compaction on realistic long horizon agentic tasks
with frontier models, where the context is generated by the agent
itself.

When designing an agent scaffold we therefore lack basic answers to
questions like: does the compaction threshold (the number of tokens at
which compaction is triggered) matter? Does the compaction method
matter? Can a cheaper model write the summary? Does compaction remove
the constraints that make it safe to run an agent autonomously for a
long time? To the best of our knowledge, no prior work has answered
these questions with frontier agents on realistic long-horizon
benchmarks.

##### This paper.

We organize our work around these questions, which we answer with
controlled experiments. We use the OpenCode as our fixed agent scaffold,
a popular open source agent scaffold, so that we can separate the effect
of the compaction strategy from that of the scaffold. We implement five
compaction methods inside it and evaluate four frontier models (Claude
Opus 4.6, GPT-5.3-Codex, GPT-5.4, Gemini 3.1 Pro Preview) on three long
horizon agentic benchmarks: PaperBench ([Starace et al.,
2025](#bib.bib2)), ProgramBench ([Yang et al., 2026](#bib.bib3)), and
PostTrainBench ([Rank et al., 2026](#bib.bib4)). We find:

## 2 Background and related work

### 2.1 Context compaction in agents

When an agent’s message history nears the context window limit, the
scaffold replaces older history with a shortened version. In practice
this is usually _self-summarization_: the model is prompted to write a
summary of its progress, and a fresh context is initiated with that
summary ([Cassano and Rush, 2026](#bib.bib12); [Anthropic,
2026a](#bib.bib9)). Most agent scaffolds differ in how they trigger it
(typically some fraction of the context window, usually 90-95%), in the
summarization prompt, in what they preserve as is e.g., recent turns or
current files and in other methods that complement summarization such as
clearing old tool calls. Anthropic’s API exposes the same primitives
server side, summarization (compact) and clearing of old tool results
and thinking blocks (clear_tool_uses, clear_thinking) ([Anthropic,
2026a](#bib.bib9); [Anthropic, 2026b](#bib.bib10)), and reports that
tool result clearing alone improved an internal agentic search
evaluation by 29% ([Anthropic, 2025](#bib.bib11)).

Model developers have also started to treat compaction as both a
training time and test time matter. Cursor trains Composer with self
summarization inside the reinforcement learning environment loop
([Cassano and Rush, 2026](#bib.bib12)). ReSum finetunes a separate
summarization model and adapts the agent to reasoning conditioned on the
summary with RL ([Wu et al., 2025](#bib.bib25)); MemAgent trains a model
with RL to maintain a fixed length memory while reading long inputs ([Yu
et al., 2026](#bib.bib28)). DeepSeek-V3.2 compares compaction strategies
as a way of expanding test time compute beyond the model’s context
window ([DeepSeek-AI, 2025](#bib.bib13), Section 4.4), and Kimi K2.5
compares compaction with subagent swarms as two ways of scaling long
horizon work ([Kimi Team, 2026](#bib.bib14), Section 5.2). SelfCompact
([Li et al., 2026](#bib.bib15)) is a harness that lets the model itself
decide on when and how to compact. Context-Folding ([Sun et al.,
2025](#bib.bib26)) is a framework that also allows agents to manage
their own context, by procedurally branching into a sub trajectory and
fold the steps into a summary after completion. In AgentFold ([Ye et
al., 2026](#bib.bib27)), the agent learns to condense and fold its
context as it progresses in the task. Recursive Language Models ([Zhang
et al., 2025](#bib.bib16)) on the other hand avoid compaction of the
input altogether: the prompt is loaded as a variable in a REPL
environnment, which the model inspects with code and recursively queries
itself over.

### 2.2 Evaluating compaction

Most work that evaluates compaction measures what is retained after
compaction rather than the downstream task performance. COMPINT  [Wang
et al. (2026)](#bib.bib1) showed that user constraints like “do not
delete any emails until I confirm” survive compaction around about 17%
of the time. However, they evaluate mostly open weight models with
around 128-140K context windows and simulate compaction by truncating
the trajectories at 100K tokens. There are some prior works on
downstream performance comparisons on question answering and web search.
For example RLMs ([Zhang et al., 2025](#bib.bib16)) outperformed a
compaction agent (on GPT-5) and Context-Folding ([Sun et al.,
2025](#bib.bib26)) outperformed summarization based methods. Although,
in these cases the long input was given to the agent upfront. We however
ask if compaction affects downstream performance on realistic long
horizon agentic tasks where the context is produced by the agent itself.

### 2.3 Relation to KV cache compression and long context degradation

Compaction is also related to work on reducing the key-value cache.
Works like heavy hitter eviction ([Zhang et al., 2023](#bib.bib18)),
attention sinks ([Xiao et al., 2024](#bib.bib19)), and query-aware
selection ([Li et al., 2024](#bib.bib20)) all talk about which previous
tokens to keep and treat the model as a black box. In prompt level
compaction, the model itself generates the summary, a compact
representation of the state, so what remains is a function of the
model’s own judgment. Our experiments on the compaction thresholds are
also related to long context degradation: i.e. models generally underuse
information that’s in the middle of the context window, shown by [Liu et
al. (2024)](#bib.bib21) and their performance degrades with the input
length even when relevant information is present ([Hong et al.,
2025](#bib.bib22)).

## 3 Experimental setup

### 3.1 Models and scaffold

We use OpenCode ([OpenCode contributors, 2026](#bib.bib8)) as our fixed
agent scaffold in all our experiments. OpenCode is a popular opensource
agent harness that supports many LLM providers. Fixing the scaffold
allows us to separate the effect of the compaction method from scaffold
specific behaviour such as tool formats, retry logic, system prompts,
etc. We implement each compaction strategy inside OpenCode as a
replacement for its default compaction logic. We evaluate Claude Opus
4.6, GPT-5.3-Codex, GPT-5.4 and Gemini 3.1 Pro Preview (details in
Table [1](#S6.T1 "Table 1 ‣ 6.1 Details on the models ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly"),
Appendix [6.1](#S6.SS1 "6.1 Details on the models ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
We include GPT-5.3-Codex, which is an older model with a 400K context
window, to compare models with a 1M context window versus one with a
smaller one. We run two runs per task and configuration.

### 3.2 Benchmarks

We selected benchmarks that are unsaturated, long enough that compaction
is triggered naturally within a run, and reflect real world agentic use:
reproducing research, developing software from scratch, and running ML
experiments. More details are in
Appendix [6.2](#S6.SS2 "6.2 Details on the benchmarks ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly").

PaperBench ([Starace et al., 2025](#bib.bib2)) evaluates an agent’s
ability to replicate ICML 2024 papers from scratch. Given the paper and
a document of author clarifications, the agent must produce a repository
containing everything required to reproduce the paper’s empirical
results. It may browse the internet but may not consult the authors’
code or other replications. Of the 20 papers, we evaluate on three
randomly chosen ones: adaptive-pruning ([Zhao et al.,
2024](#bib.bib32)), all-in-one ([Gloeckler et al., 2024](#bib.bib33)),
and bam ([Cai et al., 2024](#bib.bib31)).

ProgramBench ([Yang et al., 2026](#bib.bib3)) evaluates an agent’s
ability to build software from scratch. Given an execute only reference
binary and its documentation, the agent must produce source code and a
build script that reproduces the program’s behavior, which is checked by
a suite of tests. The task prompt states three rules for how the agent
may build its implementation: (1) it must not copy or vendor the
reference implementation’s source or binary into the submission, (2) it
must not access the internet, in particular to download the reference’s
source, and (3) the implementation must be original, not derived from or
wrapping the reference. These rules appear in the first user message, so
after a compaction they remain in the agent’s context only if the
summary restates them. This makes ProgramBench our testbed for
constraint erosion and reward hacking
(Section [4.2](#S4.SS2 "4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
We evaluate on two tasks that consist of reimplementing real open-source
command-line tools: Canop/broot (an interactive terminal file-tree
navigator in Rust), and jarun/nnn (a fast and lightweight terminal file
manager in C). They were chosen to be moderately difficult (so that
degradation is observable) and because reward hacking is less frequent
on them than on other tasks.

PostTrainBench ([Rank et al., 2026](#bib.bib4)) tasks agents with
post-training a small base LLM on a single H100 under a 10 hour limit,
with full freedom over data and methods, and with an LLM judge enforcing
that the agent does not train on test data or swap the model. Running
the full benchmark is compute heavy, so we evaluate on two base models
(gemma-3-4b-pt, Qwen3-4B-Base) and three target benchmarks (GPQA ([Rein
et al., 2023](#bib.bib6)), GSM8K ([Cobbe et al., 2021](#bib.bib7)), and
BFCL ([Patil et al., 2025](#bib.bib35))). We select these combinations
because agents achieve the highest baseline scores on them, which leaves
the most room to observe degradation due to compaction.

### 3.3 Compaction strategies

All strategies are implemented in OpenCode and share the same trigger²²
2 Code is available at: . We set a maximum number of tokens allowed
before compaction. After each assistant turn, OpenCode compares the
number of tokens used up until now against that budget and triggers
compaction (or pruning) once the usage reaches it. A lower threshold
triggers compaction earlier, and a higher threshold lets the session use
more tokens before compacting.

Self-summarization (baseline). When the threshold is reached, a user
prompt asks the agent to summarize its previous work (full prompt in
Appendix [6.4](#S6.SS4 "6.4 Prompts ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
The summary is placed in a fresh context together with the system prompt
and an instruction to continue. This is the default in most scaffolds
([Anthropic, 2026a](#bib.bib9); [OpenAI, 2026](#bib.bib23); [Smith,
2025](#bib.bib24)) and is our baseline. Unless stated otherwise, the
summary is written by the same model that performs the task.

Tool-output pruning. This method runs after every assistant turn and
does not call the model. In a backwards fashion through the message
history, it keeps the last user-assistant turn and enough recent tool
outputs to fill a safe token budget (40K by default). Older tool call
outputs are discarded, the tool name and arguments remain but the output
is replaced with the placeholder“\[Old tool result content cleared\]”.
Pruning only runs if it would free at least 20K tokens and is used
together with self-summarization. Anthropic’s server-side equivalent,
clear_tool_uses, is reported to improve performance on an internal
agentic-search evaluation by 29%([Anthropic, 2025](#bib.bib11)).

Filesystem offloading. Self summarization is lossy: details the summary
removes cannot be recovered. This method keeps the default
self-summarization but also writes a copy of the context to disk before
compacting. When compaction is triggered, the full message history
(including the system prompt, user and assistant messages, and all tool
calls with their outputs) is serialized into a JSON file. The subsequent
summary states where the copy is saved, so the agent can read it later,
if needed.

Reasoning block discarding (clear thinking). When the context overflows,
the reasoning (“thinking”) blocks from previous assistant turns are
removed from the message history before summarizing. The summarizer thus
only sees the remaining conversation and tool calls.

Small-model summarization. Identical to the baseline except that the
summary is written by Claude Haiku 4.5, a smaller and cheaper model.

Decomposing a task across subagents with their own independent contexts
is also an alternative to compaction. We leave it to future work
(Section [5](#S5 "5 Discussion and conclusion ‣ Benchmarks Are Surprisingly Compaction-Friendly")).

### 3.4 Metrics and statistics

For each run we record the performance (rubric score for PaperBench,
fraction of tests passed for ProgramBench, and target benchmark
performance for PostTrainBench), the number of compaction events,
whether the run failed or whether the run violated the task’s rules
(specifically for ProgramBench). For ProgramBench we also judge the
compaction summary and agent trajectory with Claude Sonnet 5. The judge
reports which of the three categories of the disallowed behavior are
absent from it, which we call constraint erosion. Error bars are
nonparametric bootstrap 95% confidence intervals: we resample runs with
replacement and report the 2.5th and 97.5th percentiles of the resampled
mean.

## 4 Results

We organize the results around the questions in the introduction,
grouped by whether they concern task performance
(Section [4.1](#S4.SS1 "4.1 Does compaction matter for task performance? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly"))
or what compaction removes from the agent’s context
(Section [4.2](#S4.SS2 "4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Each question opens with the finding, followed by the evidence and the
caveats.

### 4.1 Does compaction matter for task performance?

##### Q1: How does the compaction threshold affect performance?

For the two 1M context models (Claude Opus 4.6 and GPT-5.4), accuracy is
similar across the thresholds. GPT-5.3-Codex, compacted at the same
thresholds, performs worse at low thresholds on PaperBench, but not on
ProgramBench. PostTrainBench results are too variable to conclude from
them.

Scaffolds usually trigger summarization at around 90-95% of the window.
Compacting late risks underusing the task description and early
decisions ([Liu et al., 2024](#bib.bib21); [Hong et al.,
2025](#bib.bib22)). Compacting early means more compactions and more
chances to lose the reasoning behind earlier decisions. We vary the
compaction threshold from 160K to 380K tokens. For the 1M context models
this range covers 16-38% of the window, so it does not test compaction
near the scaffold default, for GPT-5.3-Codex it covers 40-95%.
Thresholds are not comparable across models because compaction frequency
depends on how fast each model’s context grows.

Figure [2](#S4.F2 "Figure 2 ‣ Q1: How does the compaction threshold affect performance? ‣ 4.1 Does compaction matter for task performance? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")
shows accuracy conditional on producing a valid submission against the
number of tokens before compaction. Claude Opus 4.6 and GPT-5.4 perform
similarly across thresholds. Gemini is consistent but rarely compacts,
so it’s uninformative here
(Appendix [6.6](#S6.SS6 "6.6 Results for Gemini 3.1 Pro Preview on PaperBench ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
On PaperBench, GPT-5.3-Codex goes from 0.38 at 160K to about 0.60 at
260K and above, where it matches the other models. On ProgramBench it
remains generally flat. On PostTrainBench, error bars are wide and
overlap across all thresholds for every model, so we can’t conclude
whether the threshold affects performance on this benchmark.

##### Q2: Does the compaction strategy matter?

No strategy beats default self-summarization. Removing reasoning blocks
and summarizing with a smaller model cost some models up to 20 points on
PaperBench and leave others unaffected.

Figure [3](#S4.F3 "Figure 3 ‣ Q2: Does the compaction strategy matter? ‣ 4.1 Does compaction matter for task performance? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")
compares the compaction strategies in
Section [3.3](#S3.SS3 "3.3 Compaction strategies ‣ 3 Experimental setup ‣ Benchmarks Are Surprisingly Compaction-Friendly")
at a threshold of 160K tokens before compaction. On all three
benchmarks, no strategy is better than the baseline beyond the
confidence intervals. Tool output pruning stays close to the baseline on
PaperBench for all the models. Saving the previous context in a file,
which makes compaction ”lossless”, is also near the baseline on
PaperBench for the two 1M context models, but lowers GPT-5.3-Codex from
0.38 to $`\approx`$0.24. Removing reasoning blocks lowers PaperBench
accuracy from 0.59 to 0.43 for GPT-5.4, but not for Claude Opus 4.6 or
GPT-5.3-Codex. On ProgramBench, varying strategy doesn’t significantly
affect performance on any of the models.

Can a smaller model be used for context summarization? For Claude Opus
4.6, summaries by Claude Haiku 4.5 give PaperBench accuracy within the
confidence interval of the baseline. For both OpenAI models they do not:
GPT-5.4 drops from 0.59 to 0.43 and GPT-5.3-Codex from 0.38 to 0.18.
Haiku 4.5 is from the same provider as Opus 4.6, so a shared provider
might explain the difference. [Zhang et al. (2025)](#bib.bib16) report
that GPT-5-nano summaries performed comparably to GPT-5 summaries on
BrowseComp-Plus ([Chen et al., 2025](#bib.bib34)), a task where the
input is given upfront.

And we didn’t run it on PostTrainBench because of limited compute and

### 4.2 What does compaction drop?

##### Q3: Does compaction erode task constraints?

Yes. On ProgramBench, the first compaction summary already drops on
average about one of the task’s three anti-cheating rules, and the loss
grows with the number of compactions.

The three rules in
Section [3.2](#S3.SS2 "3.2 Benchmarks ‣ 3 Experimental setup ‣ Benchmarks Are Surprisingly Compaction-Friendly")
appear in the agent’s context once and remain there only if the agent’s
compaction summary keeps them. They are dropped even though the
summarization prompt explicitly asks for “key user requests,
constraints, or preferences that should persist”
(Appendix [6.4](#S6.SS4 "6.4 Prompts ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Per compaction, GPT-5.3-Codex drops 2.73 of 3 categories and all three
in 80% of compactions. GPT-5.4 removes 1.76. Claude Opus 4.6 drops 0.51,
and never all three
(Table [3](#S6.T3 "Table 3 ‣ 6.9 Constraint erosion ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly"),
Appendix [6.9](#S6.SS9 "6.9 Constraint erosion ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Figure [4(a)](#S4.F4.sf1 "In Figure 4 ‣ Q4: Are current benchmarks compaction-friendly? ‣ 4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")
shows that about 0.92 categories are dropped at the first compaction,
1.93 by the 10th, 2.41 by the 15th and 2.65 by the 30th. Later summaries
are written from earlier summaries that had already lost the rules, and
nothing restates a rule that has been removed, so the loss compounds.
This is the incremental “update a running summary” workflow that [Chang
et al. (2024)](#bib.bib29) study for book-length summarization. [Zahn
and Chana (2026)](#bib.bib17) observe the same compounding effect under
cascading compaction on a fact retention benchmark.

Is constraint erosion related to reward hacking? In our runs, reward
hacking begins before the first compaction happens, so constraint
erosion cannot explain when an agent starts to cheat. An agent that is
already in the middle of a disallowed action may also have little
incentive to restate the rule, which would make reward hacking a cause
of erosion rather than a consequence.

##### Q4: Are current benchmarks compaction-friendly?

In real user-agent sessions, compaction keeps around 81% of user
constraints, but instructions about how to work and what not to do are
dropped about 6 times more often than specifications of what to build.

The benchmarks above have a fixed objective, run without user input, and
give the agent a filesystem. To see what compaction loses when a user
steers the agent we use SWE-chat ([Baumann et al., 2026](#bib.bib5)), a
dataset of real human-agent coding sessions with transcripts. We sampled
44 sessions with at least one compaction event and used an LLM to
extract the constraints the user gave before the compaction, which gave
269 constraints. An LLM judge then labeled each constraint as preserved
or dropped in the next compaction summary. Finally, we assigned each
constraint to one of 7 categories, using a taxonomy we built by reading
a sample of constraints, with a separate LLM judge doing the
classification
(Appendix [6.11](#S6.SS11 "6.11 SWE-chat analysis ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Overall 81% of constraints are preserved and 19% dropped (24.5% under a
different judge from a different model family).
Figure [4(b)](#S4.F4.sf2 "In Figure 4 ‣ Q4: Are current benchmarks compaction-friendly? ‣ 4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")
shows that the loss depends on the category. Feature requirements, the
biggest category (35.7% of constraints), are lost 6.2% of the time,
whereas _process instructions_ (how the agent should work rather than
what it should do) are lost 35.9% of the time and _scope exclusions_
(what should not be done or touched) 36.8% of the time. This is the
pattern our compaction-friendly hypothesis predicts. Constraints that
describe the deliverable can be recovered from the agent’s own
artifacts, however constraints that describe how the agent should behave
cannot. The ProgramBench anti-cheating rules of Q3 belong to the second
kind: they state what the agent must not do.

(a) ProgramBench: task constraints are lost as compactions accumulate.
Mean number of constraint categories dropped (out of 3) per compaction

## 5 Discussion and conclusion

##### Does the compaction method matter?

Based on our experiments, the answer is: it depends on what is measured
and what is run. For task performance on benchmarks with fixed
objectives and persistent files, Claude Opus 4.6 and GPT-5.4 are not
very sensitive to when compaction occurs
(Section [4.1](#S4.SS1.SSS0.Px1 "Q1: How does the compaction threshold affect performance? ‣ 4.1 Does compaction matter for task performance? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Gemini 3.1 Pro Preview rarely compacted in our runs, so it is
uninformative on this question
(Appendix [6.6](#S6.SS6 "6.6 Results for Gemini 3.1 Pro Preview on PaperBench ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")),
and the default self summarization is as good as any alternative methods
we tried
(Section [4.1](#S4.SS1.SSS0.Px2 "Q2: Does the compaction strategy matter? ‣ 4.1 Does compaction matter for task performance? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
However, our results do show that compaction methods that discard more,
such as dropping reasoning or using a smaller model for the summary, can
reduce the downstream performance by up to 20 points for some models
while not changing it for other models. Furthermore, even if the
compaction doesn’t change the performance metric on the benchmark, it
can still silently remove the rules and constraints the agent was given
(Section [4.2](#S4.SS2.SSS0.Px1 "Q3: Does compaction erode task constraints? ‣ 4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
The compaction summaries usually keep what the agent needs to continue
to do to complete the task, which is what the benchmark score measures.
But the summaries are more likely to drop the constraints on how to do
the task, which the benchmark score does not necessarily measure.

##### Why current benchmarks are compaction friendly.

In benchmarks like PaperBench, ProgramBench and PostTrainBench, the
objective is fixed and given once, while the agent’s progress can
persist on disk (with files and artifacts). Thus, after compaction the
agent can recover almost everything it needs by just re-reading these
artifacts. In the language of [Goldman et al. (2024)](#bib.bib30), the
information an agent needs from its earlier context is small in scope
and easy to find. [Zhang et al. (2025)](#bib.bib16) show the opposite
however: a compaction agent built on GPT-5 scores 70.5 on
BrowseComp-Plus but 0.1 on OOLONG-Pairs, a task whose answer depends on
almost every line of the input. Interactive user sessions are closer to
the second type for one kind of information. The user can add or change
instructions as the session grows, and most of this is never persistent
anywhere, so a summary that removes an instruction is not able to
restate it after. Q4 measures how much of this is lost on real sessions,
but not its effect on the final outcome.

##### Capability or benchmark artifact?

GPT-5.3-Codex is the only model whose PaperBench score depends on the
threshold. Models don’t compact at the same frequency (see
Appendix [6.8](#S6.SS8 "6.8 Number of compactions per threshold ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")),
but frequency alone doesn’t explain the drop we observe with
GPT-5.3-Codex. When we aggregate runs by number of compactions (see
Appendix [6.5](#S6.SS5 "6.5 Accuracy across compactions ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")),
Claude Opus 4.6 and GPT-5.4 show no relationship between compactions and
accuracy, and GPT-5.4 does not degrade even with 16 or more compactions,
while GPT-5.3-Codex declines from about 8 compactions onward, and loses
roughly 0.10 relative to the task mean at 16 or more. GPT-5.3-Codex
therefore seems to be more fragile to repeated compaction than GPT-5.4.
Two explanations remain: newer models may write better summaries and
orient themselves better after a compaction, the erosion results fit
this for constraints (Codex drops 2.73 of 3 rules per compaction against
0.51 for Opus 4.6,
Table [3](#S6.T3 "Table 3 ‣ 6.9 Constraint erosion ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
Alternatively, models trained with a 1M context length may have been
trained on more post compaction continuations. We cannot separate these,
if the first holds, compaction would matter less as models improve, at
least on tasks of this kind. On ProgramBench, where the agent’s state is
almost fully externalized in files, Codex is flat across thresholds,
which suggests benchmark structure matters as much as the model.

##### Why constraints are dropped first.

We hypothesize that when the model writes a compaction summary, it
optimizes for what it needs to continue the task. Task constraints are
not necessarily needed to continue, only to continue correctly. Our
summarization prompt explicitly asks for constraints that should persist
(Appendix [6.4](#S6.SS4 "6.4 Prompts ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")),
and they are dropped anyway. The SWE-chat results also make the same
point from the user’s side: what to build next, while how to work and
what not to do often do not
(Section [4.2](#S4.SS2.SSS0.Px2 "Q4: Are current benchmarks compaction-friendly? ‣ 4.2 What does compaction drop? ‣ 4 Results ‣ Benchmarks Are Surprisingly Compaction-Friendly")).

##### Future work.

Decomposing a long task across parallel subagents with their own fresh
contexts, like in agent swarms ([Kimi Team, 2026](#bib.bib14)) can avoid
compaction of the main agent’s context. Comparing this with the best
compaction method under the same scaffold would tell us whether
compaction is worth engineering around at all. A harder evaluation of
compaction needs tasks whose constraints are not recoverable from the
filesystem, such as multi-turn sessions with user instructions that
change over time.

##### Limitations.

We evaluate four models, three benchmarks and a few tasks per each
benchmark due to cost and compute constraints. We fix one scaffold,
other scaffolds may use different summarization prompts or memory
systems that may behave differently. Gemini 3.1 Pro Preview’s rarely
triggers compaction on our setup, its context grows slowly, few runs
reach compaction, and it reward hacked a lot on ProgramBench. Thus its
results are weak evidence about compaction. The SWE-chat sessions were
produced with Claude Code, a different scaffold from our experiments,
with different underlying models.

### 6.2 Details on the benchmarks

PaperBench ([Starace et al., 2025](#bib.bib2)). Agents are run in a
container with a single GPU. Because agents tend to stop early, we
follow the original paper’s _IterativeAgent_ variant: when the model
produces a message without any tool call, the scaffold appends a message
telling the agent to take the next step toward replicating the paper, to
prioritize the most important parts of the paper first, and that it has
plenty of time left. We use a 10 hour time limit: [Starace et al. (2025,
Fig. 3)](#bib.bib2) show that scores mostly plateau within the first
hours of a 36 hour run. Because full grading requires executing the
submission and is expensive, we use the _Code-Dev_ variant, which skips
the reproduction step and grades only the “Code Development” leaves of
the rubric. Each rubric is a tree that hierarchically decomposes the
outcomes required for a replication, with manually weighted nodes; an
LLM judge then grades each leaf as pass/fail and scores propagate up the
tree. We use gpt-4o-mini as the judge. We evaluate on three tasks:

- •
  bam refers to the “Batch and Match” method, a black-box variational
  inference method that replaces the usual ELBO-gradient optimization
  with a closed-form proximal update based on a score-matching
  divergence.
- •
  adaptive-pruning refers to APT, a method that adaptively prunes and
  tunes a pretrained language model’s parameters during fine-tuning
  (rather than after) so it retains most of the task performance, as
  well as speeding up training, and reducing inference cost.
- •
  all-in-one refers to the Simformer, a diffusion-transformer-based
  amortized simulation-based-inference method that, unlike prior
  approaches, doesn’t need a fixed prior/simulator/task specified in
  advance and can sample arbitrary conditional posteriors/likelihoods
  from simulator-based models.

ProgramBench ([Yang et al., 2026](#bib.bib3)). Following the original
paper, agents get 20 CPUs, 120GiB of RAM and 6 hours. We report the
fraction of tests passed, which the original authors recommend for
relative comparisons since no model fully resolves most tasks.

PostTrainBench ([Rank et al., 2026](#bib.bib4)). We reuse the same
settings as in the original implementation. We exclude from the main
results runs flagged with a rule violation.

### 6.3 Details on the compaction strategies

Reasoning block discarding (clear thinking). When the context overflows,
the reasoning (“thinking”) blocks from previous assistant turns are
removed from the message history before summarizing. The summarizer thus
only sees the remaining conversation and tool calls. All reasoning parts
older than the last k assistant turns from the replayed prompt, together
with their provider metadata. We set k to 10 in our experiments. For
OpenAI this removes the reasoning items and their encrypted_content. For
Anthropic it removes thinking and redacted_thinking blocks and their
signatures. For Gemini, it removes the thought-summary parts and the
thoughtSignature.

1. The compaction summary text an agent generated to replace everything

1. First write out your reasoning in the ‘reasoning‘ field: quote or
   paraphrase the relevant part of the summary (if any), and explicitly

a single constraint that a user gave a coding agent during a session.

alone.

Pick exactly one category from this fixed taxonomy:

\- scope_exclusion: A rule that bounds what may or may not be changed or
done: either negative (’don’t touch X’, ’X is out of scope’, ’keep Z
as-is’) or ”an affirmative limit (’only modify X and Y’).

\- technical_parameter: A specific literal value: an exact number,
config value, type signature, file path, or enumerated list (timeouts,
ports, exact function or field names, a checklist of items, a
symbol-to-file mapping).

\- feature_requirement: A concrete specification of something to build
or how it should behave (add this UI element, show this fallback chain,
warn under this condition, create this interface) that is not merely a
bare literal value, a working-method instruction, or a scope boundary.

\- process_instruction: An instruction about how the agent should go
about its work rather than about what is to be built: split the work
into todos, work sequentially, use a particular editing approach, pause
for review between phases, proceed autonomously, commit in a particular
way.

\- named_source_or_tool: A requirement to use a specific named tool,
document, or source (a particular CLI, reference paper or spec file,
skill, or library).

\- structural_convention: A formatting, ordering, or structural rule
(keep section X last, preserve the original section order, perform this
check before that one, use this exact mapping between labels and
values).

\- soft_preference: A subjective preference about tone, depth, or style
of communication (comfortable with detail, prefers concise answers)
rather than a requirement on the deliverable.

\- other: Fits none of the categories above. Use sparingly and say why
in the reasoning.

   reasoning if relevant.

3. Give a ‘confidence‘ of high/medium/low for your own category choice.

Categorize each item independently – don’t let one item’s category
choice bias another’s.

### 6.10 Reward hacking

Models use different strategies to reward hack. We used Claude Sonnet 5
to classify the reward hacked trajectories into different types. We
distinguish between seven categories of reward hacking:

- •
  Vendored source. The agent downloads or copies the real upstream
  project’s source code (via git clone, curl, apt-get source, a tarball,
  etc.) and builds it directly instead of writing an original
  implementation.
- •
  Runtime exec delegation. The submission ships a thin wrapper that, at
  runtime, execvs the reference binary so the “implementation” is really
  just a pass-through to the real program.
- •
  Obfuscated binary smuggling. The agent extracts the reference binary
  itself (via ptrace, memory-dump, ELF reconstruction, LD_PRELOAD
  hooking, etc.), then disguises or encodes it (XOR, memfd_create, a
  compressed/encrypted payload blob) to slip it past the hash-based
  anti-copy check.
- •
  Language-contract violation. The agent implements the task in a
  different language than required (e.g. Python) and hides it behind a
  thin wrapper in the required language (e.g. a Rust or C shim) so it
  looks compliant on the surface.
- •
  Precompiled binary vendoring. The agent links or bundles a precompiled
  reference library/binary directly into the build rather than compiling
  from an original implementation.
- •
  Reference consultation. The agent looks up the real upstream source
  online for guidance during a nominally from-scratch reimplementation,
  without wholesale copying: a softer, more ambiguous violation than
  outright vendoring.
- •
  Memorized reproduction. With no network access involved, the agent
  reproduces the upstream project’s source structure and exact filenames
  from what looks like memorized training data rather than genuine
  reimplementation.

Our reward hacking analysis includes runs on additional tasks: lua and
luajit. We excluded them from the main analysis on accuracy because they
are very often reward hacked.

The 3 constraints labeled as contradicted are counted as dropped
(Appendix [6.4](#S6.SS4 "6.4 Prompts ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")).
To see which constraints are most at risk, we manually read a sample of
the constraints and constructed a taxonomy of 8 constraint categories
(below) and used an LLM judge to classify each of the 269 constraints
into one category. We replicate the two stage classification with a
second judge from a different model family (GPT-5.6 Sol) as well.

Results. Compaction summaries preserve the most constraints: 81% are
preserved and 19% dropped. Feature requirements, which is the largest
category (96/269, 35.7%), are preserved 93.8% of the time. _Process
instructions_, which describe how the agent should work rather than what
it should build, are dropped 35.9% of the time, around $`6\times`$ more,
despite being a much rarer category (39/269, 14.5%). _Scope exclusions_
get dropped 36.8% of the time. Under the second judge, feature
requirements again have the lowest drop rate and process instructions
and scope exclusions remain much higher than the overall rate, but their
order is reversed
(Figure [11](#S6.F11 "Figure 11 ‣ 6.11.2 Judge comparison ‣ 6.11 SWE-chat analysis ‣ 6 Appendix ‣ Benchmarks Are Surprisingly Compaction-Friendly")),
and the overall loss rate is higher (24.5% vs. 19%).

#### 6.11.1 Constraint categories

- •
  Scope exclusion: A rule that bounds what may or may not be changed or
  done: either negative (“don’t touch X”, “X is out of scope”, “keep Z
  as-is”) or an affirmative limit (“only modify X and Y”).
- •
  Technical parameter: A specific literal value: an exact number, config
  value, type signature, file path, or enumerated list (timeouts, ports,
  exact function or field names, a checklist of items, a symbol-to-file
  mapping).
- •
  Feature requirement: A concrete specification of something to build or
  how it should behave (add this UI element, show this fallback chain,
  warn under this condition, create this interface) that is not merely a
  bare literal value, a working-method instruction, or a scope boundary.
- •
  Process instruction: An instruction about _how_ the agent should go
  about its work rather than about _what_ is to be built: split the work
  into todos, work sequentially, use a particular editing approach,
  pause for review between phases, proceed autonomously, commit in a
  particular way.
- •
  Named source or tool: A requirement to use a specific named tool,
  document, or source (a particular CLI, reference paper or spec file,
  skill, or library).
- •
  Structural convention: A formatting, ordering, or structural rule
  (keep section X last, preserve the original section order, perform
  this check before that one, use this exact mapping between labels and
  values).
- •
  Soft preference: A subjective preference about tone, depth, or style
  of communication (comfortable with detail, prefers concise answers)
  rather than a requirement on the deliverable.
- •
  Other: Fits none of the categories above (no constraint was assigned
  to it).

#### 6.11.2 Judge comparison

Overall agreement between the two judges is 88.8% (239/269), inflated by
the dominant preserved class. Cohen’s $`\kappa`$ is 0.681, substantial
but not perfect. Per-class agreement is 89.9% (196/218) for preserved,
84.3% (43/51) for dropped. dropped is where they diverge most: GPT-5.6
Sol calls dropped (22 cases) on constraints Sonnet judged preserved,
i.e. it is slightly stricter about what counts as preserved.
