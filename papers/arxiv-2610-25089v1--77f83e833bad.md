###### Abstract

Automated AI research agents aim to improve machine learning methods by
iteratively proposing, implementing, and evaluating candidate methods.
Existing work uses the outcome of each evaluation to determine how the
next candidate should be revised for performance improvement. However, a
candidate often combines multiple design decisions, and its overall
outcome alone does not reveal which decisions produced their expected
effects, whether their required conditions were satisfied, or which
decisions should be retained or revised. Inspired by ablation studies in
the machine learning community, we propose DAGLoop to test the expected
effect of a design decision by comparing implementations with and
without that decision while preserving the other decisions it requires.
Specifically, DAGLoop translates each design decision’s rationale into a
testable expectation and pairs it with a targeted experiment, forming an
experimental specification for assessing the expected effect under its
required conditions. Using these specifications, we formulate ablation
planning as the construction of a directed acyclic graph (DAG) from the
candidate method’s design: nodes associate decisions with tests, and
edges encode dependencies. The DAG specifies which decisions each
experiment must retain and supports joint tests when an expected effect
requires several decisions to act together. Outcomes are recorded with
the tested decisions, expectations, and conditions to form structured
research memory. This memory guides the agent in retaining
experimentally supported decisions, revising unsupported ones, and
planning further experiments when the evidence is unresolved.
Experiments on dozens of research tasks demonstrate substantial
performance improvements achieved by DAGLoop across diverse executable
research settings. Code and evaluation scripts are available at
[https://github.com/deng34567/DAGLoop](https://github.com/deng34567/DAGLoop).

## 1 Introduction

Improving a machine learning method requires repeated decisions about
what to change, what to test, and how to interpret the result. Recent
research agents automate this process by proposing candidate methods,
implementing them, running experiments, and using the outcomes to guide
subsequent revisions. MLAgentBench studies agents that conduct machine
learning experiments, while The AI Scientist extends automation to
longer research workflows and agentic tree search ([Huang et al.,
2024](#bib.bib1); [Lu et al., 2026](#bib.bib22); [Yamada et al.,
2025](#bib.bib3)). AlphaEvolve uses executable evaluators to guide
program and algorithm discovery ([Novikov et al., 2025](#bib.bib4)). We
study the executable method-improvement setting: given a research task,
a baseline, an experimental environment, and a finite budget, an agent
seeks to improve performance under a fixed task evaluator.

Experimental feedback determines which candidates the agent explores
next. Optimization by PROmpting (OPRO) generates candidates from scored
solutions; FunSearch selects evaluated programs for further search
([Yang et al., 2024](#bib.bib13); [Romera-Paredes et al.,
2024](#bib.bib14)). Richer feedback includes MetaReflection’s memory of
past reflections and Trace’s execution traces for parameter updates
([Gupta et al., 2024](#bib.bib26); [Cheng et al., 2024](#bib.bib17)).
Our focus is the relation between this feedback and the design decisions
being revised. A candidate may combine a data transformation, a
representation, an objective, and an optimization rule. Its overall
performance measures their combined effect, but does not establish which
decisions produced their expected effects or whether their required
conditions held. The evaluator scores the complete candidate, whereas
revision must determine which constituent decisions to retain, revise,
or test further.

Ablation studies examine decisions by comparing implementations with and
without them; recent benchmarks study whether language models can plan
informative ablations ([Zhao et al., 2025](#bib.bib25); [Abramovich and
Chechik, 2026](#bib.bib19)). However, testing each decision
independently can remove the conditions needed for its effect. Suppose
$`z_{1}`$ constructs a representation and $`z_{2}`$ introduces an
objective that uses it. The representation may provide a necessary
intermediate property without improving the task metric alone, while the
objective may be meaningless without it. Rejecting $`z_{1}`$ for lacking
standalone gain prevents a meaningful test of $`z_{2}`$; evaluating only
their composition leaves each decision’s contribution unresolved.
Decision-level evidence therefore requires experiments that preserve the
prerequisites of the decision being tested
(Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).

Figure 1: Why dependencies matter. Candidate-level feedback combines
decision effects, while independent tests can remove prerequisites.
DAGLoop preserves prerequisites in the control. Here $`M_{0}`$ is the
baseline, $`J_{q}`$ the task metric, and $`p_{1}`$ a property supplied
by $`z_{1}`$.

We present DAGLoop, a general-purpose research system that addresses
executable method-improvement problems through proposal, implementation,
experimentation, and revision. It constructs targeted experiments from a
candidate method’s design. For each decision, it translates the
rationale into a testable expectation: the effect the decision should
produce and its required conditions. A targeted experiment specifies
what to compare and measure, forming an experimental specification that
connects design reasoning to evidence. These specifications define a
DAG, whose nodes associate decisions with tests and whose edges encode
their dependencies. Each experiment compares a control implementation
containing the prerequisites with a treatment implementation that
additionally applies the decision: $`z_{1}+z_{2}`$ against $`z_{1}`$ in
the example. A decision that provides a prerequisite, such as $`z_{1}`$,
is assessed through the intermediate property it is intended to provide.
Effects requiring several decisions are tested jointly, retaining their
external prerequisites and attributing experimental support to the group
of decisions tested together.

After checking execution validity, DAGLoop records each outcome
alongside the decision, expected effect, required conditions, and saved
control implementation. This structured research memory guides the agent
to retain supported decisions, revise unsupported ones, and plan further
experiments when evidence is unresolved. Failed implementations provide
debugging information. Revised decisions are assembled into a subsequent
candidate and evaluated with the same official evaluator. Targeted
experiments guide revision; complete-candidate evaluation measures
improvement.

We evaluate DAGLoop on 36 AutoLab tasks spanning CPU optimization, CUDA
kernels, program synthesis, and model development ([Xu et al.,
2026](#bib.bib9)), comparing with Terminus-2 using the same language
model. Our contributions are threefold:

- •
  We identify a mismatch between evaluating complete candidates and
  revising individual decisions, motivating experiments that retain
  prerequisites for decision-level evidence.
- •
  We propose DAGLoop, a research system that translates design
  rationales into experimental specifications, constructs a dependency
  DAG to plan targeted ablations, and uses structured research memory to
  guide evidence-based revision and further experimentation.
- •
  Experiments on 36 AutoLab tasks demonstrate method improvement across
  diverse executable problems. DAGLoop achieves a mean score of 0.6459,
  compared with 0.5831 for Terminus-2 using the same language model,
  with higher means on both CPU and GPU tasks. Additional comparisons
  with reasoning disabled cover GLM-5.2 and DeepSeek-V4-Flash.

## 2 Method

DAGLoop organizes method proposal, implementation, experimentation, and
revision into a research loop. The system turns a candidate’s design
into experimental specifications, uses their dependencies to construct
targeted comparisons, and records the outcomes for revision
(Figure [2](#S2.F2 "Figure 2 ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).
The assembled candidate is evaluated by the official task evaluator.

Figure 2: DAGLoop research loop. Each DAG node represents a decision or
jointly tested group; $`S`$ denotes such a group. Control $`P_{i}`$
preserves prerequisites; treatment $`T_{i}`$ adds the change
$`\Delta_{i}`$. Their observations $`O_{i}^{-}`$ and $`O_{i}^{+}`$ enter
research memory and guide revision. Complete candidates are evaluated
separately by the task evaluator, with feedback returned for revision.

### 2.1 Task Setup and Experimental Specifications

Starting from the user’s research question, DAGLoop clarifies objectives
and constraints with the user, retrieves relevant literature, and
proposes a method. The user confirms the research direction and method.
With an executable baseline, evaluator, environment, and budget
established, the system proceeds to implementation, experimentation, and
revision.

An executable research task is

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \mathcal{T}=(q,M_{0},\mathcal{E},J_{q},B),
       ```                                         |     | (1) |

where $`q`$ describes the task, $`M_{0}`$ is an executable baseline,
$`\mathcal{E}`$ is the experimental environment, and $`B`$ is the
research budget. The official evaluator returns a raw (native) task
metric $`m_{q}(M)`$, such as accuracy or execution time, and a task
score $`R_{q}(M)`$. We define $`J_{q}`$ so that larger values indicate
better performance: $`J_{q}(M)=m_{q}(M)`$ for maximization tasks and
$`J_{q}(M)=-m_{q}(M)`$ for minimization tasks. The score $`R_{q}`$
follows the official reward rule, including its thresholds and clipping.

Let $`\tau`$ be the research trajectory, including proposals,
implementations, experiments, and revisions, and let
$`\mathcal{C}(\tau)`$ contain the complete executable candidates it
evaluates. We seek

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\widehat{M}(\tau)\in\arg\max_{\begin{subarray}{c}M\in\mathcal{C}(\tau)\cup\{M_{0}\}\\
M\ \text{passes the task checks}\end{subarray}}J_{q}(M),\qquad\operatorname{Cost}_{\mathcal{E}}(\tau)\leq B.
``` |  | (2) |

Task checks enforce correctness and task constraints. Cost includes
planning, implementation, targeted tests, repair, repeated measurements,
and final evaluation. Improvement means
$`J_{q}(\widehat{M})>J_{q}(M_{0})`$. The baseline remains available when
no evaluated candidate improves it.

A candidate method $`M`$ consists of design decisions
$`Z=\{z_{i}\}_{i=1}^{n}`$. The complete-candidate metric $`J_{q}(M)`$
evaluates their combined performance, whereas revision requires deciding
which $`z_{i}`$ to retain or change. To test the effect expected from a
particular decision, we associate it with an experimental specification
linking its rationale, expected effect, conditions, and test:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
s_{i}=(r_{i},e_{i},D_{i},x_{i}),\qquad x_{i}=(\Delta_{i},\rho_{i},o_{i},v_{i}),
``` |  | (3) |

where $`r_{i}`$ is the rationale, $`e_{i}`$ the expected effect, and
$`D_{i}`$ the required conditions. The experiment $`x_{i}`$ specifies
the implementation change $`\Delta_{i}`$, execution procedure
$`\rho_{i}`$, quantity to measure $`o_{i}`$, and validation rule
$`v_{i}`$. The specification defines the measurement and criterion
before execution; the experiment report supplies the observed value. A
decision can provide an intermediate property $`p_{i}`$ required by
another decision, with a corresponding property check.

Each node in the experimental DAG represents an executable component:
one decision or a group of decisions tested together. Each component has
an implementation and a specification. Tests assess either improvement
in the task metric or an intermediate property required by another
decision. We refer to these as *performance tests* and *property
checks*, respectively. A checkpoint stores the implementation and
artifacts needed to reconstruct a control or candidate.

#### From a rationale to a test.

In the representation–objective example, the rationale for $`z_{1}`$
identifies a property $`p_{1}`$ needed by $`z_{2}`$. Its specification
makes that property the expected effect and selects an observable that
checks whether the representation supplies it. The specification for
$`z_{2}`$ instead declares a task-metric improvement, with $`p_{1}`$
included in its required conditions. These declarations determine both
what is measured and which implementation is a meaningful control. A
successful property check establishes the context for testing $`z_{2}`$;
the downstream experiment then assesses its own declared effect. The
planner records these roles before execution so that a decision that
supplies a prerequisite is assessed by its intended property even when
its standalone task metric does not improve in isolation under the same
evaluation protocol.

The planner uses a language model to propose decisions, dependencies,
and tests from the method, task, literature summary, and baseline
evidence. A review agent (the critic) checks whether the tests assess
the expected effects under the required conditions. The planner revises
the proposal using this feedback. The plan is accepted after review
finds no outstanding issues and graph validation passes;
Section [2.2](#S2.SS2 "2.2 Ablation Planning ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
describes the graph and the prerequisite checks used to validate it.

When an effect requires several decisions to act together, the planner
groups them into one component with a shared specification and test. The
plan records the original decisions and their external dependencies. The
result is attributed to the group.

### 2.2 Ablation Planning

Ablation analysis compares algorithm configurations to assess particular
changes ([Abramovich and Chechik, 2026](#bib.bib19)). Fix the baseline,
implementations, and evaluation conditions, and let $`f(C)`$ denote
$`J_{q}`$ for the implementation containing a feasible set $`C`$ of
decision indices. For $`C`$ and $`C\cup\{i\}`$ satisfying the declared
dependencies, the marginal effect of adding decision $`i`$ is

|     |                                                       |     |     |
|-----|-------------------------------------------------------|-----|-----|
|     |
       ``` math
       \delta_{i\mid C}=f(C\cup\{i\})-f(C),\qquad i\notin C.
       ```                                                    |     | (4) |

This difference measures the marginal contribution of decision $`i`$ to
configuration $`C`$ ([Olsen et al., 2024](#bib.bib28)). For $`z_{2}`$
requiring $`z_{1}`$, setting $`C=\{1\}`$ recovers
$`\delta_{2\mid 1}=f(\{1,2\})-f(\{1\})`$. Baseline and
complete-candidate values do not determine its sign because they leave
$`f(\{1\})`$ unobserved
(Proposition [1](#Thmproposition1 "Proposition 1 (Insufficiency of baseline and complete-candidate evaluations). ‣ D.1 Baseline and Complete-Candidate Evaluations ‣ Appendix D Proofs ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).
Testing $`z_{1}`$ supplies this control measurement; the property check
assesses whether this implementation provides the declared intermediate
property.

Let $`V`$ index the components. The conditions $`D_{i}`$ describe what
component $`i`$ requires; $`d_{i}^{0}`$ identifies the other components
whose outputs or properties it directly needs. An edge $`(j,i)`$ denotes
such a dependency. Other conditions, such as the data split and
measurement settings, are specified in the experimental protocol. The
set $`K_{i}`$ contains all ancestors of $`i`$, including indirect
prerequisites:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle A_{0}`$ | $`\displaystyle=\{(j,i):j\in d_{i}^{0}\},\qquad G_{0}=(V,A_{0}),`$ |  | (5) |
|  | $`\displaystyle K_{i}`$ | $`\displaystyle=\bigcup_{j\in d_{i}^{0}}\bigl(\{j\}\cup K_{j}\bigr).`$ |  |  |

Graph validation checks identifiers, acyclicity, and agreement between
$`K_{i}`$ and the declared prerequisites
(Appendix [A](#A1 "Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).
The control $`P_{i}`$ retains prerequisites; treatment $`T_{i}`$ adds
the change:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
P_{i}=\operatorname{Build}(M_{0},K_{i}),\qquad T_{i}=P_{i}\oplus\Delta_{i}.
``` |  | (6) |

$`\operatorname{Build}`$ combines saved implementations of the required
components with the baseline. The operator $`\oplus`$ applies the tested
component’s implementation change to this control. Implementation review
checks that the resulting code follows the specification.
Appendix [A](#A1 "Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
details this merge.

For $`z_{1}\to z_{2}`$, the test compares $`z_{1}+z_{2}`$ with
$`z_{1}`$, preserving the representation required by the objective.
Testing $`z_{c}`$ in $`z_{a}\to z_{b}\to z_{c}`$ retains both $`z_{a}`$
and $`z_{b}`$. Thus, the control contains every required component
together with its own prerequisites.

For a component $`u`$ representing a group $`S`$, the experiment applies
the decisions together to a control containing their external
prerequisites. The shared specification defines the expected effect of
this combined change. The result is attributed to the group, and the
record identifies all participating decisions without assigning separate
gains to individual members. The revised graph must remain acyclic.
Appendix [A](#A1 "Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
gives the construction algorithm and examples;
Appendix [D](#A4 "Appendix D Proofs ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
proves that baseline and complete-candidate evaluations alone cannot
determine the improvement in
[equation 4](#S2.E4 "In 2.2 Ablation Planning ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research"),
and that $`K_{i}`$ is the smallest set satisfying the declared
dependencies.

### 2.3 Executing and Assessing Experiments

The procedure $`\rho_{i}`$ specifies how to run the experiment; the
protocol $`\omega_{i}`$ specifies the evaluation conditions and
measurement settings shared by control and treatment:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
O_{i}^{-}=\operatorname{Run}(\mathcal{E},P_{i};\rho_{i},\omega_{i}),\qquad O_{i}^{+}=\operatorname{Run}(\mathcal{E},T_{i};\rho_{i},\omega_{i}).
``` |  | (7) |

The records $`O_{i}^{-}`$ and $`O_{i}^{+}`$ link observations to their
implementations and execution attempts. Both runs use the validation
rule specified in $`s_{i}`$. Matching conditions controls data and
execution differences; training randomness also affects performance
comparisons ([Bosma et al., 2024](#bib.bib29)).

For valid executions with finite measurements and correctly matched
reports, let $`m_{i}^{-}`$ and $`m_{i}^{+}`$ be the control and
treatment metrics, and let $`d_{q}\in\{-1,1\}`$ denote minimization or
maximization. The numerical test criterion is expressed by the
predeclared predicate
$`\phi_{i}(y)=\mathbf{1}[y\ \bowtie_{i}\ \theta_{i}]`$, with
$`\bowtie_{i}\in\{<,\leq,=,\geq,>\}`$ and threshold $`\theta_{i}`$. The
resulting criterion separates performance tests from property checks
according to the declared experimental objective:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\delta_{i}`$ | $`\displaystyle=d_{q}(m_{i}^{+}-m_{i}^{-}),`$ |  | (8) |
|  | $`\displaystyle g_{i}`$ | $`\displaystyle=\begin{cases}\mathbf{1}[\delta_{i}>\max(0,\epsilon_{i})]\,\phi_{i}(y_{i}^{\rm test}),&\text{performance test},\\
\phi_{i}(a_{i}^{\rm obs}),&\text{property check}.\end{cases}`$ |  |  |

A performance test requires improvement beyond zero and the protocol
threshold $`\epsilon_{i}`$, and applies $`\phi_{i}`$ to
$`y_{i}^{\rm test}\in\{\delta_{i},m_{i}^{+}\}`$ as specified before
execution. A property check applies $`\phi_{i}`$ to the reported
intermediate observable $`a_{i}^{\rm obs}`$. An observable such as the
number of failed property checks can summarize several assertions.
Appendix [A](#A1 "Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
gives the full numerical and report-matching checks.

Execution validity and effect assessment are separate. A checkpoint is
*qualified* for retention after successful execution, implementation
review, task checks, and a passed test, with no pending plan revision. A
component is *accepted* when its search ends with a retained qualified
checkpoint. Failed execution triggers repair; a valid test that fails
its criterion informs revision of the expected effect or design. See
Appendices [A](#A1 "Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
and [C](#A3 "Appendix C State Transitions and Evidence Reuse ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
for details.

### 2.4 Research Memory and Revision

For each component, DAGLoop records the specification version,
prerequisites, checkpoints, code changes, observations, validation
results, and execution artifacts. Each observation remains associated
with the decision, expected effect, conditions, and specification
version tested. These records supply the evidence for subsequent
implementation and method revision.

At research step $`t`$, let $`\mathcal{L}_{t}(j)`$ record component
$`j`$’s history. For active component $`i`$, the agent receives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{H}_{t}(i)=\left(\{\mathcal{L}_{t}(j):j\in K_{i}\cup\{i\}\},\quad\{\operatorname{Summary}(\mathcal{L}_{t}(j)):j\notin K_{i}\cup\{i\}\}\right).
``` |  | (9) |

Detailed histories of the active component and its ancestors let the
agent inspect how the control was built, which prerequisite checks
passed, and how the current attempt differs from earlier ones. Summaries
of other branches supply context for revising the method without
including their full execution traces in each component’s input. Failed
attempts remain available for debugging; method revision receives the
accumulated research memory.

For example, when a valid test of $`z_{2}`$ does not support its
expected gain, the record identifies the control containing $`z_{1}`$.
Revision can reconsider the objective while retaining the supported
representation. If revision changes $`z_{1}`$, the earlier result for
$`z_{2}`$ remains a record of the previous experiment. The revised
representation defines a new control for the objective; testing it again
determines whether the expected effect persists after the prerequisite
changes.

DAGLoop reuses a saved implementation only when its specification,
prerequisite implementations, and recorded execution context remain
compatible. Otherwise, the earlier result stays in memory for reference.
Appendix [C](#A3 "Appendix C State Transitions and Evidence Reuse ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
gives the equality and checkpoint checks used for reuse.

Search processes an active component first; a pending component becomes
ready after its prerequisites are accepted. The agent drafts the first
implementation, debugs execution errors or code that does not follow the
specification, and reassesses the expectation when a valid test fails
its criterion. Otherwise, it improves the implementation. Each operation
uses research memory. Replanning can revise the decomposition or group
decisions within the revision budget. When no component is ready, the
system reports which prerequisites remain unresolved.

Component search retains the best qualified checkpoint. Performance
tests rank checkpoints by the task metric; property checks use the
specified comparison rule, with task performance breaking ties. Search
continues to the attempt limit, retaining the best checkpoint found
(Appendix [C](#A3 "Appendix C State Transitions and Evidence Reuse ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).

### 2.5 Complete-Candidate Evaluation

Once all components are accepted, DAGLoop assembles their checkpoints
and runs the official evaluator. Targeted tests assess effects in the
prerequisite context, whereas the assembled candidate also includes
decisions from other branches. These combinations can change task
performance. Complete-candidate evaluation checks whether the supported
changes improve the full method, and its result enters research memory
to guide the next revision. Only complete candidates that pass the task
checks can replace the current best:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{M}_{t+1}\in\arg\max_{M\in\{\widehat{M}_{t}\}\cup\mathcal{C}_{t}^{\rm valid}}J_{q}(M).
``` |  | (10) |

Here $`\mathcal{C}_{t}^{\rm valid}`$ contains newly evaluated complete
candidates. Component measurements guide revision through memory.

## 3 Related Work

#### Automated AI Research.

Recent work automates method proposal, implementation, experimentation,
and revision. MLAgentBench studies language agents that conduct
machine-learning experiments; The AI Scientist, its extension using
agentic tree search, and Agent Laboratory address longer research
workflows ([Huang et al., 2024](#bib.bib1); [Lu et al.,
2024](#bib.bib2); [Yamada et al., 2025](#bib.bib3); [Lu et al.,
2026](#bib.bib22); [Schmidgall et al., 2025](#bib.bib23)). AlphaEvolve
uses executable evaluators to guide program and algorithm discovery
([Novikov et al., 2025](#bib.bib4)).

Executable benchmarks make this research loop measurable. MLE-bench,
MLGym, and RE-Bench evaluate agents on executable tasks; MLR-Bench
assesses open-ended research ([Chan et al., 2025](#bib.bib5); [Nathani
et al., 2025](#bib.bib7); [Wijk et al., 2025](#bib.bib6); [Chen et al.,
2025a](#bib.bib8)). ScienceAgentBench evaluates scientific code using
execution results and cost ([Chen et al., 2025b](#bib.bib24)).
ResearchGym, AutoLab, and AutoResearchEval examine longer research
trajectories, artifact improvement, and failures linking experiments to
claims ([Garikaparthi et al., 2026](#bib.bib11); [Xu et al.,
2026](#bib.bib9); [Fei et al., 2026](#bib.bib12)). Our work studies the
evidence used to revise design decisions within these executable
research settings.

#### Evaluator Feedback and Research Memory.

OPRO conditions candidate generation on score histories; FunSearch
selects evaluated programs for further search; Automated Design of
Agentic Systems (ADAS) and AFlow optimize agent designs and workflows
([Yang et al., 2024](#bib.bib13); [Romera-Paredes et al.,
2024](#bib.bib14); [Hu et al., 2025](#bib.bib15); [Zhang et al.,
2025](#bib.bib16)). MetaReflection uses past reflections; TextGrad and
Trace optimize variables using textual and execution feedback ([Gupta et
al., 2024](#bib.bib26); [Yuksekgonul et al., 2025](#bib.bib27); [Cheng
et al., 2024](#bib.bib17)). The AI Scientist maintains an experimental
journal, Meta-Harness exposes earlier candidates’ code, scores, and
traces, and ResearchLoop organizes questions, evidence, and claims as
durable research state ([Lu et al., 2026](#bib.bib22); [Lee et al.,
2026](#bib.bib18); [Xia and Wang, 2026](#bib.bib20)). AutoResearchEval
examines links between implementations, observations, and claims ([Fei
et al., 2026](#bib.bib12)). Our memory associates each outcome with the
tested decision, expected effect, and prerequisite context, so revision
can use evidence at the level of the decision being changed.

#### Ablation Planning and Experimental Attribution.

AbGen and AblationBench evaluate whether language models can design
informative ablations, and The AI Scientist includes ablations in its
experiment schedule ([Zhao et al., 2025](#bib.bib25); [Abramovich and
Chechik, 2026](#bib.bib19); [Lu et al., 2026](#bib.bib22)). Software
composition also requires explicit component dependencies. Cordis
represents these dependencies, motivating our description of the
properties that one decision requires from another ([Shi et al.,
2026](#bib.bib21)). DAGLoop uses these dependencies to construct the
control implementation for each targeted experiment during revision. It
distinguishes task improvement from a property required by another
decision and uses joint tests when an expected effect requires several
decisions. The evidence guides decision retention, revision, and further
testing.

## 4 Experiments

We evaluate DAGLoop on diverse executable research tasks. We use AutoLab
as the main benchmark and compare with locally run Terminus-2 using
GLM-5.2 with maximum reasoning effort or reasoning disabled, and
DeepSeek-V4-Flash with reasoning disabled. We also evaluate on
FML-Bench; its results are reported in
Appendix [G](#A7 "Appendix G Additional FML-Bench Results ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research").

### 4.1 Benchmark and Task Protocol

We use all 36 official AutoLab tasks: 25 CPU tasks and 11 GPU tasks
covering CPU optimization, CUDA kernels, program synthesis, and model
development ([Xu et al., 2026](#bib.bib9)). Each task provides a
baseline repository, evaluator, reward rule, correctness checks, and
protected task files. DAGLoop reproduces the baseline locally, proposes
a candidate, constructs the dependency DAG, runs component experiments,
and evaluates candidate checkpoints.

The primary comparison uses GLM-5.2, with maximum reasoning effort for
both DAGLoop and Terminus-2. The additional comparisons disable
reasoning for both agents, using either GLM-5.2 or DeepSeek-V4-Flash.
All AutoLab GPU experiments for both agents run on NVIDIA H800 GPUs. The
comparison uses the official Terminus-2 agent in Harbor 0.3.0 and the
original task verifiers ([Harbor Framework Team, 2026](#bib.bib30)).
Both agents run to completion with AutoLab’s task-level time budgets
disabled.

For each DAGLoop configuration, we report one selected result per task.
The reasoning-disabled Terminus-2 scores are arithmetic means of two
local runs; the reasoning-enabled reference retains the existing
reported scores.
Section [2.5](#S2.SS5 "2.5 Complete-Candidate Evaluation ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
describes how the system selects its final complete candidate.
Appendix [F](#A6 "Appendix F Full AutoLab Results ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
reports all task scores and their normalization and aggregation
conventions.

Higher scores are better. We report task scores and means for the full
suite, CPU tasks, and GPU tasks. Reward thresholds and clipping can
produce ties despite different native metrics. Native metrics are listed
in their original units when available for the selected result; the
paired comparison uses task scores. Win, tie, and loss counts compare
scores rounded to six decimal places, matching the precision of the
reported reference.

complete-candidate result answer different questions: the former
isolates a decision under its prerequisites, while the latter tests the
assembled method.

Taken together, these chains show why the ablation record separates
direct performance gains, enabling property checks, and joint results. A
direct gain supports retaining a decision for the tested context; a
passed property check makes a prerequisite available to downstream
tests; and a joint result evaluates an interaction that cannot be
assigned to either component alone. This distinction lets the agent
revise the relevant decision rather than treating every change in the
final task score as evidence for every component.

## 5 Limitations

Decision-level evidence assesses the declared effect under the tested
conditions. Its reliability depends on the decomposition, prerequisite
graph, observable, and the experiment’s statistical power. It does not
identify a unique causal explanation, and joint tests attribute results
to the merged component when member-level isolation is not meaningful.
The end-to-end benchmark measures the complete DAGLoop workflow.

DAGLoop addresses candidate-method improvement under executable task
constraints. Evidence reuse depends on recorded context: changes to
data, hardware, evaluation, or upstream decisions can require new
experiments. Repeated optimization against a fixed evaluator can overfit
task artifacts. Broader scientific generalization and revision of the
research agent itself require separate evaluation.

## 6 Conclusion

We present DAGLoop as a general-purpose research system for executable
method improvement. It connects candidate-method revision to targeted
experiments on its constituent design decisions. Experimental
specifications link each decision’s rationale and expected effect to
tests that preserve its prerequisites. Structured research memory
carries the outcomes into subsequent revisions, while complete-candidate
evaluation measures task performance. Preserving prerequisites lets the
agent assess intermediate properties and downstream effects in their
intended context. Joint experiments assess effects that require several
decisions to act together, while the accumulated records guide further
tests when the evidence remains unresolved. On 36 AutoLab tasks, DAGLoop
obtains a mean task score of 0.6459, compared with 0.5831 for Terminus-2
using GLM-5.2 with maximum reasoning effort. DAGLoop scores higher on 19
tasks, ties on seven, and scores lower on ten. With reasoning disabled,
DAGLoop also has higher mean scores for GLM-5.2 (0.5485 versus 0.4266)
and DeepSeek-V4-Flash (0.5340 versus 0.4202), under the score
conventions in
Appendix [F](#A6 "Appendix F Full AutoLab Results ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research").
The research output records which expectations were supported, under
which prerequisites, and which remain unresolved.

## Ethics Statement

Automated research consumes compute and can amplify errors in
experimental interpretation. DAGLoop retains evaluator requirements,
experiment records, and the context of each result. The authors remain
responsible for resource use, interpretation, and reported claims.

### A.1 Graph Construction and Comparison Configurations

Let $`N`$ convert component names to a consistent identifier format
(Appendix [C](#A3 "Appendix C State Transitions and Evidence Reuse ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")).
The declared dependencies $`d_{i}^{0}`$ and ancestor sets $`K_{i}`$ are
defined in
[equation 5](#S2.E5 "In 2.2 Ablation Planning ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research").

The constructor rejects duplicate identifiers, unknown or
self-referential dependencies, and cycles. Kahn’s topological sort,
using a first-in, first-out (FIFO) queue for eligible nodes, gives the
order $`\pi`$ in which the ancestor sets are computed, preserving the
input traversal order when nodes become eligible together. The plan also
declares $`a_{i}`$, the set of components that must be accepted before
testing component $`i`$. The constructor removes redundant direct edges,
retaining the parents $`d_{i}`$, and requires $`a_{i}`$ to equal all
ancestors:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle d_{i}`$ | $`\displaystyle=d_{i}^{0}\setminus\{j\in d_{i}^{0}:\exists k\in d_{i}^{0}\setminus\{j\},\ j\in K_{k}\},`$ |  | (11) |
|  | $`\displaystyle a_{i}`$ | $`\displaystyle=K_{i},\qquad A=\{(j,i):j\in d_{i}\}.`$ |  |  |

The equality is a validation requirement: a missing ancestor or an
unrelated component causes rejection. Semantic adequacy of the proposed
dependencies and tests is assessed by the critic.

$`\operatorname{Build}`$ restores the checkpoints of the required
components and combines their files with the baseline. When multiple
branches contribute changes, it uses a shared earlier version as the

checks whether the code follows the specification for the active

both incident dependencies gives $`u\to z_{b}\to u`$ and is rejected.

### A.2 Numerical Criteria and Checkpoint Qualification

$`\mathsf{Fin}(v_{1},\ldots,v_{k})`$ is true when every argument is a
finite numerical value and none is Boolean. For a performance test, the
predicate specified before execution chooses
$`y_{i}^{\rm test}=\delta_{i}`$ or $`m_{i}^{+}`$, and the numerical
acceptance criterion is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
g_{i}^{\rm dir}=\mathbf{1}[\mathsf{Fin}(m_{i}^{-},m_{i}^{+})]\,\mathbf{1}[\delta_{i}>0]\,\phi_{i}(y_{i}^{\rm test})\,\mathbf{1}[\delta_{i}>\epsilon_{i}].
``` |  | (12) |

Here $`\epsilon_{i}`$ is the minimum improvement specified by the
measurement protocol, with $`\epsilon_{i}=0`$ for a test requiring
positive improvement. Thus a positive observed gain must also satisfy
the declared predicate. For a property check, let $`a_{i}^{\rm obs}`$ be
its reported intermediate observable and $`b_{i}=1`$ indicate exactly
one report matching the specified test and linked to its execution
record. Its acceptance criterion is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
g_{i}^{\rm ena}=b_{i}\,\mathbf{1}[\mathsf{Fin}(a_{i}^{\rm obs})]\,\phi_{i}(a_{i}^{\rm obs}).
``` |  | (13) |

An aggregate observable, such as the number of failed property checks,
can summarize several assertions. The execution script computes that
aggregate; the criterion compares it with the threshold specified before
execution.

Numerical acceptance and checkpoint qualification are separate. For
attempt $`t`$, let $`e_{it}`$ indicate successful execution, $`h_{it}`$
an existing checkpoint, $`r_{it}`$ a requested plan revision, and
$`c_{it}`$ a review of task constraints that has not blocked the
attempt. Method implementation review (MIR), denoted by
$`\mathrm{MIR}_{it}`$, assesses whether the code implements the
specified method. Let $`g_{it}`$ be $`g_{i}^{\rm dir}`$ or
$`g_{i}^{\rm ena}`$ according to the test type. Qualification is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
q_{it}=e_{it}h_{it}(1-r_{it})c_{it}\,\mathbf{1}[\mathrm{MIR}_{it}\in\{\mathrm{faithful},\mathrm{partial}\}]\,g_{it}.
``` |  | (14) |

A partial implementation supports only the implemented and tested scope.
Failed attempts remain in the history, while an earlier qualified
checkpoint can be retained.

### A.3 Memory Records and Feedback Scheduling

The component histories record the specification reference, ancestor
set, checkpoints, code difference, observations, validation results, and
execution artifacts. We write an attempt record as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
F_{it}=(z_{i},\nu_{i},e_{i},D_{i},P_{i},O_{it}^{-},O_{it}^{+},g_{it},q_{it},\mathcal{A}_{it}),
``` |  | (15) |

where $`\nu_{i}`$ identifies the specification version and
$`\mathcal{A}_{it}`$ references supporting artifacts.

Let
$`\sigma_{t}(i)\in\{\mathrm{pending},\mathrm{active},\mathrm{accepted},\mathrm{exhausted}\}`$
denote search not yet started, search in progress, search ended with a
qualified checkpoint, and attempts exhausted without one, respectively.
With topological order $`\pi`$, define

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathcal{U}_{t}`$ | $`\displaystyle=\{i:\sigma_{t}(i)=\mathrm{active}\},`$ |  | (16) |
|  | $`\displaystyle\mathcal{R}_{t}`$ | $`\displaystyle=\{i:\sigma_{t}(i)=\mathrm{pending},\ \forall j\in d_{i},\ \sigma_{t}(j)=\mathrm{accepted}\},`$ |  |  |
|  | $`\displaystyle i_{t}`$ | $`\displaystyle=\begin{cases}\min_{\pi}\mathcal{U}_{t},&\mathcal{U}_{t}\neq\varnothing,\\
\min_{\pi}\mathcal{R}_{t},&\mathcal{U}_{t}=\varnothing,\ \mathcal{R}_{t}\neq\varnothing,\\
\bot,&\text{otherwise}.\end{cases}`$ |  |  |

$`\min_{\pi}`$ denotes the first component in the stored order; $`\bot`$
denotes no available component or checkpoint. Thus an active component
is processed before a newly ready one.

Let $`n_{i}`$ count started attempts, $`u_{i}`$ infrastructure attempts
that did not start, and $`\ell_{i}`$ the last outcome. The next
implementation action is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\operatorname{Op}(i)=\begin{cases}\textsc{Draft},&n_{i}=u_{i}=0,\\
\textsc{Debug},&\ell_{i}\in\mathcal{F}_{\rm impl},\\
\textsc{Check-Expectation},&\ell_{i}=\mathrm{contract\_failed},\\
\textsc{Improve},&\text{otherwise}.\end{cases}
``` |  | (17) |

Here contract_failed denotes a valid execution whose result fails the
declared test criterion. $`\mathcal{F}_{\rm impl}`$ contains execution
failure, implementation failure, a missing checkpoint, and code changes
that depart from the specification. Check-Expectation reassesses the
expected effect when a valid test fails its criterion; Debug repairs
execution or implementation errors. The agent uses the selected action
and research memory to generate the next implementation. A failed design
or test can prompt replanning within the revision budget, including a
revised decomposition or a group of decisions tested together.

Component search retains the best qualified checkpoint. Performance
tests rank checkpoints by the task metric. Property checks use the
specified comparison rule, with task performance breaking ties. Search
continues until its attempt limit is reached;
[equation 18](#A3.E18 "In Qualification and retained checkpoints. ‣ Appendix C State Transitions and Evidence Reuse ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
gives the resulting state.

  end while
- 27:
  return $`\widehat{M},\mathcal{L}`$

## Appendix B Plan and Experiment Records

For each component, DAGLoop stores its specification and the history of
implementation and evaluation attempts. The following fields describe
these records.

The design fields specify the component identifier, purpose, mechanism,
inputs, outputs, and dependencies. The experiment fields specify the
expected effect, test type, and acceptance criterion. The implementation
check describes how to assess whether the code follows the design; the
optimization space specifies which changes are allowed; the downstream
requirements state the properties required by later components. A
performance test compares task performance, and a property check checks
an intermediate property. Joint tests also record their original
decisions. The tuple $`s_{i}`$ groups the design and experiment fields
for each component.

An attempt records the implementation action, ancestor set, checkpoints,
code difference, measurements, implementation review, review of task
constraints, and artifact references. Commands and execution records
link observations to the corresponding attempt. The record $`F_{it}`$ in
[equation 15](#A1.E15 "In A.3 Memory Records and Feedback Scheduling ‣ Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
summarizes these fields. The research memory in
[equation 9](#S2.E9 "In 2.4 Research Memory and Revision ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
preserves detailed current-component and ancestor histories and
summarizes other branches.

## Appendix C State Transitions and Evidence Reuse

#### Graph and semantic checks.

The identifier map $`N`$ trims and lowercases strings, replaces runs of
non-alphanumeric characters with a hyphen, and assigns an index-based
identifier when the result is empty. The constructor computes ancestor
sets, removes redundant edges, and validates acceptance prerequisites
according to
[equations 5](#S2.E5 "In 2.2 Ablation Planning ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
and [11](#A1.E11 "Equation 11 ‣ A.1 Graph Construction and Comparison Configurations ‣ Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research").
Inputs and outputs are checked for structure and nonemptiness; the
critic evaluates their semantic compatibility and the adequacy of the
proposed tests. A merged component passes the ordinary DAG checks after
replanning.

#### Control measurement.

A root component has no prerequisites and uses the baseline as its
control. For a single direct parent, the component history can provide
that parent’s finite metric. Components with multiple direct
prerequisites require a measurement of the combined control
implementation. A reported control attempt can supply this value after
matching the control implementation, source state, and evaluation
settings. Control reuse checks the saved measurement evidence, protocol,
and restorable checkpoint. A control value that fails these checks is
cleared. Protocol identity is defined by the recorded evaluation
configuration.

#### Numerical predicates and repetitions.

The criterion for performance tests accepts one comparison of signed
metric improvement or candidate metric with a finite numerical constant.
The criterion for property checks accepts one scalar comparison,
including a reported aggregate such as a failed-check count. Unsupported
expressions return a plan-format error. Boolean, missing, and nonfinite
values fail the numerical check. Equality is exact unless tolerance is
expressed in the declared observable or predicate. The measurement
protocol specifies the reported statistic. For repeated measurements,
the execution system checks the sample count, finite control and
treatment samples, and the specified mean or median against the reported
aggregate. These criteria serve as threshold filters for search
decisions.

#### Qualification and retained checkpoints.

In
[equation 14](#A1.E14 "In A.2 Numerical Criteria and Checkpoint Qualification ‣ Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research"),
the task-constraint indicator excludes violation and
insufficient_evidence. Qualification additionally requires successful
execution, an existing checkpoint, a faithful or partial implementation
review, a passed component test, and no pending plan revision. The
latest attempt’s test result and the retained checkpoint’s test result
are stored separately.

Let $`\widehat{T}_{i}^{t}`$ be the retained qualified checkpoint after
attempt $`t`$ and $`N_{i}`$ the component attempt limit. Search
continues to this limit, preserving the best qualified checkpoint. After
a started attempt, the state is updated as follows:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\sigma_{t+1}(i)=\begin{cases}\mathrm{accepted},&n_{i}\geq N_{i},\ \widehat{T}_{i}^{t}\neq\bot,\\
\mathrm{exhausted},&n_{i}\geq N_{i},\ \widehat{T}_{i}^{t}=\bot,\\
\mathrm{active},&\text{otherwise}.\end{cases}
``` |  | (18) |

A non-started attempt instead increments $`u_{i}`$ and follows the
infrastructure limit. On exhaustion, an existing qualified checkpoint is
preserved; otherwise the workflow reports infrastructure exhaustion. For
a property check, checkpoints are ranked using the specified comparison
direction. Equality tests use distance from the target value, and task
performance breaks ties.

#### Checkpoint reuse.

Write $`c_{j}`$ for a component’s recorded specification and acceptance
requirements, $`h_{j}`$ for its retained checkpoint identity, and
$`\mathbf{h}_{d_{i}}`$ for the ordered direct-parent checkpoint
identities. An old accepted checkpoint can enter a new component history
only if

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\operatorname{Inherit}(i)={}`$ | $`\displaystyle\operatorname{ExecMatch}\ \land\ \operatorname{Restorable}(h_{i})`$ |  | (19) |
|  |  | $`\displaystyle\land\;\bigl(\forall j\in K_{i}\cup\{i\},\ c_{j}^{\rm new}=c_{j}^{\rm old}\bigr)`$ |  |  |
|  |  | $`\displaystyle\land\ \bigl(\forall j\in K_{i},\ \sigma^{\rm new}(j)=\mathrm{accepted},\ h_{j}^{\rm new}=h_{j}^{\rm old}\bigr)`$ |  |  |
|  |  | $`\displaystyle\land\ (\mathbf{h}_{d_{i}}^{\rm new}=\mathbf{h}_{d_{i}}^{\rm old}).`$ |  |  |

$`\operatorname{ExecMatch}`$ compares execution identifiers derived from
baseline records. A specification reference identifies the tested
version of the design, a protocol identifier denotes the recorded
evaluation configuration, and a checkpoint identifier locates the saved
implementation. These checks associate reuse with the recorded
experiment. Old records remain in history when a checkpoint cannot be
reused in the revised context.

#### Resource limits.

Resource limits apply to component implementation attempts, experiment
launches, individual commands, and revisions of the candidate method.
The reference configuration uses six component attempts, six experiment
launches per sandbox, 7,200 seconds per command, and three outer
revisions. A control measurement counts as an experiment launch. An
executed failure consumes a component attempt; a failure before
execution increments the separate infrastructure count. Component
progress does not consume an outer method-revision round. Cost is
recorded, and component selection follows
[equation 16](#A1.E16 "In A.3 Memory Records and Feedback Scheduling ‣ Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research").

## Appendix D Proofs

### D.1 Baseline and Complete-Candidate Evaluations

For the metric $`f`$ on feasible configurations and the marginal effect
in
[equation 4](#S2.E4 "In 2.2 Ablation Planning ‣ 2 Method ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research"),
we have:

###### Proposition 1 (Insufficiency of baseline and complete-candidate evaluations).

For an arbitrary deterministic metric $`f`$, the baseline value
$`f(\varnothing)`$ and complete-candidate value $`f(\{1,2\})`$ do not
determine the sign of $`\delta_{2\mid 1}`$.

###### Proof.

Consider two metrics on the three feasible configurations:

|  |  |  |
|----|----|----|
|  |
``` math
\begin{array}[]{c|ccc|c}&f(\varnothing)&f(\{1\})&f(\{1,2\})&\delta_{2\mid 1}\\
\hline\cr f_{A}&0&0&1/2&1/2\\
f_{B}&0&1&1/2&-1/2\end{array}
``` |  |

Both metrics lie in $`[0,1]`$ and have identical baseline and
complete-candidate values. Any rule that receives only those two values
has identical inputs in the two cases, although the marginal effects
have opposite signs. It therefore cannot determine the sign for all
metrics. ∎

### D.2 Minimal Prerequisite Context

A set $`C\subseteq V`$ is *closed under prerequisites* if $`j\in C`$
implies $`d_{j}^{0}\subseteq C`$.

###### Proposition 2 (Minimal prerequisite context).

For a DAG $`G_{0}`$, $`K_{i}`$ is the unique smallest set containing
$`d_{i}^{0}`$ that is closed under prerequisites. Also,
$`i\notin K_{i}`$, $`K_{i}\cup\{i\}`$ is closed under prerequisites, and
the edge reduction in
[equation 11](#A1.E11 "In A.1 Graph Construction and Comparison Configurations ‣ Appendix A Detailed Experimental Procedure ‣ DAGLoop: Aligning Method Designwith Experimental Feedbackin Automated AI Research")
preserves every ancestor set.

###### Proof.

Every member of $`K_{i}`$ lies on a directed path to $`i`$. If
$`j\in K_{i}`$ and $`k\in d_{j}^{0}`$, appending the path from $`j`$ to
$`i`$ shows $`k\in K_{i}`$, so $`K_{i}`$ is closed under prerequisites.
It contains $`d_{i}^{0}`$. Conversely, any set containing $`d_{i}^{0}`$
that is closed under prerequisites must contain every predecessor along
each path ending at $`i`$, hence all of $`K_{i}`$. This proves
uniqueness and minimality. Acyclicity gives $`i\notin K_{i}`$, and
adding $`i`$ preserves closure because $`d_{i}^{0}\subseteq K_{i}`$.

For the reduction, process vertices in topological order. A removed
parent $`j\in d_{i}^{0}`$ is an ancestor of another direct parent $`k`$.
Following this relation among direct parents must terminate at a
retained parent $`k^{*}`$, since the graph is finite and acyclic. By
induction, the reduced graph on the earlier vertices preserves the path
from $`j`$ to $`k^{*}`$. The retained edge $`(k^{*},i)`$ therefore
preserves reachability from $`j`$ to $`i`$. Retained edges are original
edges, so the reduction creates no new reachability. Induction over
$`\pi`$ establishes equality of all ancestor sets. ∎

### E.1 BM25 Retrieval in Go

The AutoLab task uses BM25 retrieval with term frequency, inverse
document frequency (IDF), and document-length normalization ([AutoLab
Authors, 2026](#bib.bib31)). For query $`u`$ and document $`d`$, the
task computes the following retrieval score:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\operatorname{BM25}(u,d)`$ | $`\displaystyle=\sum_{w\in\operatorname{uniq}(u)}\operatorname{IDF}(w)\,\frac{\operatorname{tf}(w,d)(k_{1}+1)}{\operatorname{tf}(w,d)+k_{1}(1-b+b|d|/\overline{L})},`$ |  | (20) |
|  | $`\displaystyle\operatorname{IDF}(w)`$ | $`\displaystyle=\log\left(1+\frac{N-\operatorname{df}(w)+0.5}{\operatorname{df}(w)+0.5}\right),\quad k_{1}=1.2,\quad b=0.75.`$ |  |  |

Here $`N`$ is the corpus size, $`\operatorname{df}(w)`$ counts documents
containing $`w`$, $`\operatorname{tf}(w,d)`$ counts its occurrences in
$`d`$, and $`\overline{L}`$ is mean document length.
$`\operatorname{uniq}(u)`$ denotes unique query terms, so repeated
tokens are counted once; $`|d|`$ is document length. The output contains
at most ten positive-score documents, ordered by decreasing score and
increasing document identifier on ties. An empty query returns no
results for the retrieval task.

The correctness check compares the batch query count, hit count, and
checksum with the reference. Scores are rounded after multiplication by
$`10^{6}`$ before checksum aggregation. The timing workload uses 4,000
documents and 40 queries, with the median over five query seeds:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
m_{\rm BM25}(M)=\operatorname{median}_{r=1}^{5}t\bigl(\operatorname{NewEngine}_{M}(\mathcal{D}),\operatorname{RunQueries}_{M}(\mathcal{U}_{r})\bigr).
``` |  | (21) |

The measured interval includes index construction, query processing,
ranking, and batch checksum computation. It excludes compilation, corpus
and query generation, the preceding correctness check, and printing.

For measured seconds $`t>0`$, the official task reward is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R_{\rm BM25}(t)=\begin{cases}0,&2.1/t\leq 1,\\
\min\{1,\tfrac{1}{2}\log(2.1/t)/\log(2.1/0.03)\},&2.1/t>1.\end{cases}
``` |  | (22) |

The scoring anchors $`2.1`$ and $`0.03`$ are benchmark constants; local
relative improvement uses the locally reproduced baseline instead.

### E.2 Transforms, Joins, Storage, and Model Training

#### Fourier transform (fft_rust).

For a real signal $`x\in\mathbb{R}^{n}`$ with $`n=32768`$, the task
computes the complex discrete Fourier transform

|  |  |  |  |
|----|----|----|----|
|  |
``` math
X_{k}=\sum_{j=0}^{n-1}x_{j}\exp(-2\pi\mathrm{i}jk/n),\qquad 0\leq k<n.
``` |  | (23) |

The metric is the median duration of the transform call. Parseval and
spectral-checksum checks use the task’s $`10^{-6}`$ relative tolerance.
The implementation is single-threaded Rust using the standard library
for the transform.

#### Hash join (hash_join).

Given indexed integer key–payload tables $`R=(r_{a})_{a=1}^{n_{R}}`$ and
$`S=(s_{b})_{b=1}^{n_{S}}`$, the task computes the matching row pairs of
an inner equijoin

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{J}=\{(a,b):1\leq a\leq n_{R},\ 1\leq b\leq n_{S},\ r_{a}.\mathrm{key}=s_{b}.\mathrm{key}\}.
``` |  | (24) |

Every matching row pair contributes, including duplicate keys. The
output is a match count and a 64-bit checksum. The benchmark uses 20,000
rows in $`R`$ and five million in $`S`$, measuring one join call after
warm-up under a single-thread constraint.

#### Number-theoretic transform (ntt_butterfly_cuda).

For $`a\in\mathbb{F}_{p}^{n}`$, the forward transform has the form

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A_{k}=\sum_{j=0}^{n-1}a_{j}\omega^{jk}\pmod{p},\qquad p=2^{64}-2^{32}+1,
``` |  | (25) |

where $`\omega`$ is the task’s forward $`n`$th root of unity. The CUDA
implementation returns canonical field elements in natural order, in
place. Correctness is bit-exact, and latency is the median CUDA-event
time after warm-up, using the prescribed workspace.

#### Multi-scalar multiplication (msm_pippenger_bls12_381_cuda).

The task maps BLS12-381 $`G_{1}`$ points $`P_{i}`$ and 256-bit scalars
$`s_{i}`$ to

|     |                               |     |      |
|-----|-------------------------------|-----|------|
|     |
       ``` math
       Q=\sum_{i=1}^{n}[s_{i}]P_{i}.
       ```                            |     | (26) |

The evaluator checks the affine output in the required Montgomery
representation and measures median CUDA-event latency. The released
starter uses naive double-and-add.

#### SSTable compaction (sstable_compaction_rs).

Sorted string tables store ordered key–value entries on disk. This task
merges several prefix-compressed tables, retains the visible latest
value for each key, and removes shadowed or deleted entries. It verifies
live-entry count, checksum, and output size. The median of five
compaction calls includes decoding, merging, and output construction,
while input generation occurs outside the measured interval.

#### Visual reasoning (grpo_multisource).

Group relative policy optimization (GRPO) fine-tunes Qwen2.5-VL-7B using
Geometry3K, MathVision, and ChartQA, producing a low-rank adaptation
(LoRA) adapter. The final native metric is accuracy on 100 held-out
MathVista examples. Let $`a`$ be this accuracy and $`r`$ the general
visual question answering (VQA) accuracy retention on 50 examples. The
task reward is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R_{\rm GRPO}(a,r)=\mathbf{1}[r\geq 0.9]\,\operatorname{clip}_{[0,1]}\left(\frac{a-0.20}{0.65-0.20}\right).
``` |  | (27) |

Retention is the adapted-to-baseline VQA accuracy ratio, defined as one
when baseline VQA accuracy is zero. The smaller local evaluation uses 20
MathVista and 10 VQA examples; the final reward uses the 100-plus-50
evaluation.
